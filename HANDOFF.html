3 · Approach Taken（采取的路径）

实现从“确认实际 cwd”出发，逐步形成一套目录切换事务：先验证目标目录；根据 Shell 类型生成命令；把命令写入当前 PTY；等待 nonce 绑定的回报；核对 Shell 回报目录与目标目录的文件系统身份；最后才提交 renderer、持久化和 Git authority。

  1. 采用实际回报，不采用乐观更新。
    原因：日志证明应用状态和 Shell 实际状态可以不同。被否决方案：仅凭目录选择结果或 PTY write 成功就更新 cwd。
  2. 增加 prompt 后独立观察。
    原因：真实 Git Bash 复现了晚注册 hook 在早期 CwdProof 后再次执行 cd。被否决方案：把启动 ACK 或同一 prompt 中的早期证明当作最终状态。
  3. 脚本失败时保留主动恢复入口。
    原因：用户明确要求把切换命令注入当前 Terminal。被否决方案：只显示 ExecutionPolicy 指令，或者要求用户手动复制命令。
  4. 下一步先缩小范围。
    原因：Git worker、缓存、原生 supervisor 和发布层改动并非即时 cwd 修复的必要组成。被否决方案：继续补充更多代码后再统一验证。

6 · What Didn't Work（已验证无用或过程失误）

  1. 无效方案：执行 Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser。用户确认问题仍存在；它不能改变 cwdProvided:false，也不能解决跨 Shell 与时序问题。
  2. 错误完成点：信任启动脚本 ACK 或早期 CwdProof。晚注册 hook 已证明该证据在 prompt 完成前可能过时。
  3. 生命周期缺陷：失配时直接 dispose PTY 曾先移除 exit listener，导致 renderer 不知道 Terminal 已失效。现有 disposal policy 是修正方向，但 packaged E2E 尚未给出最终证据。
  4. 过程失误：把 cwd 一致性继续扩大成 Git worker、缓存、原生 Job supervisor 和发布流程的一次性重构。结果是 254 个路径尚未形成可审核、可构建、全绿的闭环。
  5. 证据表达不准确：7,800 个组合主要是故障目录/设计清单，不等于 7,800 次真实产品端到端运行。后续汇报必须明确区分。
