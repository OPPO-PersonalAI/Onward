① 问题与现场证据The bug + evidence

现象：在 Git History 里，当前分支 kae-0.36 的本地标签停在 58feede，而远端标签 origin/kae-0.36 却画在 3 个提交之前的 d2b0c86，看起来"当前分支跟远端分叉了"。但磁盘上 kae-0.36 == origin/kae-0.36 == 58feede，二者完全对齐。Onward 把远端标签画在了一个 push 之前的旧位置上。 Symptom: In Git History the local label kae-0.36 sits on 58feede while the remote label origin/kae-0.36 is drawn 3 commits back on d2b0c86 — looking like the branch forked from its remote. But on disk kae-0.36 == origin/kae-0.36 == 58feede, fully aligned. Onward drew the remote label at its pre-push position.

四方实证（已闭环）Four-way confirmation

  • 实仓库：git ls-remote + fetch 后追踪参考都显示 origin/kae-0.36 = 58feede，ahead/behind = 0/0。Repo: git ls-remote + post-fetch tracking ref both show origin/kae-0.36 = 58feede, ahead/behind = 0/0.
  • 截图：本地标签在 58feede，远端标签在 d2b0c86（差 3 个提交）。Screenshot: local label on 58feede, remote label on d2b0c86 (3 commits apart).
  • 诊断包 trace：6 分钟内开了约 10 次 Git History，全部命中同一份缓存，list-cache.hit 的 ageMs 从 64s 涨到 427s（≈7 分钟），且整份 trace 无任何 list-cache.invalidate 事件。Bundle trace: ~10 Git History opens in 6 min, all the same cache entry; list-cache.hit ageMs climbed 64s → 427s (≈7 min); zero list-cache.invalidate events anywhere.
  • 源码：缓存键不含任何 ref 状态（见 ② 节）。Source: the cache key contains no ref state (see §②).

② 当前策略：为什么 push 后会陈旧Current strategy: why it goes stale after push

Git History 列表（L8 缓存）的键只认 HEAD 的 commit OID，且把分支/远端标签（git log 的 %D 字段）一起烤进了缓存值。The Git History list (L8 cache) key tracks only HEAD's commit OID, and bakes the branch/remote labels (git log's %D field) into the cached value.

buildHistoryListCacheKey(cwd, branchOid, limit, skip)
  → `${resolve(cwd)}::${branchOid ?? 'nohead'}::${limit}::${skip}`
// :55  HISTORY_LIST_TTL_MS = 30 * 60 * 1000  (30 分钟保底 TTL)

// electron/main/git-utils.ts:2289-2299 — git log 格式串里含 %D（decoration）

// :1595  解析后塞进 GitCommitInfo.refs（即标签来源）→ 随列表一起被缓存

深层原因：ref 事件"到了门口被吞掉"Deeper cause: the ref event arrives but is swallowed

缓存键的"新鲜度信号"branchOid 来自 GitStateMirror 快照。而 mirror 的变更指纹压根没把 ref 算进去：The key's freshness signal (branchOid) comes from the GitStateMirror snapshot. But the mirror's change-fingerprint does not include refs at all:

git push → origin/kae-0.36: d2b0c86 → 58feede (HEAD 不动 / HEAD unchanged) .git/refs/remotes/origin/kae-0.36 改变 │ ▼ watcher 触发（已监听 .git/refs/** + packed-refs） git-state-mirror-worker-core.ts:146-156 │ ▼ computeDelta 比对 change-fingerprint │ change-fingerprint 输入 = repoRoot + 工作区 status + 工作区文件 stat （不含 ref！） change-fingerprint.ts:52-84 │ ▼ 指纹未变 → delta 为空 → mirror-update 被短路，不广播 │ ▼ getLatest(cwd).branchOid 仍是旧快照 → 缓存键不变 → 命中旧缓存（含旧 %D 标签） ipc-handlers.ts:1857 │ ▼ 最长陈旧 30 分钟（TTL）或直到 HEAD 自己移动
关键认知：Onward 的 watcher 已经监听了 .git/refs/** 和 packed-refs，所以没有 VS Code 那个"漏看 packed-refs"的缺陷（issue #79776）。push 的 ref 事件本来就到了——是"指纹不含 ref"把它吞了。这意味着修复成本很低：信号已在手，只差消费它。 Key insight: Onward's watcher already watches .git/refs/** and packed-refs, so it does not have VS Code's packed-refs gap (issue #79776). The push ref event already arrives — it's the ref-blind fingerprint that swallows it. So the fix is cheap: the signal is in hand; we just need to consume it.

④ 候选方案Candidate options

共同前提：三个方案都需要"让 mirror 开始把 ref 变更暴露出来"（今天 watcher 监听了 ref，但指纹把事件吞了）。区别只在如何消费这个 ref 信号。 Shared prerequisite: all three need the mirror to start surfacing ref changes (today the watcher sees refs but the fingerprint swallows the event). They differ only in how that ref signal is consumed.

A — refsDigest 入缓存键（结构性新鲜度，延续现有 branchOid 模型）refsDigest in the cache key (structural freshness)

键: cwd :: branchOid :: refsDigest :: limit :: skip mirror 每个 recompute 周期算一个 refsDigest（hash 仓库 ref 集，如 git show-ref / for-each-ref 输出） → push 后 origin 移动 → refsDigest 变 → 新键 → 结构性 miss → 重跑 git log（带新 %D）
  • 改动点：MirrorState 加 refsDigest 字段（与 branchOid 并列）；worker recompute 时计算；ipc-handlers.ts:1857 取出并传入 buildHistoryListCacheKey；指纹纳入 ref（让 mirror-update 在 ref 变时也广播）。Touches: add refsDigest to MirrorState (beside branchOid); compute it in the worker recompute; read it at ipc-handlers.ts:1857 and pass into buildHistoryListCacheKey; make the fingerprint ref-aware so mirror-update fires on ref moves.
  • 同行对应：介于 git-graph 与现状之间——仍把 %D 烤进列表，但让键对 ref 敏感。Peer match: between git-graph and the status quo — still bakes %D into the list, but makes the key ref-sensitive.
  • 优点 最小、最贴合现有"结构性新鲜度"哲学（branchOid 已是这个套路）；无新失效接线；复用 mirror 既有 recompute。Pros Minimal; consistent with the existing "structural freshness" philosophy (branchOid already does this); no new invalidation wiring; reuses the mirror's existing recompute.
  • 取舍 任意 ref 移动都会让该仓库所有页换键失效（粗粒度）；标签仍随列表一起重算。因 History 列表只有 50 条且已 prewarm，重算成本低，可接受。需定 refsDigest 范围（建议：全部本地分支 + 全部远端追踪 ref + tag，覆盖图上所有可能标签）。Trade-off Any ref move re-keys (invalidates) all pages for that repo (coarse); labels recompute with the list. Since the list is 50 commits and prewarmed, recompute is cheap → acceptable. Must fix the refsDigest scope (suggest: all local branches + all remote-tracking refs + tags, covering every label that can appear).

B — ref 变更触发强制失效（复用 diff 缓存的现成先例）force-invalidate on ref change (reuse the diff-cache precedent)

键不变（仍 branchOid） ref 变 → mirror-update 广播 → historyListCache 强制失效该仓库所有页（仿 git-state-mirror-router.ts:455 的 gitDiffCacheInvalidator.invalidate(cwd,'mirror')） → 下次开 History → miss → 重跑
  • 改动点：同样需指纹纳入 ref（或加并行 refs 指纹 + 新信号）；在 router 的 mirror-update 分支里，对 history 列表缓存调 invalidateKey/clear（参照 diff 的 git-diff-content-cache-wiring.ts:323）。Touches: also needs the fingerprint ref-aware (or a parallel refs-fingerprint + new signal); in the router's mirror-update branch, call invalidateKey/clear on the history list cache (mirroring diff's git-diff-content-cache-wiring.ts:323).
  • 同行对应：JetBrains 的"按 .git 事件刷新"。Peer match: JetBrains' "refresh on .git event".
  • 优点 复用现成失效信号路径；键保持简单。Pros Reuses an existing invalidation path; keeps the key simple.
  • 取舍 比 A 多一条显式失效接线；同样粗粒度（清整仓库的页）；与现有"结构性新鲜度（靠键）"哲学不完全一致（改成"命令式失效"）。Trade-off One more explicit invalidation wire than A; equally coarse (clears the repo's pages); slightly off the existing "structural freshness via key" philosophy (becomes imperative invalidation).

C — decoration 与提交列表解耦（同行共识 / git-graph + JetBrains 模型）decouple decorations from the commit list (peer consensus)

提交列表缓存（不带 %D，按 sha 不可变，可长 TTL） + ref 来源（mirror 的 ref→sha 映射，或一次 git show-ref） 每次读 History：取缓存列表 → 用当前 ref 映射现场贴标签 → 返回（标签永远新鲜）
  • 改动点：git log 去掉 %D；列表缓存值不再含标签；新增"取 ref 映射 + 合并 decoration"的读时步骤（理想来源是 mirror 现成的 ref 快照，避免额外 git 调用）。Touches: drop %D from git log; the list cache value no longer holds labels; add a read-time "fetch ref map + merge decorations" step (ideally sourced from the mirror's existing ref snapshot to avoid an extra git spawn).
  • 同行对应：最强——git-graph 正是如此；JetBrains 缓存提交、按事件刷 ref；GitLens 按可变性分 TTL。Peer match: strongest — exactly git-graph; JetBrains caches commits + refreshes refs on event; GitLens splits TTL by mutability.
  • 优点 架构最干净；标签永远新鲜；提交列表可用更长 TTL（提交按 sha 不可变）；细粒度（标签变不必重算提交）。Pros Cleanest architecture; labels always fresh; the list can use a longer TTL (commits immutable per sha); fine-grained (label changes don't recompute commits).
  • 取舍 改动面最大（缓存值结构、读时合并逻辑、ref 来源）；风险最高。其核心收益"标签变了不必重算提交"对 Onward 而言较弱——History 列表只有 50 条且已 prewarm，重算本就便宜。Trade-off Largest change (cache payload shape, read-time merge, ref source); highest risk. Its core benefit — "refresh labels without recomputing commits" — is marginal for Onward, where the list is only 50 commits and prewarmed, so recompute is already cheap.

附：短 TTL 缓解（不是真修复）aside: short-TTL mitigation (not a real fix)

把 L8 的 TTL 从 30 分钟降到 ~60 秒（仿 GitLens 的可变-ref 保底 TTL），可把陈旧窗口从 30 分钟压到 60 秒。一行常量改动、零结构风险，但不消除问题：60 秒内重开仍看到旧标签，且会牺牲 prewarm 命中率（30 分钟 TTL 本是为"几分钟后再开仍命中"设计的）。只建议作为临时止血或与 A 叠加。 Drop the L8 TTL from 30 min to ~60 s (à la GitLens's mutable-ref failsafe) to shrink the stale window from 30 min to 60 s. One-constant change, zero structural risk, but does not eliminate it: reopening within 60 s still shows stale labels, and it hurts prewarm hit-rate (the 30-min TTL exists so "reopen minutes later" still hits). Only as a stopgap or layered onto A.

⑥ 推荐Recommendation

推荐 A（refsDigest 入键）+ 让指纹纳入 ref。理由：(1) 它是延续现有 branchOid 结构性新鲜度模型的最小、最一致改动，无新失效接线；(2) Onward 的 watcher 已监听 packed-refs，ref 信号现成；(3) C 的核心收益"标签变了不必重算提交"对 Onward 价值有限——列表仅 50 条且已 prewarm，重算很便宜，所以 C 属过度设计。把 C 记为理想终态（同行共识），若将来 History 规模变大、重算变贵，再演进到 C。 Recommend A (refsDigest in key) + make the fingerprint ref-aware. Why: (1) it's the smallest, most consistent extension of the existing branchOid structural-freshness model, with no new invalidation wiring; (2) Onward's watcher already watches packed-refs, so the ref signal is in hand; (3) C's core benefit — "refresh labels without recomputing commits" — is marginal here (50-commit, prewarmed list → cheap recompute), so C is over-engineering. Record C as the ideal end-state (peer consensus); evolve to it later if History grows large and recompute becomes expensive.
