PDF Git Diff 标注差异 + 外部变更自动刷新 — 设计方案

本文档是策略确认材料：先呈现现状与方案对比，列出取舍，待决策项见 § 8。确认后才动手写实现。

1. 两个需求与结论摘要

需求 2 — Git Diff 里看 PDF 差异（重点是标注差异）。结论：两侧 iframe 其实已经把各自 PDF 里的标注解析出来并广播给宿主了，只是比较组件把消息丢弃。方案是接住两侧标注集合，按标注 id 做三态 diff（新增 / 删除 / 修改），在比较页加一个「标注差异」侧栏，点击条目跳转到对应窗格的标注位置。不需要新增任何 PDF 解析代码，不需要新增 IPC 传输。

需求 3 — PDF 阅读器自动刷新。结论：现状比「缓存不刷新」严重——PDF 完全在监听体系之外，而且标注自动保存用的是 iframe 加载时的内存字节整体重写文件，agent 在后台改过的内容会被静默覆盖。方案是给监听器加二进制模式，外部变更后让 viewer 原地重载文档并恢复页码/缩放/滚动（SumatraPDF/Okular 模式）；「本地有未保存标注时文件被外部改了」的处理策略需要你拍板（§ 5.2）。

2. 现状：代码考古结论

2.1 Git Diff 的 PDF 链路（现状）

git cat-file blobelectron/main/git-utils.ts:3001
→
base64 over IPC整份 PDF，两侧各一份
→
Blob URLGitPdfCompare.tsx:52
→
两个 viewer.html iframeoriginal / modified 窗格
→
onward:pdf:annotationsviewer 已广播，宿主丢弃
  • 比较组件 GitPdfCompare.tsx 仅 214 行，与 Project Editor 的 PdfReader 是两套独立嵌入；窗格可见性决策表（added→仅右、deleted→仅左、modified→双栏）已有纯函数 + 单测锁定。
  • viewer.html 无条件加载全部标注脚本；文档打开后 readAnnotationStateFromPdf() 把 PDF 内的高亮全部读出，并以 onward:pdf:annotations post 给宿主（payload：id/labelId/labelName/color/page/note/textSnapshot/createdAt/updatedAt）。diff 双侧的标注集合在运行时已经存在。
  • 约束：diff 窗格没有文件路径（只有 Blob），任何「回写」类设计在此不可行——但标注 diff 是只读呈现，不受影响。

2.3 三个必须先修的缺陷（不修则需求 3 不成立）

缺陷 1 — 静默覆盖窗口。标注保存的源字节来自 pdfDocument.getData()（iframe 加载时的内存副本），不是磁盘当前内容。agent 改完文件后,你只要加一条高亮，自动保存就把 agent 的修改覆盖掉。annotation-file.js:149
缺陷 2 — suppressNext 对 PDF 保存无效。它只压制普通 change 事件；而我们的 PDF 保存是「临时文件 + rename 覆盖」，走 rename→重建分支，该分支不查压制窗口（file-watch-manager.ts:152）。即使把 PDF 纳入监听，每次自动保存都会自触发一次刷新。另外 PDF 从未被监听，所以当前保存链路里的 suppressNext 调用每次都命中「无监听项」空转。
缺陷 3 — 监听器是纯文本设计。每次事件把整个文件按 UTF-8 读入做内容比对——对 20 MB 的 PDF 既昂贵又语义错误。且整个监听器零 trace 埋点,用户报「没刷新」时拿不到任何证据。宿主侧 pdfAnnotationsDirty 是无人读取的死状态。

3. 同类产品调研（详情与全部引用见 § 9 来源）

需求 2 对照

产品diff 粒度标注感知
GitKraken / Sublime Merge / Fork / Tower二进制,无可视 diff无
diff-pdf / diff-pdf-visually像素级无（标注只是变化的像素）
Adobe Acrobat Compare页面+文本级有,但默认关闭的过滤类别
pyHanko diff_analysisPDF 对象级名义有、实际禁用（视为可疑）
PSPDFKit Instant JSON标注记录级三态模型:create / update / delete 按对象 id 判定

结论：标注级 PDF diff 没有可抄的完整作业；所有认真做标注协作的产品（Zotero/Hypothesis/PSPDFKit）都把标注当记录集处理。我们的标注有稳定 CYY_MARK_Id，照 Instant JSON 的三态模型做记录集 diff 是最干净的路线。

需求 3 对照

产品检测重载保持失败处理
SumatraPDFFS 通知页码/滚动/缩放/侧栏/窗口静默延后,不弹错
Okular监听 dirty 和 created（覆盖原子替换）视口/侧栏/旋转750ms 去抖,每个事件重置计时
Skim默认弹窗询问视图保持,标注丢失写入过快直接报错,官方 wont-fix
LaTeX Workshopwatcher+WebSocketrestoreState 恢复滚动250ms 写入稳定延迟,可调
VS Code 文本编辑器内置 watcher脏缓冲区不动绝不静默重载脏缓冲:Compare / Overwrite / Discard 三选

三条一致技术：写入去抖、快照-恢复视图状态、自动路径失败静默延后。Okular 的教训直接命中我们：原子替换写入会让 modify-only 监听失明——我们的保存正是原子替换。

4. 需求 2 方案：Git Diff 标注差异

4.1 现状 vs 提议架构

两个 iframe已解析并广播标注
→
GitPdfCompare 接住两侧集合新增两个 message case
→
annotationDiffModel.ts纯函数三态 diff,单测锁定
→
标注差异侧栏新增/删除/修改分组列表
→
点击跳转postMessage goToAnnotation 到对应窗格
  • 计算位置：渲染进程。PDF 为了显示本来就要全量传到渲染进程，viewer 本来就要解析标注——在渲染进程做 diff 是零额外成本；主进程解析需要在 Node 侧重写或抽出 CYY_MARK 解析器,是纯增量代码。唯一放弃的能力是「不打开文件就在列表里显示标注变化角标」,那是将来的增强,不影响本需求。
  • 跳转目标选择：新增/修改 → modified 窗格;删除 → original 窗格。viewer 已支持 goToAnnotation 消息,GitPdfCompare 补上转发即可。
  • 单栏情形（文件级 added/deleted）：全部标注按「新增/删除」显示,退化为普通标注列表,决策表照旧。
  • 修改判定的字段集：id 相同则比较 labelId / labelName / color / note / page / textSnapshot,任一变化即列为「修改」并标明变化字段。textSnapshot 变化意味着高亮下方的正文被改了（agent 改文件的典型场景）,单独用一个「文字已变」徽标呈现。
  • GitHistoryViewer 免费获益：两个页面共用 GitPdfCompare,历史提交间的标注 diff 同时生效。
  • 顺带修债：GitPdfCompare 补上 onward:pdf:trace 中继;清掉死 i18n 键 viewerMissing。

4.2 三态变更模型（借鉴 PSPDFKit Instant JSON）

diffAnnotationSets(original: Record[], modified: Record[]) → {
  added:   Record[]              // id 只在 modified 侧
  removed: Record[]              // id 只在 original 侧
  changed: { before, after, changedFields[] }[]   // id 两侧都有且字段有差
}
// 排序:按 page,再按 createdAt;损坏输入(同侧重复 id)取后者并计数上报 trace

4.3 决策点与权衡

呈现方式优点缺点
推荐差异列表侧栏 + 点击跳转 + 窗格内对变更标注加强调框一眼看全所有变化;跳转直达;窗格内强调让视觉定位闭环三块都要做,工作量最大（约多 1 个组件 + viewer 一条消息）
备选仅差异列表 + 跳转工作量小一档;信息完整跳过去之后哪个是变更的标注要靠肉眼找
备选仅窗格内标记最轻没有汇总视图,多页文档要翻着找,体验差

5. 需求 3 方案：外部变更自动刷新

5.1 现状 vs 提议架构

FileWatchManager 二进制模式不读 UTF-8;指纹 = size+mtime,哈希确认
→
suppressNext 修复压制窗口同样约束 rename→重建路径
→
project:file-changed二进制变更不携带内容
→
ProjectEditor:PDF 通过 isBinary 门脏/净分流
→
onward:pdf:reloadDocument带 ?v=mtime cache-buster
→
viewer 原地重载快照页码/缩放/滚动 → getDocument → 恢复;失败静默延后重试
  • iframe 不重挂载——viewer 在内部换文档（LaTeX Workshop 模式）,调色板、标签、i18n、面板状态全部天然保留;只有文档本身换新。
  • 视图状态恢复复用现成机制:per-file 位置记忆已经有 getCurrentState / restoreState,重载路径直接用,页码超界钳制。
  • 部分写入防护:getDocument 失败（写了一半的文件）→ 保留旧文档 + 静默重试一次（1s 后）→ 仍失败则维持旧文档并打 trace（SumatraPDF 模式,不弹错误框）。
  • 打开时也去陈旧化:buildPdfViewerUrl 补 v=mtimeMs 参数（EPUB 已有 ?mtime= 先例）,关掉「重新打开还是旧内容」这一半问题。
  • 标注保存同步修正缺陷 1:保存前若检测到磁盘指纹与加载时不一致,先走冲突策略（§ 5.2）,不再无条件用内存旧字节覆盖。

5.2 冲突策略：本地有未保存标注 + 文件被外部修改（需拍板）

我们的标注模型是id 键控的记录集,保存 = 基底字节 + 记录集 → 重写文件。这给了我们比 Skim（直接丢标注）好得多的选项:

策略行为优点风险
推荐A. 自动变基合并以外部新字节为新基底,重载文档;把本地未保存的标注记录重放上去;同一 id 两侧都改 → 本地（用户）胜,并打 trace + 轻提示agent 工作流零打断;两侧修改都不丢;符合「标注=记录集」的本质（Zotero/PSPDFKit 同思路）外部改动若大幅重排了正文,重放的高亮坐标可能落在旧位置（与所有阅读器同级的固有风险）;合并逻辑需要完整单测
B. VS Code 式拦截保持本地状态,暂停自动保存,顶部横幅:「文件已被外部修改」→ [重载(丢弃我的)] / [保留我的并覆盖]绝不静默动用户数据,语义最保守agent 频繁改文件时横幅反复打断;用户二选一必丢一侧
C. 重载并丢弃本地Skim 模式:外部优先,本地未保存标注丢弃实现最简单用户刚写的笔记说没就没,不可接受,仅列出供完整性
注:「净状态」（无未保存标注）下的外部变更三个方案行为一致——直接自动重载并恢复视图,这半边你已在需求里定了,不需要再选。冲突窗口本身很窄（自动保存静默窗口 800ms 内）,但 agent 高频写文件的场景会周期性踩到,必须有明确定义。

5.3 关键参数

参数建议值依据
写入稳定确认（去抖）沿用现有 400ms 去抖 + rename 重建 500ms（合计外部变更后约 0.9s 触发重载）介于 LaTeX Workshop 250ms 与 Okular 750ms 之间,无需新旋钮
重载失败重试1 次,间隔 1s,再失败静默维持旧文档SumatraPDF 静默延后模式
大文件（>20MB）哈希确认跳过,仅 size+mtime 判变与既有大文件阈值一致,避免每次事件全量哈希
端到端刷新预算（autotest 门槛）见 § 8 问题 4延迟预算是产品决定,按仓库规则向你确认
