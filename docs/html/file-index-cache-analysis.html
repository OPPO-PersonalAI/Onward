文件索引缓存方案分析

针对 Cmd+P 快速搜索背后的文件索引缓存，做一次自下而上的实现梳理、风险定位与心理模型对照。 本文只做分析与方案陈列，不包含任何已落地的策略改动——按项目规则，缓存策略必须先经您确认再动代码。

0. 结论摘要

一句话结论

索引本身没有任何忽略规则，把 node_modules、.git 整个吞了进去； 而负责过滤噪音的忽略列表只装在「监听」这一侧，没装在「构建」这一侧。 结果是：Cmd+P 实际在一个 93% 是依赖包与版本库内部文件 的清单里做模糊匹配， 并且每保存一次文件，这份清单就被整份丢弃、下次搜索时重新走一遍全盘。

1. 当前架构长什么样

1.1 两份互不相通的缓存

「文件索引」这个东西在代码里存在两份，分别活在两个进程里，各自有各自的失效策略，而且两套策略并不一致。 先把它们摆清楚：

缓存 A · 渲染进程

src/components/ProjectEditor/GlobalSearch/fileIndexCache.ts

  • 按项目根路径分条目，上限 MAX_ENTRIES = 8，按最近使用淘汰
  • 支持精细的增量修补：addFile / removeFile / renameFile / applyFsEvent
  • 有订阅者通知机制、构建令牌（buildToken）防竞态
  • 有 getCacheStats() 供自动化测试观测 totalBuilds

写得相当讲究：并发构建去重、令牌校验、监听器隔离异常都考虑到了。

缓存 B · 主进程 Worker 线程

electron/main/project-fs-worker-entry.ts

  • 就一行：const fileIndexCache = new Map<string, string[]>()
  • 没有上限，没有淘汰
  • 只有两种状态变化：整份写入、整份删除
  • 没有增量修补，没有观测接口

粗放到只有「有」和「没有」两态。

1.2 谁真正决定了搜索结果

关键问题：您按下 Cmd+P，看到的那 50 条结果，是从哪份缓存来的？答案是缓存 B：

Cmd+P 的实际数据通路
按下 Cmd+PProjectEditor.tsx:9730 → handleOpenSearch:5811 → IPCsearchFilenames(root, '', 50) → Worker 缓存 B命中则返回，未命中则全盘遍历
缓存 A 全程没有参与结果计算——它只在 worker 完全不可用时作为兜底路径被 buildFuzzyResults 用到。

再看文件变化时两份缓存各自发生了什么。下面这张图是本次分析的核心， R2 和 R3 两个风险都能从图里直接读出来：

保存一个已存在的文件（比如 Cmd+S 保存 src/foo.ts）时发生了什么
@parcel/watcher发出 update 事件 → parcelEventActionupdate → classify → stat 判定为 filewatch-manager.ts:280 → pendingAdded.add(rel)无条件加入
└→ 渲染进程收到{ added: ['src/foo.ts'] } → 缓存 A：applyFsEventfileSet 已有 → 不变（正确）
└→ 缓存 B：invalidateFileIndex因为 added.length > 0 → 整份删除 → 下次 Cmd+P重新遍历 38,068 个文件
判断条件用的是事件数组的长度，而不是「集合是否真的变了」。缓存 A 明明算出了「没变」， 但这个结论没有回传，缓存 B 照样被清空。
代码注释与实际行为背离

project-tree-watch-classify.ts 的注释明确写道： 「'update' is treated like 'create' on purpose: it is idempotent for the filename index (re-adding a known file is a no-op)」。 这个推理对缓存 A 完全成立。但作者没有考虑到上一层的 fileIndexCacheBootstrap.ts:50 会基于原始数组长度去清空缓存 B—— 「幂等」的设计意图在跨进程边界上被抵消了。这类缺陷单看任何一个文件都发现不了， 必须把三个文件连起来读才会显形。

3. 风险点逐条拆解

R1 索引构建没有忽略规则，与监听侧完全不对称 高

忽略列表 project-tree-watch-ignore.ts 定义得很完整—— .git/、node_modules/、.cache/、.next/、 .turbo/、.parcel-cache/、.DS_Store。 但它只被监听器引用。构建索引的 project-fs-worker-entry.ts 里， 「ignore」「node_modules」这些词一次都没出现过。

于是形成一个自相矛盾的局面：往 node_modules 里写文件不会进索引（监听拦住了）， 但只要索引重建一次，整个 node_modules 又会被完整收录回来。 索引的内容因此取决于「上次重建之后有没有发生过重建」这种偶然因素，不稳定。

证据：electron/main/project-fs-worker-entry.ts:77-99（buildFileIndex 无过滤） vs electron/main/project-tree-watch-ignore.ts:19-33（忽略列表仅供监听用）

R2 保存一个已存在的文件，也会作废整份索引 高

失效判断写在 fileIndexCacheBootstrap.ts:50： 

applyFsEvent(event.cwd, { added, removed })
if (added.length > 0 || removed.length > 0) {
  void api.invalidateFileIndex?.(event.cwd)   // ← 只看数组长度
}

判断依据是「事件里带了几个路径」，不是「文件集合是否真的变了」。 而保存一个已有文件会产生一条 update 事件、被归类成 added—— 于是每次 Cmd+S 都会清空缓存 B，下一次 Cmd+P 付出一次约 300 ms 的全盘遍历。

讽刺的是 applyFsEvent 内部已经算出了 changed 这个布尔值， 只是没有返回给调用方。修复所需的信息本来就在手边。

证据链：project-tree-watch-classify.ts:25（update → classify）→ project-tree-watch-manager.ts:280（file → pendingAdded.add，无条件）→ fileIndexCacheBootstrap.ts:50（按长度判定）→ project-fs-worker-entry.ts:163（整份 delete）→ :130（下次搜索重新 buildFileIndex）

R3 渲染进程那套增量补丁，对搜索结果没有影响 中

缓存 A 实现了 addFile / removeFile / renameFile / applyFsEvent 四个精细的增量入口，还带前缀级联删除、令牌防竞态。 这部分代码质量很高，也有专门的单元测试和 FIC 自动化测试在盯着。

问题是搜索结果不经过它——Cmd+P 直接走 IPC 问缓存 B。 所以缓存 A 再准，用户也感知不到；缓存 B 再糙，用户全都要承受。 目前缓存 A 的增量能力实际只服务于「索引状态展示」和「worker 不可用时的兜底」这两个次要用途。

这不是「坏」，是投入放错了地方：花在缓存 A 上的精细度，本该花在缓存 B 上。

证据：ProjectEditor.tsx:6618 与 :5820 都直接调用 window.electronAPI.project.searchFilenames

R4 worker 侧缓存没有条目上限，也没有淘汰 中

缓存 A 有 MAX_ENTRIES = 8 和按最近使用淘汰。缓存 B 是一个裸 Map， 只在收到 invalidateFileIndex 时删除对应条目，没有任何容量约束。

在多标签页、频繁 cd 切换项目的使用方式下（这正是本产品的典型场景）， 每访问过一个项目就留下一份完整路径清单。按本仓库的规模，一个项目就是 38,068 个字符串， 粗估 3–5 MB。访问过 20 个项目就是几十兆，而且永远不释放。

证据：electron/main/project-fs-worker-entry.ts:32，全文件仅 set / get / delete 三处操作，无淘汰逻辑

R5 结果被截断，界面上没有任何提示 中

文件名搜索硬性只返回前 N 条（scored.slice(0, limit)）。界面上既不显示 「共匹配 M 条，当前显示 N 条」，也没有「结果已截断」的提示。

对比之下，内容搜索（Cmd+Shift+F）是有 limitReached 提示的。 两个入口在这件事上的诚实程度不一致。

这一条与您提的第 2 点（翻页）是同一个问题的两面：要能翻页，前提是先知道「还有下一页」。 当前连总数都没有从 worker 返回，翻页无从谈起。

证据：project-fs-worker-entry.ts:150 只返回数组，不返回总数；ProjectEditor.tsx:11661 只有空态提示

R6 两个入口的结果上限不一致 低

同一个文件名搜索能力，三处调用给了三个不同的上限：

调用方位置上限
Cmd+P 弹窗ProjectEditor.tsx:5820 / 661850
侧边栏文件名标签SearchPanel.tsx:124 / 14680
IPC 默认值ipc-handlers.ts:271480

同一个关键词，在弹窗里搜和在侧边栏里搜，条数不同。这正好也是您第 1 点要解决的那类不一致。

4. 与用户心理模型的落差

「符不符合用户预期」这件事，可以逐条对照「用户以为的」和「实际发生的」：

用户心里默认的规则实际行为落差的后果
Cmd+P 搜的是我的项目文件 搜的是整个目录树，含 node_modules、.git 内部对象 搜 index 会被上百个依赖包的 index.js 淹没，自己的文件排不进前 50 条
搜索是即时的，不该有等待 刚保存过文件的话，要先跑 ~300 ms 全盘遍历 「写两行、搜一下」的高频节奏里，每次都卡顿，而且卡得没有规律可循
搜不到就是没有这个文件 可能只是被截断在第 50 条之外 用户会去别处找、或以为文件被删了，产生错误判断
同一个功能在哪里用都一样 弹窗 50 条、侧边栏 80 条；弹窗无过滤器、侧边栏有 用户学会一套用法后换个入口失效，形成「这个功能不太可靠」的印象
忽略规则一处生效、处处生效 只在监听生效，重建时又全部收录回来 行为随「最近有没有重建过」漂移，用户无法建立稳定预期
最伤的一条

第一条。用户对 Cmd+P 的心理模型来自 VS Code / JetBrains——「它搜的是我的工程」。 把依赖包混进来，不是「多给了一些结果」，而是把用户真正要的结果挤出了可见范围。 结果条数越少（现在是 50），挤压效应越严重。这也是为什么单纯加翻页解决不了问题： 翻的仍然是噪音。

5. 同类产品怎么做

按项目要求，在提设计之前先看最接近的成熟产品——VS Code 的 Quick Open 是这个功能的事实标准：

维度VS Code 的做法本项目现状
索引范围 由 files.exclude 决定，默认排除常见噪音目录；还可通过 search.useIgnoreFiles 直接读取 .gitignore 无 构建侧零过滤
规则可配置 用户级 + 工作区级两层，用户可自行增删 无 忽略列表硬编码在源码里，用户改不了
多种搜索共用一个框 同一个 quick-pick 组件，用前缀切换模式：无前缀=文件名、>=命令、@=符号、:=行号 部分 侧边栏是标签页切换，弹窗只有文件名一种
结果超量 设上限（search.maxResults，默认 20,000）+ 明确的截断提示，引导用户细化查询而非翻页；列表本身是虚拟滚动 无 静默截断在 50/80 条

值得注意的是：VS Code 没有做「下一页」按钮。它的判断是——文件名搜索里， 用户要的那个文件如果没排进前几十条，多半是查询词不够准，让他多打两个字符比让他翻页更快。 这个取舍值得参考，但不是必须遵循；本文第 6 节把两种做法都列为可选项，由您定。

资料来源： VS Code Tips and Tricks、 vscode#16226（Quick Open 排除文件）、 vscode#126762（search.maxResults）、 VS Code v1.58 更新说明

6. 可选方案与权衡

把上面六个风险映射成三档改动幅度。这三档需要您选择，我不会擅自决定。

现状策略

构建：全盘遍历，无过滤 · 失效：任意事件即整份清空 · 淘汰：无 · 两份缓存策略不一致 · 上限：50 / 80 静默截断

方案 A — 最小修复（只堵漏，不改架构）

覆盖改动代价
R1在 buildFileIndex 的遍历里引用已有的 getIgnoredRelReason，让构建与监听共用同一份规则约 10 行；忽略列表已存在且已被单测覆盖
R2让 applyFsEvent 返回它内部已经算好的 changed，bootstrap 改成按 changed 决定是否清空缓存 B约 6 行；纯逻辑，易单测
R4给 worker 的 Map 加与缓存 A 一致的 MAX_ENTRIES + 最近使用淘汰约 25 行
R6把 50 / 80 收敛成一个共享常量约 3 行

收益 索引从 38,068 降到 2,688；重建从 ~300 ms 降到 ~22 ms；保存文件不再触发重建。 不覆盖 R3（架构冗余）、R5（截断提示）。

方案 B — 方案 A ＋ 让截断变得诚实（支撑「翻页」的前提）

覆盖改动代价
方案 A 全部见上
R5searchFilenames 的返回值从 string[] 改成 { items, total, offset }，并支持 offset 参数约 40 行，跨 worker / IPC / preload / 两个界面共 6 个文件；是接口变更

收益 界面能显示「第 1–50 条，共 312 条」，翻页/加载更多才具备数据基础。 代价 改动跨进程边界，需要同步改自动化测试断言。

方案 C — 方案 B ＋ 消除双缓存冗余（架构级）

在 B 的基础上，明确「缓存 B 是唯一权威，缓存 A 降级为纯展示态镜像」， 或者反过来「把增量能力下沉到 worker，缓存 A 只保留订阅通知」。 这一步能消掉 R3，但会动到已被 FIC-01..32 与多个单测锁定的行为， 属于架构决策，建议单独立项、单独评审，不建议和本轮的界面改动混在一起做。

我的建议

先做方案 B。理由：A 的四条都是低风险、高收益的纯堵漏，其中 R1 和 R2 直接决定用户 「Cmd+P 到底快不快、准不准」；而 B 多出的那一条（返回总数）是您提的「翻页」功能的硬前提—— 不先拿到总数，翻页做不出来。C 留到以后单独处理。

7. 与「统一搜索框」「翻页」的依赖关系

您提的三点不是并列的，它们之间有明确的先后依赖：

建议的实施顺序
① 缓存修复方案 A：R1 + R2 + R4 + R6 → ② 返回总数方案 B：R5 → ③ 翻页 / 加载更多您的第 2 点
① 缓存修复 → ④ 弹窗与侧边栏功能对齐您的第 1 点
④ 与 ②③ 相互独立，可以并行推进；但两条线都必须在 ① 之后， 否则做出来的是「在 93% 噪音之上的过滤器」和「翻遍噪音的翻页器」。
您的诉求为什么必须先修缓存否则会怎样
第 1 点
弹窗与侧边栏功能一致		 侧边栏的 include/exclude 过滤器只作用于内容搜索；文件名搜索这一侧根本没有过滤能力可对齐 把过滤器搬进弹窗，用户会发现它对文件名模式无效——功能「看起来有、实际没用」，比没有更糟
第 2 点
超出一页可翻页		 worker 当前只返回数组、不返回总数，界面无从判断有没有下一页 做不出来；强行按「返回满 N 条就假设还有下一页」实现，会在正好 N 条时显示一个空的下一页
下一步需要您拍板的三件事

1）缓存修复走 A / B / C 哪一档；
2）弹窗与侧边栏的对齐方式——共用同一个组件（改动大、彻底消除漂移）还是弹窗内单独实现一套相同的界面（改动小、但两套代码会再次漂移）；模式切换用标签页（同侧边栏现状）还是 VS Code 式前缀（> / #）；
3）超量结果用「下一页」按钮、「加载更多」滚动追加，还是 VS Code 式的「提高上限 + 截断提示 + 引导细化查询」。
