1. 结论（TL;DR）1. Verdict (TL;DR)

直接原因：用户 12:46:42（本地）点击 Git Diff，renderer 的 git:get-diff IPC 往返耗时 15,967 ms——这就是转圈的全部时长。期间 git-ipc-worker 对 E:\RTOS-stablity\winWatchRTOS-Build 近似串行地跑了 4 个 git 子进程：rev-parse 4.9s → ls-files 5.1s → status 4.1s → diff --numstat 5.9s（合计 20.1s，部分重叠后墙钟 16s）。这台公司 EDR 管控机上每一次 git.exe 进程创建本身就要 3~6 秒（全会话 4,777 次后台 status 重算的 p50 = 3.0s 证实这是常态）。 Immediate cause: the user clicked Git Diff at 12:46:42 local; the renderer's git:get-diff IPC round-trip took 15,967 ms — that IS the spinner. 是不是已知问题？——是已知问题类，但根因这次才定位完整。「打开慢」正是 2026-07-03 报告（git-diff-stale-cache-analysis.html）里被立案为后续跟进的症状 B；更早，2026-06-02 的 lessons 明确把「冷开（刚被失效）要现场重算」接受为例外。本次 trace 证明：在「agent 持续写文件」的工作流下，这个例外成了必然路径——预热去重的寿命是「整个会话（4.2 天）」，而缓存的寿命是「到下一次 mirror 失效（几分钟）」。列表缓存 4.5 小时只命中 3 次。 Known issue? — Known class, but the root cause is only now fully localized. 5. 五个代码级缺口5. The Five Code-Level Gaps

G1预热去重寿命错配：去重活一个会话，缓存活几分钟Prewarm-dedup lifetime mismatch: dedup lives a session, the cache lives minutes

RepoPrewarmCoordinator.prewarm（git-repo-prewarm.ts:150-166）以 diffPrewarmedCwds 做「每 cwd 每会话一次」去重，且是乐观置位（先 add 再执行，warm 失败也不回滚）；只有「终端离开该 cwd 超过宽限期」才清除（:226-233）。用户的终端在同一仓库停了 4.2 天 → 预热恰好只跑过一次。而 mirror 失效每隔几分钟就把它填的缓存全部清掉（git-utils.ts:487-507），失效路径不触发任何列表再预热——内容侧仅当「已缓存条目被驱逐 >0」才间接触发 burst（git-diff-content-cache-wiring.ts:396-402），空桶不会再暖。trace 铁证：事发仓库两次 repo-skipped-dedup（04:33/04:43），同期 32 次失效。 RepoPrewarmCoordinator.prewarm dedups once per cwd per session via diffPrewarmedCwds, set optimistically (added before the warm runs; not rolled back on failure); it is only cleared when the terminal leaves the cwd past a grace window. The user's terminal sat in one repo for 4.2 days → exactly one warm ever ran. Mirror invalidations wipe everything it filled every few minutes, and the invalidation path never re-warms the list — the content side only indirectly triggers a burst when evicted>0; an empty bucket never re-warms. Trace proof: two repo-skipped-dedup events for the victim repo vs 32 invalidations.

G2冷路径 = 4 个 await 串行 spawn；mirror 的新鲜 status 被无视Cold path = 4 await-serialized spawns; the mirror's fresh status is ignored
getGitDiff(cwd)                          // git-utils.ts:2026

三点关键：(a) 串行来自 await 结构本身，4 次 EDR 税无法摊薄；(b) status/numstat 在 worker 里只有 normal 优先级（:1941），并不因用户在等而提升；(c) mirror worker 12 秒前刚为同一仓库算完 porcelain status（53 个文件），getDiff 完全不复用，自己再跑一遍 spawn①③。另注：spawn① 理论上应命中「永久 meta 缓存」，实际却发生了——见 §8 疑点 Q1。 Three key points: (a) the serialization is the await structure itself — four EDR taxes that cannot amortize; (b) status/numstat run at normal priority in the worker, never boosted although a user is waiting; (c) the mirror worker computed the same repo's porcelain status 12 s earlier (53 files) and getDiff never reuses it, re-spawning ① and ③. Also: spawn ① should have hit the permanent meta cache but didn't — open question Q1 in §8.

G3三个互不知晓的 spawn 域；mirror worker 无池化、watcher 路径无节流Three mutually-blind spawn domains; mirror worker unpooled, watcher path unthrottled

gitRuntimeManager 是模块级单例，但 worker 线程各自加载模块图 → 主进程、git-ipc-worker（maxInflight=6）、git-state-mirror worker 各有一套互不知晓的调度；且 mirror worker 根本不用调度器，直接 execFile（git-state-mirror-worker-entry.ts:79,309-332），无并发上限、无优先级。峰值：6（ipc-worker）+ ~5（mirror 5 仓库并行）≈ 11 个 git.exe 同时挤 EDR minifilter。前台高优 getDiff 无法抢占或让后台让路。另外 watcher 触发路径只有 80ms debounce，自适应 backoff 只管 heartbeat 不管 watcher（git-reconcile-scheduler.ts:84-93 vs worker-entry.ts:670-678）→ agent 持续写 = 事发仓库背靠背重算。没有任何「这台机器 git 很慢」的全局降载机制（延迟指标只记录不反馈）。 gitRuntimeManager is a module-level singleton, but each worker thread loads its own module graph → main, git-ipc-worker (maxInflight=6) and the git-state-mirror worker have mutually-blind schedulers — and the mirror worker uses none at all, calling execFile raw with no cap or priority. Peak: 6 + ~5 ≈ 11 concurrent git.exe against the EDR minifilter; a high-priority foreground getDiff cannot preempt or pause the background. The watcher path has only an 80 ms debounce — adaptive backoff governs the heartbeat only → back-to-back recomputes while the agent writes. No global "git is slow here" load-shedding exists (latency metrics are recorded, never fed back).

G4全有全无的转圈：现成的 mirror 文件列表没有被用来先画骨架All-or-nothing spinner: the ready-made mirror file list never paints a skeleton

GitDiffViewer.renderContent() 在 !diffResult 时整页转圈（GitDiffViewer.tsx:6731）；已有的渐进机制只覆盖「子模块合并」与「文件正文懒加载」，对无子模块仓库的首屏毫无帮助。而 mirror 快照里此刻就躺着 53 个文件的路径 + 状态分类（renderer 侧 useGitStateMirror 已经订阅，GitDiffViewer.tsx:1444）——足够立即画出文件列表骨架（缺的只是 +/- 行数）。30 秒看门狗只防「彻底卡死」，对 16 秒的「慢但活着」不提供任何降级 UI 或进度提示。 GitDiffViewer.renderContent() shows a full-page spinner whenever !diffResult; the existing progressive paths (submodule merge, lazy file bodies) don't help the first paint of a submodule-free repo. Yet the mirror snapshot already holds all 53 file paths + status classes (the renderer subscribes via useGitStateMirror) — enough to paint a skeleton list instantly (only the +/- counts are missing). The 30 s watchdog covers "wedged", offering nothing for 16 s of "slow but alive".

G5死仓库陪跑 + 三处打点基建缺口Dead-repo churn + three instrumentation gaps

(a) 全天 1 tab / 2 终端，但 5 个仓库被 mirror 重算——3 个无终端仓库合计约 2,850 次重算 ≈ 5,700 次无效 spawn，在 spawn 即税的机器上是纯浪费（订阅来源待查，见 §8 Q2）。(b) 打点缺口：main:git.diff.precompute.schedule 在注册表存在但代码中从未发射（本次「0 次」是假信号）；Git Diff 页面打开路径没有分相打点（click-phase 系列只测文件点击）；worker 侧 git.runtime.task 的时间戳与主进程漂移 5~21 秒（5 天 uptime 的 performance-origin 漂移），影响 Perfetto 对齐。 (a) 1 tab / 2 terminals all day, yet 5 repos mirrored — the 3 terminal-less repos burned ~2,850 recomputes ≈ 5,700 wasted spawns (subscription origin TBD, §8 Q2). (b) Instrumentation: main:git.diff.precompute.schedule is registered but never emitted anywhere (this session's "0" is a false signal); the page-open path has no phase breakdown (click-phase events only cover file clicks); worker-side git.runtime.task timestamps drift 5–21 s from main (performance-origin drift over 5 days uptime), breaking Perfetto alignment.

按项目规则，缓存策略属于必须先确认再实施的策略级决策。以下选项相互正交、可组合；每项标注预期收益与代价。 Per project rules, cache strategy is a confirm-before-implement decision. The options below are orthogonal and composable; each lists expected gain and cost.

方案 A · 失效后自动再预热（治 G1）Option A · Re-warm after invalidation (fixes G1)

把去重键从「每会话一次」改为「每失效代际一次」：对有活跃订阅者的仓库，mirror 失效后经过一段静默期（如 5–10s 无新失效）在低优先级 lane 自动重跑列表 warm。
收益：点击命中率从「几乎必冷」回到「几乎必暖」，配合既有暖路径实现秒开。代价：agent 持续写 → 每静默窗口约 +2~4 个后台 spawn；须与 G3 的池化配合，避免加剧挤兑。风险：低——机制已存在，只改触发条件。 Change the dedup key from per-session to per-invalidation-generation: for repos with live subscribers, auto re-run the list warm on a low lane after a quiet window (5–10 s with no further invalidation). Gain: click hits go from almost-always-cold to almost-always-warm. Cost: ~2–4 extra background spawns per quiet window under agent churn; must pair with G3 pooling. Risk: low — the machinery exists, only the trigger changes.

方案 B · 列表缓存 serve-stale-then-revalidate（治 G1/G4 的感知延迟）Option B · Serve-stale-then-revalidate for the list cache (fixes perceived latency of G1/G4)

失效改为「标记 stale」而非删除；打开时立即返回 stale 列表（UI 明示「正在刷新」），后台重算完成后原位更新。与 7-03 的新鲜度权威设计一致：症状 A 的问题是「陈旧而不自知」，此方案是「陈旧但明示 + 主动刷新」。
收益：打开感知 <1s（显示几分钟前的列表）。代价：短暂展示旧数据；需要 UI 状态与既有失效通知联动。风险：中——须严防 lessons §4 的「强刷自毁预热」回归。 Invalidation marks entries stale instead of deleting; open serves the stale list immediately (UI shows "refreshing"), then patches in place when the recompute lands. Consistent with the 7-03 freshness-authority design: Symptom A was "stale unknowingly"; this is "stale, declared, and self-refreshing". Gain: perceived open <1 s. Cost: briefly shows old data; UI wiring. Risk: medium — must not regress lesson §4 (force-refresh wiping prewarm).

方案 C · 冷路径瘦身（治 G2；对所有冷场景生效）Option C · Slim the cold path (fixes G2; helps every cold scenario)

(i) getDiff 复用 mirror 的新鲜 porcelain status（经 main 转发或直接查询 router 快照），省掉 spawn①③；(ii) unstaged/staged numstat 并行（放宽该对的 repoConcurrencyLimit:1）或合并为一次 spawn；(iii) 结构快照的 gitlink 结论按 refsDigest 缓存，不随每次 mirror 失效重跑 ls-files。
收益:4 spawn → 1~2 spawn，冷开 16s → 约 5~8s;暖路径不受影响。代价：需要为「mirror status → getDiff 输入」定义新鲜度契约（防倒退回症状 A）。风险：中——动的是数据通路，须有严格的等价性测试。 (i) getDiff reuses the mirror's fresh porcelain status (forwarded via main or read from the router snapshot), removing spawns ① and ③; (ii) run unstaged/staged numstat in parallel or merge into one spawn; (iii) cache the snapshot's gitlink conclusion keyed by refsDigest so ls-files doesn't rerun per invalidation. Gain: 4 → 1–2 spawns; cold open 16 s → ~5–8 s. Cost: needs a freshness contract for "mirror status as getDiff input" (must not regress Symptom A). Risk: medium — data-path change, needs strict equivalence tests.

方案 D · 渐进 UI：mirror 骨架列表 + 阶段进度（治 G4）Option D · Progressive UI: mirror skeleton list + stage progress (fixes G4)

列表未返回时，先用 renderer 已订阅的 mirror 快照（53 个路径 + 状态分类）画出可点击的文件列表骨架（+/- 行数占位 shimmer），numstat 到达后原位补全；转圈替换为阶段文案。纯 renderer 层改动,不碰缓存策略。
收益：感知延迟 16s → <1s。代价：骨架期功能受限（无行数、正文按需仍慢）。风险：低。 Before the list returns, paint a clickable skeleton from the already-subscribed mirror snapshot (53 paths + status classes, shimmer for +/- counts), fill in when numstat lands; replace the spinner with stage text. Renderer-only, no cache-strategy change. Gain: perceived 16 s → <1 s. Cost: limited function during skeleton. Risk: low.

方案 E · spawn 全局治理（治 G3/G5）Option E · Global spawn governance (fixes G3/G5)

(i) mirror worker 纳入并发预算（跨线程 semaphore 或经 main 令牌），前台 getDiff 在飞时暂停/降速该仓库的后台重算；(ii) 排查并修复 3 个无终端仓库的订阅来源；(iii) 建立机器级「git 慢」信号（如滚动 p50 > 1s 时收紧后台并发与 heartbeat）。
收益：减少挤兑让每个 spawn 更快，全局背景负载 -50% 以上。代价：跨线程协调复杂度。风险：中。 (i) Bring the mirror worker under a shared spawn budget (cross-thread semaphore or main-issued tokens), pausing/slowing that repo's background recomputes while a foreground getDiff is in flight; (ii) find and fix the dead-repo subscriptions; (iii) add a machine-level "git is slow" signal (e.g. rolling p50 > 1 s tightens background concurrency and heartbeat). Gain: less contention → every spawn faster; >50% background load cut. Cost: cross-thread coordination. Risk: medium.

建议的组合与顺序（供决策参考）：第一阶段 D + A（感知秒开 + 命中率回升，风险最低、见效最快）；第二阶段 C(i)(ii)（冷路径本质提速，惠及首次打开/重启后等 A 覆盖不到的场景）；第三阶段 E（结构性治理）。B 与 A 二选一即可（同为「点击即有列表」，A 走预热、B 走 stale 兜托；A 更简单、B 更彻底）。G5 的打点缺口（precompute.schedule 接线、页面打开分相、worker 时钟）建议随第一阶段一并补上——本次分析被这三个缺口拖慢了不少。 Suggested combo & order: Phase 1 D + A (perceived instant open + hit-rate recovery; lowest risk, fastest payoff); Phase 2 C(i)(ii) (true cold-path speedup, covering first-open/post-restart cases A can't); Phase 3 E (structural governance). Choose A or B, not both (A via prewarm, B via stale-serve; A simpler, B more thorough). Fix the G5 instrumentation gaps alongside Phase 1 — they measurably slowed this very investigation.
