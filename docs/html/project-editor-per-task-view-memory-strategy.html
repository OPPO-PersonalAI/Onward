Project Editor 多 Task 视图记忆：现状 vs 新策略

缓存策略变更文档（按 CLAUDE.md 缓存策略硬性规则生成）· 用户已于 2026-07-10 通过 AskUserQuestion 逐项确认策略选项

1. 问题与结论

设计意图：每个终端 Task 用编辑器打开文件、离开后再进入，应当立刻回到上次的文件与位置（Markdown 滚动、PDF 页码、HTML 滚动、代码光标）。每个 Task 独立记忆，互不影响（用户确认的语义）。

现状：单实例编辑器 + 多个跨 Task 共享的单例状态槽，导致多 Task 交替使用时记忆偶发丢失。

结论：持久化 key 归一到仓库根（D1）、快照槽位按 scope 分槽（D2）、渲染缓存提额加保护集（D3）、HTML 位置补持久化（D4），再加三处纯正确性修复（D5、D6）。

用户看到的症状根因

2. 现状架构

全窗口只有一个 <ProjectEditor> 实例（TerminalGrid.tsx:3102，无 per-terminal key），由 props 重参数化。持久化层按 [terminalId, normalizeProjectCwd(cwd)] 分 key（AppStateContext.tsx:154-159）——这一层的分 key 是对的；丢失全部发生在内存层与恢复时序上。

ESC 关闭
flush 持久化 + 软关闭快照（单槽）
→
其他 Task 打开编辑器
快照与自己 scope 不符 → 置空（5751-5752）
→
原 Task 重入
快照没了 → 走慢速恢复；若 cwd 还漂了 → 连持久化都查不到

3. 六个缺陷（全部已在代码层面验证）

D1 — scope key 随终端 cwd 漂移 最严重

打开编辑器时 cwd 是当时实时解析的终端 cwd（App.tsx:1464-1473）。两次进入之间终端里 cd 过（agent 干活极常见），第二次的 key 就不同 → 持久化记忆整体查不到。中途 cwd 覆盖还会触发 root-change 全量重置（ProjectEditor.tsx:5524-5532）。

D2 — 软关闭快照单槽位

"零闪烁秒开"依赖 editorSoftCloseSnapshotRef 单例槽位；任何其他 scope 的打开都会把它置空（ProjectEditor.tsx:5751-5752）。A 的秒开能力被 B 的一次打开摧毁。

D3 — Markdown 渲染缓存全局 7 条、不分 Task

markdownSessionCacheStore（module 级 Map，ProjectEditor.tsx:484），key = [rootPath, filePath]，默认上限 7，评分淘汰。多 Task 共享同一预算互相挤占。注意：渲染 HTML 本身与 Task 无关（同文件同内容同 HTML），问题在预算与保护，不在 key。

D4 — HTML 滚动位置从未持久化

FileViewMemory（tab.d.ts:104-126）有 PDF/EPUB 字段但没有 HTML 字段；HTML 滚动只活在会话 ref 里，全靠软关闭快照保命——D2 一发生就必丢。

D5 — 同 root 跨 Task 污染 + 恢复令牌竞态

  • (a) 恢复效应查不到存储状态时直接 return 不清屏（6335-6339）→ 同 root 下 B 直接看到 A 的文件；
  • (b) 关闭持久化读单例 activeFilePathRef（2660,2686）→ 把 A 的文件写进 B 的 key，污染持久化；
  • (c) 恢复令牌被其他 Task 的关闭/换 root 自增（5440-5441），位置应用中途被静默取消（6454-6456）。

D6 — validateFileStates 白名单漂移 跨重启

electron/main/app-state-storage.ts:573-602 的字段白名单缺全部 6 个 PDF/EPUB 字段（pdfPageNumber/pdfScrollTop/pdfScale/epubFontPct/epubLocation/epubScrollTop）——应用重启从磁盘加载时这些位置被静默剥掉。类型定义与校验器漂移的典型 bug。

4. 同类产品对照（调研结论，附来源）

VS Code：视图状态用 EditorMemento 存储，两级 key：resource → editor-group id → state——不同 pane 的状态互不挤占，只会随整个 resource 一起从 LRU 掉出；文本编辑器的 LRU 上限是 100。Markdown 预览走"极小序列化状态（{resource, line}）+ 快速重渲染 + scrollTo"，保 DOM 的 retainContextWhenHidden 被官方标注为高内存开销、万不得已才用。一个只按文件分 key 的 7 条缓存，恰好复现了 VS Code 两级 key 设计要避免的失效模式。

  • vscode editorPane.ts（EditorMemento） · editorWithViewState.ts（limit 100）
  • issue #102485（group id 变化导致状态丢失） · v1.59 sharedViewState
  • Webview API（retainContextWhenHidden 取舍）
  • JetBrains：EditorHistoryManager 持久化 caret+scroll，LRU 上限 = recentFilesLimit+1（默认 50）；Obsidian：per-leaf ephemeral state。

5. 新策略（用户已逐项确认）

缺陷现状新策略（已确认）
D1 key 漂移 key 用打开瞬间的终端 cwd 归一仓库根打开时经 git.resolveRepoRoot（已有 API，非 git 回退原 cwd）；精确 miss 时回退查同 terminal 的旧 key，写入时迁移收编
D2 快照单槽 单例槽位，他人打开即清 按 scope 分槽 LRU Map（cap 4）仿 VS Code 两级 key；其他 scope 打开不再互清；同 scope 重开行为与现状逐位一致
D3 渲染缓存 全局 7 条，无保护 上限 7→12 + 活跃文件保护集key 保持 [root,file] 全局共享（不重复占内存）；每个活跃 scope 的最后文件免淘汰
D4 HTML 位置 仅会话内存 补 htmlScrollX/Y 持久化对齐 PDF/EPUB；捕获走异步 IPC + 2s 后台跟踪兜住硬退出
D5/D6 — 纯正确性修复活跃文件 scope 归属守卫；stored-null 清屏；pending 状态带 scope 标记；非用户取消幂等重跑；白名单补全 8 字段
Task A ESC 关闭
快照 → store.set(scopeKey_A)
→
Task B 打开/关闭
store.get(scopeKey_B)，A 的槽位不动
→
Task A 重入
快照命中 → 秒开；cwd 漂移已被仓库根归一挡掉

6. 权衡清单

决策收益代价 / 风险缓解
D1 归一仓库根同仓库内 cd 不再丢记忆；换项目自然开新会话编辑器树根从"cwd"变为"仓库根"（可见变化，用户已接受）；多一次 IPCresolveRepoRoot 结果永久缓存；requestedRepoRoot 已提供时跳过
D2 快照 Map cap=4各 Task 秒开互不摧毁快照持有渲染 HTML/内容字符串，内存 × 槽数cap=4 + LRU；淘汰有埋点可观测
D3 提额 + 保护集多 Task 不再互相挤掉秒开缓存缓存内存上界 7→12 条；全保护时允许临时超额保护集按 scope LRU cap=4 兜住陈旧性
D4 补 schema 字段HTML 位置跨会话/重启存活持久化 schema 增 2 字段；捕获为异步 IPC 有时窗字段可选、向后兼容；多个捕获点 + 2s 兜底轮询
被否掉的备选（记录以免重提）：D3 的"key 加 terminalId 完全隔离"——同文件双 Task 存两份相同 HTML，内存翻倍，与"渲染结果与 Task 无关"的事实相悖；D2 的"放弃保挂载走纯重渲染"——PDF/HTML 重开体感退化。
