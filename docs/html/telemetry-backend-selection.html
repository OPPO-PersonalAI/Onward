Onward 使用量统计后端选型决策

状态：已定案 — PostHog 云免费层（2026-07-17）类型：策略级决策文档

定案记录：用户选定方案 B（PostHog 云免费层）；日志对接范围 = 后续新事件 + 回填本地 JSONL；装机量级 < 1 千日活，免费额度充裕。接入实现见 electron/main/telemetry/telemetry-service.ts（posthog-node 5.45.2, MIT）与回填脚本 scripts/telemetry-backfill-posthog.mjs。

Azure Application Insights 后端已被微软下线，Onward 的每日使用量汇总无处可发。本文档整理了现状、候选替换方案、同类产品做法与取舍，最终选型由用户决定，未经确认不写任何接入代码。

1. 背景与问题

事件：Onward 之前将匿名使用量统计上报到 Azure Application Insights（eastus-8 端点，连接串硬编码于 electron/main/telemetry/telemetry-constants.ts）。该后台服务被微软单方面下线，上报通道中断。

需要一个替换服务，硬性要求：

  • 免费 —— 托管服务要有真正够用的免费额度，或者是免费的自建开源软件；
  • 能对接已抓取的日志 —— 应用现有的事件格式（JSON）要能直接送进去，本地已积累的日志可以回填导入；
  • 稳定 —— 不能再出现"服务突然消失"这种情况；
  • 对开源软件友好 —— 许可条款与 Apache-2.0 兼容，SDK 不能带 copyleft 传染。

2. 现状架构

代码摸底结论：遥测管线是我们自己的代码，Azure 只是最后一跳的"投递地址"。事件不逐条上传——本地按天聚合，每天只发一条匿名 daily/summary 汇总。

每天上传的 daily/summary 长什么样

由 telemetry-aggregator.ts 的 buildDailySummary() 生成，纯 JSON：

{ date, sessionCount, totalActiveMs,
  sessionDuration: { min / max / avg / p50 / p95 },
  tab/terminal/layout 的 max 与 avg, prompt 使用计数,
  8 个下拉菜单计数, rendererCrashCount }
+ 公共字段: instanceId(随机 UUID), sessionId, appVersion,
  buildChannel, releaseChannel, platform, arch, electronVersion

事件量级极小：每个用户每天约 1 条汇总（外加去重后的 update/error）。任何候选服务的免费额度对这个量级都绰绰有余。

3. 替换面分析

好消息：真正碰 Azure 的代码只有一小段。事件采集、同意管理、按天聚合、本地日志、IPC、设置界面全部与 Azure 无关，可原样保留。
模块是否需要改动说明

4. 候选方案对比

方案免费额度SDK 许可自建选项历史导入稳定性风险
Aptabase（托管） 100 万事件/月，超额暂停 MIT（@aptabase/electron） 有（AGPL 服务端，.NET + Postgres + ClickHouse） 批量 API，每请求 25 条，支持历史时间戳 中 近乎单人维护，托管服务低 bus-factor
PostHog（云） 100 万事件/月（另含错误、feature flag 额度） MIT（posthog-node） 实际已弃：仅 ~10 万/月 hobby 版，官方不推荐生产使用 最强：/batch 无条数上限 + historical_migration 标志 低 风投背书、免费额度历史上未收紧过；但云锁定
Umami（自建） 完全免费（自付服务器） MIT（服务端也是 MIT） 是（单容器 + 仅 Postgres，最轻） 无现成导入器，需自写 ETL 调 /api/send 零跑路风险 但自己运维；产品分析能力偏弱（网页分析形态）
OTel + ClickHouse + Grafana（自建） 完全免费（自付服务器） OTel/ClickHouse 均 Apache-2.0 是（Docker Compose 参考方案成熟） 自定义管线，导入自由 零跑路风险 但工程量最大，形态偏可观测性而非产品分析

4.1 Aptabase — 贴合度最高

专为桌面应用设计MIT Electron SDK小团队风险

  • 唯一一个专为桌面/移动应用统计而生的开源候选，官方有 @aptabase/electron（区分主进程/渲染进程入口）。
  • 托管免费额度 100 万事件/月 —— 我们每用户每天 1 条，够支撑约 3 万日活。
  • 批量接口 POST /api/v0/events 接受 ISO 8601 历史时间戳 → 本地 JSONL 可回填。
  • 限制：自定义属性只支持字符串/数字（我们的 daily/summary 是平铺数字字段，兼容）；仪表盘较简单，无自由 SQL 查询。
  • 主要风险：项目近乎单人维护。托管版若停摆，等于重演 Azure 事件——但它有自建出口（AGPL 服务端），数据主权可收回。

4.2 PostHog — 最稳的云免费额度

公司体量大、免费额度稳定最强历史导入云锁定

  • 免费 100 万事件/月，历史上从未收紧（对比 Mixpanel/TelemetryDeck 都改过价）；MIT 的 posthog-node，官方有 Electron 接入文档。
  • 历史导入是所有候选里最完善的：/batch 端点单请求最大 20MB、无条数上限，且有专门的 historical_migration: true 标志避免触发风控。
  • 产品分析能力最强（漏斗、留存、自由查询）。
  • 主要风险：自建通道实际上已废弃（hobby 版约 10 万事件/月且官方不推荐生产使用），选它基本等于绑定它的云。风投驱动，长期存在免费额度商业化压力。

4.3 完全自建 — 零跑路风险，代价是运维

数据完全归自己需要自己有服务器并长期运维

  • Umami（推荐的轻量自建）：MIT、单容器 + Postgres，服务端 /api/send 可直接收桌面应用事件；代价是仪表盘偏网页分析形态、回填要自写脚本。
  • Aptabase 自建：兼得"桌面应用形态 + 数据主权"，但要运维 .NET + Postgres + ClickHouse 三件套，服务端 AGPL（作为独立服务运行，不传染应用代码，政策上需要知悉）。
  • OTel + ClickHouse + Grafana：许可最干净（全 Apache-2.0/AGPL 仅 Grafana），扩展性最强，但事件模型、看板全要自己搭，工程量最大。

4.4 排除项及理由

服务排除理由
TelemetryDeck2026-07-01 刚把免费额度从 10 万砍到 5 万/月；服务端闭源、无自建出口 —— 在"免费、稳定"两条上都不达标
Mixpanel / Amplitude额度目前慷慨（100 万/200 万每月）但纯商业闭源、无自建出口，结构性跑路风险与 Azure 同类
Countly Lite可用（AGPL 自建），但形态和运维成本相对 Aptabase/Umami 无优势
Plausible / Matomo网页分析形态，自定义事件属性受限（Plausible）或 GPL + PHP 栈过重（Matomo）
Sentry形态是错误监控不是产品分析；云免费额度极小；自建栈极重。可作为崩溃上报的补充，不是本次替换对象

7. 权衡与建议

如果最看重"不再被下线"

选 方案 C 自建。数据和服务都在自己手里，代价是需要一台长期在线的服务器和运维投入。前提：你有可用的服务器资源。

如果最看重"零运维 + 稳定免费"

选 方案 B PostHog 云。公司体量、免费额度稳定史、导入能力都是最好的；接受的代价是绑定它的云（自建出口很弱）。

如果最看重"形态贴合 + 保留退路"

选 方案 A Aptabase 托管，它是唯一专为桌面应用设计的候选，且托管若出问题可迁到自建版（同一套 API）。接受的代价是小团队的存续风险。

组合思路

本地 JSONL + 按天聚合这层无论选谁都保留，它天然就是"服务商中立"的缓冲层——将来再换后端，同样只动发送段。

倾向性意见（仅供参考，决定权在你）：就"免费、稳定、开源友好、能回填"四条硬要求的综合得分，PostHog 云免费层最均衡；若你手上有现成服务器且愿意运维，自建 Umami 是把"稳定"做到极致的做法；Aptabase 形态最贴合但存续风险最高。

8. 待你确认的问题

  1. 选哪个方案？A（Aptabase 托管）/ B（PostHog 云）/ C（自建，需说明用哪套）。
  2. "对接已抓取的日志"的范围？只需新服务接收现有格式的后续事件；还是要把各机器本地已积累的 JSONL 回填导入；Azure 侧的历史数据是否已有导出（若无导出，随服务下线大概率已不可取回）。
  3. 大致装机量/日活量级？用于核对免费额度是否长期够用（当前设计下 100 万事件/月 ≈ 3 万日活）。
  4. 若选自建：是否已有可用服务器（配置、位置）？由谁负责运维？
