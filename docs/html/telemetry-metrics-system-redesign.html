Onward 数据指标体系重构设计

状态：待用户拍板类型：策略级决策文档

现有埋点是一月份按当时的产品形态设计的。半年过去，产品面扩大了数倍而埋点没有跟上。本文档基于两路调研——① Onward 当下完整功能面盘点，② VS Code / JetBrains FUS / Zed / Warp 的遥测分类法与标准产品分析框架（HEART、留存队列、无崩溃率）——设计一套面向"以数据驱动改进产品"的新指标体系，以及配套的分析 Skill。关键取舍列在 § 10，由用户拍板后实施。

1. 现状与问题

核心结论：现有埋点约 15 个信号，其中只有约 11 个进入上传的每日汇总；而今天的产品有 90+ 个用户可触达的交互面。覆盖率不足，且已有数据存在结构性缺陷。
问题细节后果
子页面内部零覆盖Git Diff / Git History / Project Editor 只记"打开"；内部约 45 种交互（暂存/丢弃、hunk 操作、大纲跳转、全局搜索、阅读模式、图片/PDF/EPUB 对比、SQLite 查看器）全部无埋点无法回答"用户打开 Diff 之后做了什么、哪些功能白做了"

2. 设计原则

① 混合制而非全原始

预算 = 1M 事件/月 ÷ 1k 日活 ≈ 33 条/用户/天。高频计数走客户端按日聚合（VS Code / JetBrains 路线），只给低频高信号时刻发离散事件（Zed 的攒批思路）。热路径（每条命令、每次轮询）永不发原始事件。

② 名字 + 属性包，不搞强类型枚举

Zed 从强类型事件枚举迁移到了"事件名 + 属性包"——僵硬分类法跟不上产品演进。我们用中央注册表（类比 perf-trace-names.ts）管名字与属性白名单，事件本体保持灵活。

③ 白名单校验 + 数值取整

学 JetBrains FUS：枚举型属性只允许预定义值，不合法就替换成占位符；聚合数值适当取整，防止极端值去匿名化。绝不采集代码内容、路径、命令行。

④ 匿名事件 + 稳定 distinct_id

全部事件带 $process_person_profile:false（便宜 55-80%，且够算 DAU/留存）。distinct_id = 现有随机 instanceId，同意撤回即换新——隐私姿态不变。

命名约定：沿用现有 <域>/<对象>.<动词> 风格并向后兼容（session/start、prompt/use 不改名）。新事件形如 feature/first-use、error/crash、update/check。PostHog 接受任意字符串，注册表内部一致性优先于照搬 PostHog 官方的空格命名。

3. 事件分类法（三层）

3.1 第一层：每日聚合骨架（daily/summary 扩展）

保留现有骨架与 outbox-ack 上传语义，DailyStats 计数器从 19 个扩到约 55 个，按域分组：

域计数器（新增以 ★ 标注）回答的问题
sessioncount、durations(p50/p95/min/max/avg)、totalActiveMs（现有）用了多久、多频繁
workspacetab/terminal/layout 快照统计（现有）+ ★tabCreated、★tabClosed、★layoutPresetApplied、★customLayoutApplied、★downsizeConfirmed工作台规模与布局习惯

subpage.gitdiff★open、★stageFile、★discardFile、★partialStage、★hunkAction、★modeToggle、★imageDiff、★pdfDiff、★epubDiffDiff 是"看"还是"改"，富媒体对比值不值

白名单纪律：所有计数器是"次数"，不带任何自由文本；shortcutFired 只计总数不记是哪个键；settingChanged 只计次数不记改了什么值。数值在上传前按 JetBrains 惯例做分档取整（如 activeMs 取整到分钟）。

3.2 第二层：离散高信号事件（经 outbox 攒批 + ack 上传）

事件属性（全白名单）用途预估量/用户/天
session/start（公共属性即可）会话计数分母、活跃判定1–5
session/enddurationMs（取整到 10s）、crashFree: bool无崩溃会话率的分子分母1–5
feature/first-usefeature: 约 30 个预定义 ID 之一采用漏斗、time-to-first-use；每功能每安装一生只发一次<1（摊薄后）
error/crashkind: renderer | gpu无崩溃用户率（7/30 天窗口）≈0
error/recoveredkind: unresponsive | webgl-fallback | watcher-degraded（每 kind 每日去重）灰色降级的用户面暴露量≈0
update/check·downloaded·installStart·installComplete·errorphase 相关（现有属性）更新漏斗逐步归因1–3
consent/granted·revoked（无属性）同意率本身也是指标≈0

上传机制直接复用刚建好的 outbox 确认送达语义：离散事件照常写入 JSONL，心跳时与积压一起批量上传，flush ack 后删除。不新增任何传输通道。

3.3 第三层：本地 perf-trace（不变）

逐操作延迟、watcher/GL 恢复细节、IPC 热路径继续只进本地 trace；第一层的 stability 计数是它们在云端的"影子"。用户报 bug 附诊断包时才能看到细节——这条既有边界不动。

4. 派生指标体系（七组）

指标全部由上述事件在查询侧派生（PostHog Insights / 分析 Skill 的 HogQL），客户端不需要为任何指标单独发事件。

#指标组指标与口径数据来源
1规模DAU / WAU / MAU（当日有任意事件的 distinct instanceId）；新增安装（首次出现的 instanceId）；版本/平台/架构分布任意事件 + 公共属性
2粘性 & 留存DAU/MAU、WAU/MAU（开发工具以周节奏为准）；D1/D7/D30 安装队列留存；人均活跃天数第二层 session/start + 第一层日报
3时长 & 强度会话时长 p50/p95（看分布不看均值）；人均日活跃时长；人均日会话数；tab/终端/布局规模分布第一层 session 域
4功能采用（HEART-Adoption）采用率（活跃用户中用过 X 的 %）、广度（人均触达的不同功能数）、深度（采用者的人均次数）、time-to-first-use（安装 → 首用天数）feature/first-use + 第一层功能计数
5激活漏斗（HEART-Task Success）安装 → 首次发送 Prompt → 首次启动 Coding Agent → 首次打开子页面 → D7 回访；各步转化率feature/first-use 序列
6稳定性无崩溃会话率（crashFree 会话 ÷ 总会话）；无崩溃用户率（7/30 天窗口）；按版本对比；灰色降级触达率（recovered 用户 ÷ 活跃）；对标 99.5% 行业基准线session/end + error/*
7更新健康更新漏斗 check→downloaded→installComplete 转化率；错误率；版本收敛速度（新版本 N 日覆盖率）update/* + 公共属性 appVersion

5. 激活漏斗与 North Star

North Star 候选（§10 拍板）

  • 候选 A（推荐）：每周活跃 Agent 用户数——当周至少启动过一次 Coding Agent 的安装数。Onward 的核心价值主张是"agent workbench"，这个动作最贴近交付的价值；同类先例：Snyk "Weekly Fixing Orgs"。
  • 候选 B：周人均 Prompt 执行数——衡量强度而非广度，适合作为二号指标而非 North Star。
  • 候选 C：WAU——最简单，但只测"打开"不测价值，容易虚高。

7. 同意模型选项

选项 1：维持单开关（现状）

同意 = 全部（匿名）遥测；拒绝 = 零上传。实现零成本，心智最简单。缺点：拒绝用量的用户连崩溃信号也不给，稳定性样本变小。

选项 2：VS Code 式分级（off ⊂ 崩溃 ⊂ 全部）

拒绝用量但接受崩溃上报的用户仍贡献稳定性数据。代价：设置 UI、i18n、存储迁移、事件分级路由，约一天的实现量；首启弹窗也要改成三选。

8. 分析 Skill 设计（ow_metrics_report）

方面设计
形态.claude/skills/ow_metrics_report/SKILL.md（正文简体中文）+ scripts/ 下的拉取/分析脚本（Node，跨平台）
参数--pull：用只读 Key 全量抓取 → 存带时间戳快照（已定案）；--range 7d|30d|90d：报告时间窗；缺省不带 --pull 时用最新本地快照离线出报告
Key 管理只读 Personal API Key（Query Read、限定 Onward 项目）存于 ONWARD_POSTHOG_API_KEY 环境变量或 ~/.config/onward/posthog-api-key；首次 --pull 未发现 Key 时给出创建引导；永不进仓库/命令行参数/报告文件
数据布局traces/metrics/snapshots/<UTC 时间戳>.json（HogQL 查询结果集合）+ traces/metrics/reports/<时间戳>.html。traces/ 已 gitignore——使用数据不进开源仓库；报告是自包含 HTML，发给任何人都能直接打开
报告内容§4 七组指标各一节：当前值 + 环比（与上一快照差值 ▲▼）+ 历史趋势表（逐快照一行，纯 HTML/CSS 渲染，暗色 + 左侧 ToC + 无动画跳转，全部遵守仓库 HTML 规范）；结尾自动生成"数据要点"清单（如"功能 X 采用率连续两期下降"）
历史追踪快照序列即历史。报告的趋势表逐期累加（append-only），支持任意两期对比；快照 JSON 保留原始查询结果，口径升级后可以离线重算旧指标
过渡期新旧埋点并存期间，Skill 对旧口径（8 个 dropdown 计数）与新口径分别标注，避免曲线错读

期内容规模
