1 · 摘要 Summary

✅ 已被数据否决的方向Ruled out by data
不是 textarea / React 受控 value / 内容大小本身的问题。把编辑器单独预载到 1.5MB（约 190 万字符 / 18750 行）、甚至叠加 5 终端狂刷 + git 压力，逐键 input→出字延迟始终 ≈10–30ms，完全平坦。若一上来就做「改非受控」，治不了这个问题。 Not the textarea / React controlled value / raw content size. Pre-loading the editor to 1.5MB (~1.9M chars / 18,750 lines), even with 5-terminal flood + git pressure, keeps per-keystroke input→paint at ≈10–30ms, perfectly flat. The obvious "make it uncontrolled" fix would not have helped.
🎯 已确证的根因（v1.3 定稿）Confirmed root cause (v1.3, final)
是 <textarea> 元素本身的原生 IME 组字实现，成本 = O(光标前文本量)——与 React 受控/非受控无关。逐个验证证实：不是拼写检查、不是 CSS containment、不是 React 受控写回（改非受控后 46→47ms 没变）。真正决定成本的是光标位置：浏览器组字时要把光标之前的全部文本重新布局来定位组字/候选词。实测（78KB）：光标在末尾 60ms、在中间 263ms、在开头仅 7ms；英文单次插入是增量更新（~12ms，不随内容变化），所以英文不卡。裸 textarea（零 React）78KB 组字也要 82ms——坐实是原生成本。 It is the native IME composition of the <textarea> element itself: cost = O(text-before-caret) — independent of React controlled/uncontrolled. Ruled out one by one: NOT spellcheck, NOT CSS containment, NOT React's controlled write-back (uncontrolled left it 46→47ms, unchanged). The driver is caret position: the browser re-lays-out all text before the caret to anchor the composition/candidate window. Measured (78KB): caret at end 60ms, middle 263ms, start only 7ms; English is an incremental insert (~12ms, flat with content), so English never lags. A bare textarea (zero React) is also 82ms at 78KB — proving it is native.
✅ 已实现并验证的修复Fix — implemented & validated
把编辑区从 <textarea> 改成 <div contenteditable="plaintext-only">（ChatGPT/Slack/Discord 输入框都用它）。contenteditable 不走 textarea 那条 O(光标前文本量) 的原生路径。实测：78KB 组字 input→出字 p95 从 47–263ms 降到 6ms。用户视角全链路 E2E（真实按键/中文 IME/Enter 换行/纯文本粘贴/保存到列表/右键菜单/双击编辑）8/8 通过，多行/前导空格/中英混合内容往返零损坏。详见 §9。 Editor changed from <textarea> to <div contenteditable="plaintext-only"> (what ChatGPT/Slack/Discord use). contenteditable does not take the textarea's O(text-before-caret) native path. Measured: 78KB IME input→paint p95 dropped from 47–263ms to 6ms. User-perspective E2E (real keys / Chinese IME / Enter newline / plaintext paste / save-to-list / context menu / double-click edit) is 8/8 PASS, with zero corruption on multi-line / leading-whitespace / mixed CJK-ASCII round-trips. See §9.
⚠️ 次要症状（独立、未在此修复）Secondary (separate, not fixed here)
你首份 trace 里的主进程 868ms 卡顿是另一个独立问题（重并发负载下的主进程争用），与本次 IME 修复无关，本地未复现。排查阶段我曾试做 main:gc-pause 观测埋点并用它取了下方浸泡数据；但它属于 868ms 这条独立线、与本次 contenteditable 修复无关，已从本次改动中剥离（保存为单独 patch），待后续专门排查 868ms 时作为独立改动再引入。虚拟光标（Canvas 模式点击行尾外补空格）随本次迁移移除（与用户确认）。 The 868ms main-process stall in your first trace is a separate issue (main-process contention under heavy load), unrelated to this IME fix and not reproduced locally. During investigation I prototyped a main:gc-pause observer and used it for the soak data below; because it belongs to the separate 868ms line, it has been factored OUT of this change (saved as a standalone patch) and will return as its own change when the 868ms stall is pursued. The virtual cursor (Canvas-mode click-past-EOL padding) was removed with this migration (confirmed with the user).

8 · 当前策略 vs 建议策略 Strategy compare

按项目规则，架构敏感改动实现前先可视化对比。以下是围绕「主进程/输入响应」的当前设计与建议方向：Per project rule, visualize before architecturally-sensitive changes. Current vs proposed around main-process / input responsiveness:

🔵 当前策略Current

  • 输入优先：渲染侧 InputPriorityLane（keydown/input/composition 捕获），prompt 输入抢占 140ms。Input priority: renderer InputPriorityLane boosts prompt input 140ms.

🟢 建议方向（待你定夺）Proposed (pending your call)

  • 先诊断：main:gc-pause 观测（排查中试做，已从本次改动剥离、留作独立改动）→ 引入后取一份带埋点的真实卡顿 trace，定位 868ms 长杆。Diagnose first: main:gc-pause (prototyped, factored out of this change as a standalone patch) → re-introduce it, then capture one instrumented real-lag trace to pinpoint the long-pole.

  • 若是同步阻塞：把那段重活移出主线程 / 拆分让路（watcher / IPC / 线程模型），确保输入投递不被饿死。If sync work: move it off-main / yield harder (watcher / IPC / threading), so input delivery isn't starved.

关键权衡：以上「若是 GC / 若是同步阻塞」是分叉——在没定位 868ms 长杆前，任何一支都可能是白做工，甚至改错方向（这正是你选「先定位再改」的原因）。所以第一步只做诊断埋点，不做策略改动。 Key trade-off: the "if GC / if sync" branches are a fork — before the 868ms long-pole is located, either branch could be wasted or wrong (why you chose "pinpoint first"). So step one is diagnostics only, no strategy change.

（历史）曾评估但否决的改法：非受控 textarea(Historical) evaluated & rejected: uncontrolled textarea

v1.1 曾提议"改非受控 textarea"，但实测证明无效——组字成本是 textarea 原生 O(光标前文本量)，与受控/非受控无关（改后 46→47ms 没变）。已回退，改用 contenteditable。下方对比保留作记录。v1.1 proposed "make the textarea uncontrolled", but measurement disproved it — the composition cost is the textarea's native O(text-before-caret), independent of controlled/uncontrolled (46→47ms, unchanged). Reverted; contenteditable used instead. The comparison below is kept for the record.

  • <textarea value={content}> → <textarea defaultValue={…} ref onInput>。去掉 value prop，DOM 成为唯一真相源，React 不再每次输入协调整份大字符串。value={content} → defaultValue + ref + onInput. Drop the value prop; DOM is the source of truth; React no longer reconciles the whole large string per keystroke.
  • 按钮禁用只需「空↔非空」布尔：onInput 里仅在布尔翻转时 setHasContent → 打字/组字时零 setState、零重渲染。Button-disable needs only an empty↔non-empty boolean: setHasContent only when it flips → zero setState / zero re-render while typing/composing.
  • 14 处程序化 setContent（编辑载入、草稿恢复、append、清空、右键菜单 mutation、虚拟光标、undo、autotest 控制）→ 命令式写 ref.value + 派发 input + 复位光标。多处已经在读 textareaRef.current.value，与现有模式一致。The 14 programmatic setContent sites (edit-load, draft-restore, append, clear, context-menu mutation, virtual cursor, undo, autotest control) → imperative ref.value writes + input dispatch + caret restore. Several already read textareaRef.current.value, so this matches existing patterns.
  • 防抖父同步 / 提交 / 保存改为读 ref.value（本就有 ref）。Debounced parent sync / submit / save read ref.value (the ref already exists).

🔵 受控（现状）Controlled (now)

  • ✅ 状态即真相，读写简单✅ state = truth, simple
  • ❌ 每次输入 O(内容) 协调；IME 组字重复付费 → 大内容 + 中文严重卡❌ O(content) reconcile per input; IME pays it repeatedly → severe lag on large + Chinese

🟢 非受控（建议）Uncontrolled (proposed)

  • ✅ 打字/组字零 React value 成本 → IME 与内容量解耦✅ zero React value cost while typing/composing → IME decoupled from content size
  • ✅ 与 VS Code/编辑器流派一致（原生输入元素不承载整份大文本的 React 协调）✅ aligns with editor-class practice
  • ⚠️ 需仔细处理光标/undo/IME 边界；改动集中在单个组件⚠️ careful caret/undo/IME edge cases; change contained to one component
