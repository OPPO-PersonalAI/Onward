HTML 预览器链接导航重设计

系统性分析：预览内超链接的全部可能形态 → 每一类的目标行为 → 承载架构选型 → 验收方案

摘要

问题：HTML 预览里点击外部链接（如 https://github.com/...）后白屏。
根因：当前架构把外部 URL 直接塞进沙箱 iframe；GitHub 等绝大多数站点通过 CSP frame-ancestors / X-Frame-Options 禁止被 iframe 嵌入，Chromium 拒绝渲染 → 空白。 这是浏览器安全机制，在 iframe 架构内无解。
目标（用户已确认）：预览内点出去的所有链接都必须正常展示，外部网页无论普通点击还是 target="_blank" / window.open，都在预览面内展开。
推荐：方案 A —— 双引擎混合：本地 HTML 继续用现有自定义协议 iframe（保留全部既有能力与 55 项测试断言）， 导航到外部 http(s) 时预览面切换为硬化 <webview>（复用 Open Browser 的成熟实现），历史跨引擎统一。

白屏根因（证据链）

  1. 触发文件 docs/html/file-index-watcher-backend-decision.html 的外链全部为普通 https://github.com/... 形态（无 target="_blank"）。
  2. 点击路径：bridge 拦截 → navigate-request → 主进程分类为 external → HtmlReader 执行 navigateFrame(url)，即 iframe.src = https://github.com/... （HtmlReader.tsx navigate-request 分支）。
  3. GitHub 响应头携带 content-security-policy: frame-ancestors 'none'。Chromium 对被禁止嵌入的 iframe 显示空文档 —— 即用户看到的白屏。Google、各类带登录态的站点行为相同。
  4. 连带缺陷：即使站点允许被嵌入，外站文档内没有我们的 bridge 脚本（bridge 只注入本地 HTML）， ESC / 查找 / 缩放 / 状态上报全部失效；外站内的继续点击不受路由管控。
  5. target="_blank" / window.open：iframe sandbox 未授予 allow-popups， 外站脚本发起的新窗口被静默丢弃 —— 与用户猜测一致（"新开页面那种支持不好"）。

方案对比

方案思路优点缺点 / 风险结论
A 双引擎混合 本地 HTML 留在自定义协议 iframe；外部 http(s) 切换为硬化 webview；历史统一 本地链路零回归（bridge / 查找 / 缩放 / 滚动记忆 / 55 断言全保留）；外站完整渲染，frame-ancestors 无效化（webview 是顶层帧）；webview 硬化、z-order、ESC 已被 Open Browser 的 OB-01..12 验证；改动集中 跨引擎历史合并是新逻辑；查找/缩放对外站需改走 webview 原生 API（findInPage / setZoomFactor，工作量小） 推荐
B 全 webview 整个预览换 webview（本地也用 webview 加载自定义协议） 单引擎、语义统一 推翻现有 iframe 架构：bridge 注入、滚动恢复、55 项断言全部重做；工期与回归风险大；项目历史上曾从 BrowserView 迁到 iframe，覆盖类场景（菜单/对话框 z-order）在预览中比 Open Browser 多得多 不推荐（收益/风险失衡）
C 外链跳 Open Browser 面板 点击外链 → 打开 Task 的 Browser 面板 零新面，全复用 离开预览上下文，不满足"在本页面里展开"；Back 无法回到 HTML 预览语境 不满足需求
D openExternal 系统浏览器 VS Code 默认做法 实现最简单 用户已明确不要 排除

推荐方案 A 细节

引擎切换模型

  • HtmlReader 内部维护 surface: 'iframe' | 'webview'。分类为 external 的导航将 surface 切到 webview 并 loadURL；分类为本地的导航切回 iframe。切换只影响渲染面，工具栏（Back/Forward/Reload/Home/查找/缩放）保持同一套。
  • 历史统一为宿主侧单栈（现状 iframe 历史本就在宿主 historyRef）：每个条目标注 {engine, url}；Back/Forward 跨引擎边界时切换 surface。webview 内部自然发生的导航（外站内点击）通过 did-navigate 事件回填进宿主栈，保持单一事实来源。
  • Home 永远回到打开的本地文件（iframe 引擎），与现状语义一致。

webview 守卫（全部复用 Open Browser 既有实现）

  • 硬化：partition 隔离、contextIsolation / sandbox / nodeIntegration=no、权限请求全拒、下载拦截。
  • setWindowOpenHandler：target="_blank" / window.open → 同 webview loadURL（页内展开，入历史）。
  • will-navigate 守卫：外站内指向本地文件方向的 URL 不放行，回宿主分类器。
  • ESC / Cmd+R / 缩放快捷键：before-input-event 转发（Open Browser 已有通道）。
  • 外站的查找/缩放：webview 原生 findInPage / setZoomFactor，工具栏按 surface 分流。

加载与失败可视化（消灭"白屏"类症状）

  • webview did-fail-load → 预览面显示明确的错误卡片（URL、错误码、重试按钮），不再是空白。
  • 离线 / DNS 失败 / 证书错误同路呈现。诊断事件全程埋点（见验收）。

竞品与内部先例

  • VS Code：Markdown 预览的外链走 vscode.open → 系统浏览器（方案 D，被用户排除）；其 Simple Browser / Live Preview 用独立 webview 面板承载网页 —— 即"外站必须顶层帧"的同一结论。来源：microsoft/vscode extensions/markdown-language-features（preview.ts / openDocumentLink.ts）、microsoft/vscode-livepreview。
  • JetBrains：内置预览是 JCEF 真浏览器（顶层帧），外站直接可渲染 —— 印证 webview 路线。来源：jetbrains.com/help/webstorm（Built-in server / preview 文档）。
  • Electron 官方：嵌入外部内容的推荐承载即 webview / WebContentsView + setWindowOpenHandler / will-navigate 守卫。来源：electronjs.org/docs（security、webview-tag）。
  • 内部先例（最强证据）：本仓库 Open Browser（BrowserPanel.tsx + electron/main/index.ts 客体守卫）已实现同款硬化 webview，含"新窗口请求 → 同面 loadURL"，并有 OB-01..12 自动化断言背书。方案 A 本质是把这套已验证的引擎接到 HTML 预览的外链分支上。

验收计划

1. 全场景验收夹具（用户要求）

新增 test/autotest/fixtures/html-preview/link-matrix.html：一页容纳矩阵中全部 12 类链接 —— 页内锚点、项目内 HTML（含 fragment）、md / 源码 / pdf / 图片、缺失文件、越界文件、file:// 绝对路径（根内 + 根外）、 外部 https（普通 + target="_blank" + window.open 按钮）、mailto:、data:。 外站目标指向测试本地 HTTP 服务器（serve-html-preview-fixture.mjs 扩展一个"模拟外站"端点，带 frame-ancestors 'none' 响应头以复现真实白屏条件），保证断言不依赖公网。

2. 自动化断言（PHTML-46.. 预估新增 8-10 项）

  • 外链普通点击 → webview surface 出现且渲染出模拟外站标记；不再白屏（对照：同 URL 用 iframe 加载必空白）。
  • target="_blank" 点击 → 同面展开、历史入栈；Back 回到本地 HTML（跨引擎边界）。
  • 外站内继续点击第二页 → 同面导航；Back×2 逐级返回直至 iframe 本地页。
  • window.open → 同面展开（setWindowOpenHandler 路径）。
  • did-fail-load（模拟断连端口）→ 错误卡片可见，重试按钮工作。
  • #3 / #5 / #7 的显式断言补齐；ESC 在 webview surface 下仍返回终端。
  • 时序敏感断言按 repeat-inside-test 规约聚合（N=5 或 3 取 1）。

3. 单元测试

  • 分类器扩展表（file:// 根内/根外、window.open URL 分类）。
  • 跨引擎历史栈纯逻辑（push / back / forward / home / did-navigate 回填的决策表）——新 test/unittest/html-preview-history.test.mts。

4. 诊断埋点

renderer:project-editor.html-surface-switched（iframe↔webview，含方向与触发 URL 摘要）、 renderer:project-editor.html-webview-load-failed（错误码）、window-open 展开事件。注册 + infra/trace.md § 2 同步。
