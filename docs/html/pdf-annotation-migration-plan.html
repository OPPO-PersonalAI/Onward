PDF 标注功能迁移：分析与选择清单

Dark PDF Reader v0.3.16 → Onward Project Editor 内置 PDF 阅读器 · 决策前文档，等待确认后再进入实现

1. 一句话结论

Onward 里的 PDF 阅读器，本来就是 Dark PDF Reader 早期版本的一次「裁剪移植」。 resources/pdfjs/app/viewer.js 文件头就写着「Adapted from the Dark_PDF_Reader Chrome extension reference」。所以这次不是从零对接两套代码，而是把同一份代码的新版本重新裁剪一次—— 路径是通的，难点在于新增的部分体量很大，而且底层依赖了对 pdf.js 的私有补丁。

好消息

两边用的是同一个 pdf.js 版本（3.11.174），viewer 的骨架、消息协议、状态记忆结构都对得上， 高亮渲染层是独立的 .highlightLayer，不侵入 pdf.js 自身。

代价

要迁移的新代码约 6000 行 JS + 1200 行 CSS。其中「文本选择引擎」一个模块就占了 2500 行，而且它是高亮功能的前置条件——选不准，就框不准。

必须先定的事

标注数据存在哪里，是一个策略级决定（数据格式 + 持久化 schema）， 按项目规范必须先由你拍板，不能由我单方面写进代码。见第 5 节。

2.3 已经存在的一个缺陷

Onward 当前的 viewer.css 里有一行会破坏文本选择精度的样式。 resources/pdfjs/app/viewer.css:116 写着 .pdfViewer .textLayer :is(span, br) { letter-spacing: 1px; }。 这行改变了 textLayer 的文字度量，导致文本层几何和实际渲染出来的字形对不上—— Dark PDF Reader 在做文本选择精度攻关时，第一步就是把这行删掉 （见 docs/TEXT_SELECTION_ADVERSARIAL.md「已移除会改变 textLayer 几何的 letter-spacing」）。 也就是说，Onward 现在选中文字时看到的高亮框和实际选中的内容本来就有偏差，只是没有高亮功能所以没人注意到。

B. 文本选择引擎 必迁

这一层不是「可选增强」，是高亮功能的地基。 高亮是用「选区的每一行矩形」换算成 PDF 用户空间的 QuadPoints 存下来的。 选区不准 = 高亮框不准 = 存进 PDF 的坐标不准。DPR 为此写了一整套对抗性测试 （docs/TEXT_SELECTION_ADVERSARIAL.md），强制验收条件是 视觉高亮 === Selection.toString() === 剪贴板文本 === 期望文本 四者完全一致。
#功能状态说明
B1删除 letter-spacing: 1px，恢复 pdf.js 原生 textLayer 几何必迁见 2.3。这是修 Onward 的既有缺陷
B2拖选：caretRangeFromPoint 映射 + 几何 fallback必迁浏览器 API 不可用时退回自己算字形几何
B3拖到边缘自动滚动（垂直 + 水平）必迁适应宽度下可以从第 1 页拖到第 3 页
B4跨页选区 overlay（多页连选的视觉高亮）必迁—
B5字素簇（grapheme）边界：Intl.Segmenter + 代理对/组合符 fallback必迁避免把一个 emoji / 带音标字符拖成半个
B6连字（ligature）作为一个选择单元：ffi / ff / fi / fl / 阿拉伯语 lam-alef必迁学术 PDF 极常见
B7标注遮挡判定：表单控件 / FreeText / Stamp / Redact 等阻断穿透选择必迁否则会选中并复制出用户看不见的底层文字
B8透明标注穿透：Highlight / Underline / 透明 Square 等允许选中下方正文必迁B7 的反面，两者必须成对

5.4 方案 C：存进 Onward AppState

优点
  • 零新增文件、零新增 IPC，复用现有 fileMemory 通道
  • 实现最快
代价
  • AppState 会被撑爆——一本书几百条标注 × 每条都带 quads 数组和原文片段
  • AppState 是「界面状态」，不是「用户内容」，语义上放错地方
  • 换电脑、换 workspace 全丢
  • 标注和 PDF 分离，删了 PDF 数据还在

我的推荐：B 为主 + A 作为显式导出动作（可以叫「混合方案」）。 日常编辑走旁车 JSON——写得快、不动源文件、可以放心自动保存； 当你需要把带标注的 PDF 发给别人或换台机器看时，手动触发一次「将标注写入 PDF」， 走 pdf-lib 生成一份带标准 /Highlight 的文件。 这样既保住「打开不改文件」的契约，又保留了标注可移植性，而且自动保存的性能问题自然消失。 代价是 pdf-lib 依赖仍然要引入，D8/D9 那套「抑制原生渲染」的逻辑在读回带标注 PDF 时仍然需要。

方案 A + 自动保存的风险与必须内建的保护

这个组合的核心矛盾：pdf-lib 是全量重写，没有增量写。 Dark PDF Reader 在浏览器里能承受 2 秒轮询的自动保存，是因为它拿到的是 File System Access 的可写句柄， 写入路径短。Onward 要经过「iframe → postMessage → 渲染进程 → IPC → 主进程 → fs」， 而且每次都是整份字节。一本 100MB 的书，单次保存是秒级开销。
#风险必须内建的保护
R1 高频自动保存拖垮渲染线程 / 磁盘 静默窗口：停止操作 800ms 后才触发；内容指纹去重：标注集合的 hash 没变就直接跳过，不做任何字节工作
R2 写到一半崩溃 / 断电 → 源 PDF 被写坏，用户原始资料丢失 临时文件 + 原子 rename：先写 <name>.pdf.onward-tmp，fsync 后再 rename 覆盖。Windows 上 rename 覆盖需用 fs.rename 并处理 EBUSY
R3 pdf-lib 重写会丢掉原有数字签名与线性化 首次对某个 PDF 写入前检测是否含签名，含签名则弹一次明确确认，之后记住选择
R4 只读文件 / 无写权限 / 被别的程序占用 自动保存静默降级（不弹窗打断阅读），改为在标题旁显示可点击的状态；手动 Cmd+S 时才给出完整错误说明
R5 超大 PDF 上自动保存永远追不上编辑速度 按文件大小自适应：超过阈值时把自动保存的静默窗口拉长，并在 UI 上明示「大文件已切换为低频保存」。阈值需要一次实测定标
R6 写盘触发 Onward 自己的文件监听 → Git 状态刷新 → 可能引起循环 写入前后打自有标记，让 watcher 识别「这是我自己写的」，避免误判为外部修改而触发全量重算

以上每一条都要有对应的 trace 事件（main:pdf-annotation.save-* / renderer:pdf-annotation.autosave-*），否则用户报「保存失败」时无从定位。

6.1 pdf.js 需要打私有补丁

Dark PDF Reader 改过 vendor 里的 pdf.js，Onward 的那份是原版。我已经把差异 diff 出来了， 一共三处：

+ this.#altTextManager?.destroy();

//    识别「不可见文本」；另加阿拉伯语 CID 保留逻辑顺序（约 80 行）
+ function isCurrentTextRenderingVisible() { ... }

补丁 1 是纯 bug 修复，无条件该打。补丁 2、3 是 B9 / B10 的前置。 麻烦在于这些补丁改的是构建产物（webpack 打包后的 pdf.js / pdf.worker.js）， 以后升级 pdf.js 时要手工重新应用。建议做法：把补丁提取成 patches/pdfjs-*.patch， 在 scripts/ 里加一个应用脚本，这样升级时至少能看到冲突。

6.2 iframe 边界

Onward 的 viewer 跑在 sandbox="allow-same-origin allow-scripts" 的 iframe 里， 只能通过 postMessage 和宿主通信。这带来几个具体约束：

  • 标注列表侧栏放在 iframe 里（跟 DPR 一样）还是提到 React 宿主侧？宿主侧样式更统一、能复用 Onward 的右键菜单规范， 但要把整个标注数组通过 postMessage 同步过去。
  • 保存要走 IPC，而 iframe 里没有 window.electron。必须：iframe → postMessage → PdfReader.tsx → preload IPC → 主进程写文件。 需要新增一条 onward:pdf:save 消息和对应的回执。
  • 快捷键 Cmd+S 现在没有被转发给宿主。要加进 forwardHostKey 的白名单， 或者在 iframe 内直接处理。

6.3 Electron 里没有 File System Access API

DPR 的保存逻辑有一大块（resolvePdfSaveHandle / requestLocalFileWriteHandle / hasHandleWritePermission / downloadPdfCopy，约 350 行）是在处理浏览器的文件句柄授权、 权限过期、另存副本。这些在 Electron 里全部不需要——主进程直接 fs.writeFile 就行。 这是迁移中少数「变简单」的部分。

6.4 跨平台

  • Windows：写文件要处理文件被占用（EBUSY）、路径分隔符、只读属性。 方案 A 的原地覆盖在 Windows 上风险更高，建议「写临时文件 + 原子 rename」。
  • Linux：Intl.Segmenter 在旧版 Electron 上可用性要确认（当前 Electron 43，没问题）。
  • 三平台一致：Cmd vs Ctrl 的快捷键分支；旁车文件的换行符不要被 Git 的 autocrlf 改掉。
