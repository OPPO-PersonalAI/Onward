Onward 内存诊断闭环 — 基线报告与方案设计

渲染进程内存可超 1 GB · 建立「开发期 + 线上用户期」都能定位内存泄露的闭环 · 2026-08-07

0 · 总览

目标:当内存出问题时,不需要用户复现、不需要开发者猜,诊断数据已经在用户的反馈包里。方案分三层:①便宜的常驻内存采样(进主流程的 perf-trace,随诊断包自动带出);②纯函数阈值检测器(可单测);③分级抓取 + 用户知情同意的反馈通道。

为什么是「闭环」而不是「工具」
本仓库没有远程日志(无 ELK / Sentry),用户反馈的诊断包就是唯一的现场证据。所以内存数据必须默认进入诊断包,而不是等出了问题再让用户装工具、开开关、复现一遍。

发现 ① — ps 的 RSS 严重低估 GPU 进程
GPU 进程 RSS 只显示 82 MB,实际 footprint 是 406 MB(IOSurface 纹理与图形内存不计入 RSS)。这意味着采样层必须用 app.getAppMetrics()(取 workingSetSize)配合分类采集,不能依赖 ps 一类的数字;跨平台语义差异(macOS 无 residentSet)也要在字段上写清单位与含义——VS Code 就因两处各换算一次单位,让 code --status 的内存列错了十个数量级、存活约两年。
发现 ② — 渲染进程的大头是 V8/JS 堆
V8 相关(含被换出部分)≈204 MB,大于 Blink/PartitionAlloc 的 ≈150 MB。用户报告的「超 1 GB」若成立,以比例推断主要是 JS 堆增长——指向监听器、缓存、终端回滚缓冲、大 diff 字符串等 JS 层驻留。这类问题恰好是 heap snapshot / retainer 分析能回答的。

1.2 空闲期采样:6 分钟无单调增长

对活实例以 20 秒间隔连续采样 18 次:渲染进程 RSS 在 122–287 MB 间波动(换页噪声),footprint 仅 364 → 374 MB。结论:短期空闲不泄露;超 1 GB 是使用行为驱动的累积(长会话、大文件 diff、多任务终端输出等),必须靠长时间序列才能定位增长拐点——这正是当前完全缺失的能力。

1.3 代码现状:内存监控为零(grep 核实)

3 · 同类产品调研(要点)

核心结论:没有任何成熟 Electron 产品做完了这个闭环
这既说明难点真实存在(抓取时机、二次 OOM、隐私),也说明按下面的护栏做完,就是超出同类产品水平的能力。
产品做法对我们的启示
VS CodeProcess Explorer(每进程 CPU+内存)+ 本地手动抓快照;生产环境不自动抓堆;内存遥测只在启动时采一次。真正好用的是两个轻量泄漏探测器:事件监听器按创建栈直方图报「最高频泄漏栈」;FinalizationRegistry 抓「被 GC 但从未 dispose」的对象轻量结构化探测器值得移植(能把「有泄漏」直接定位到「哪一行」);连续采样默认关的姿态我们不照抄——他们有海量遥测,我们只有反馈包
Chromium对小比例用户做泊松采样堆剖析并匿名上传;从不对所有人抓完整快照生产环境的答案是「采样 + 有界产物」,完整快照只留给知情同意的场景
Discord内存超 4 GB 触发的是自动重启,且有五重护栏:阈值 + 运行≥1h + 用户空闲≈30min + 不在通话中 + 24h 最多一次凡是自动触发的用户可见动作,光看内存数字不够,要叠加用户状态与频次上限
Sentry .NET唯一的阈值触发抓堆先例:EnableHeapDumps(90%, Debouncer.PerDay(3)),默认每次应用生命周期只抓 1 次(JS/Electron SDK 均无对应物)去抖参数的直接范本;上传通道尺寸上限(压缩 40 MB)说明「自动上传完整快照」这条路本来就不通
Slack对 10% 用户做生产遥测,报 p10/p50/p90/p99 分布(基线 130 MB – 960 MB/workspace),无快照时间序列分布本身已能支撑大多数决策

3.1 「抓取不能把进程搞死」的六种手法(全部纳入本方案)

  1. 能用采样就不用快照 — 泊松分配采样开销极小(Chromium 线上做法);
  2. 能用有界产物就不抓堆 — 堆统计 + 栈写入定长字段(Electron 43 OOM 栈的做法);
  3. 抓之前检查余量 — 完整快照需约 2 倍当前堆的内存(Node 官方警告),余量不足直接放弃并记录 dump-skipped;
  4. 推迟到安全点 — 不在濒死回调里抓(V8 RequestInterrupt 模式);
  5. 阈值设在危险区之前 — 接近堆上限时抓取无法可靠完成(Node 文档承认 + 0 字节文件实证),所以要早触发;
  6. 让健康进程干重活 — renderer 快照由主进程经 webContents.takeHeapSnapshot() 发起,解析在进程外。

4 · 目标架构:三层闭环

第 1 层 · 常驻低频采样 便宜 · 常开(待拍板)
主进程 MemoryWatcher 定时(默认 30 s)采集:app.getAppMetrics()(main / renderer / GPU / 网络)+ 主进程 v8.getHeapStatistics()(含 number_of_detached_contexts 泄漏信号)+ 7 个 worker 自报告(新增一条控制消息:process.memoryUsage() + 堆统计)+ 渲染进程报告(process.getHeapStatistics() + webFrame.getResourceUsage(),把「Blink 资源缓存涨」和「JS 堆涨」区分开)。全部以 perf-trace 计数器事件落盘 → Perfetto 可视 → 随诊断包自动带出。
↓ 样本进入环形缓冲(近 N 分钟)
第 2 层 · 阈值检测器 纯函数 · 可单测
(样本时间序列, 配置) → { pressure: none | warn | critical, reason }。滑动窗口 + 双口径(footprint 绝对值 / V8 used÷limit 比例)+ 连续上升斜率条件;叠加 Discord 式护栏:运行时长下限、每会话触发上限、冷却期。所有参数可用 ONWARD_* 环境变量覆盖,先按初始值上线,等第 1 层收集到真实曲线后再校准。
↓ warn / critical 触发
第 3 层 · 分级抓取 + 用户提示 重型 · 三重防护
A 级(自动,安全):生成轻量「内存报告」JSON(KB 级:指标历史、各进程/线程堆统计、资源缓存、detached contexts 计数)→ 落到 traces 目录 → 通知条提示用户。
B 级(仅用户同意后):完整 .heapsnapshot——单飞锁 + 每会话 1 次 + 余量检查(空闲内存 > 当前堆)+ 冷却期;renderer 由主进程发起,main/worker 各自 v8.writeHeapSnapshot()。
面包屑事件:main:mem-watch.pressure-detected / dump-written / dump-skipped(reason)。
↓ 用户点击「打开反馈」
反馈通道 · 诊断包整合 知情同意
内存报告 JSON 自动纳入诊断包(小,无堆内容)。.heapsnapshot 永不自动打包:反馈弹窗中单独勾选,并用大白话提示(Chrome 模式):「快照包含打开文件的全文、终端记录,可能包含密钥」。大文件走 sync-directory 旁路,避开 zip 全量读入内存的路径。
↓ 用户发给开发者
开发端分析 · 回到起点
诊断包里的内存时间序列直接用现有 open_trace.sh 在 Perfetto 看曲线;.heapsnapshot 用 Chrome DevTools / VS Code 的 v8-heap-parser 看 retainer。开发期同一套设施:ONWARD_MEM_WATCH 调频、调阈值、手动触发 dump(debug IPC),配自动化压力测试建立增长基线。

5 · 现状 vs 目标

现状(用户报「内存超 1 GB」时)

  • 反馈包里没有任何内存数据——只能请用户描述、截图活动监视器
  • 无法区分 JS 堆 / Blink 缓存 / GPU 纹理,只能猜
  • worker 线程内存完全不可见(与主进程共 pid)
  • 不知道内存从何时开始涨、伴随什么操作
  • 开发期也没有任何内存基线,回归无从谈起

目标(本方案落地后)

  • 反馈包自带每 30 s 一个点的内存时间序列,Perfetto 里与用户操作事件对齐
  • 逐进程、逐 worker、JS 堆 / Blink 缓存 / detached contexts 分类归因
  • 阈值触发自动生成轻量内存报告 + 通知用户一键进反馈
  • 用户同意后才有完整快照,retainer 级定位泄漏持有者
  • 同一套设施支撑开发期压测基线与回归门禁

6 · 待拍板的 4 个决策

以下每项都会同时以选择题形式请你确认;推荐项已标出,理由与代价写在卡片里。

决策 1 · 第 1 层采样器在用户正式版的默认状态
A · 默认开启,30 s 低频,走 diagnostic 通道 推荐
代价:每天约 3000 个小事件(<1 MB/天,64 MB 预算内自动轮转);收益:每个用户反馈包天然带内存曲线,闭环第一环免费。VS Code 默认关是因为他们另有海量遥测;我们没有,反馈包是唯一现场。
B · 默认关闭(VS Code 姿态),ONWARD_MEM_WATCH=1 才开
最保守;但用户报内存问题时包里依旧无数据,回到「请用户复现」的老路,闭环断在第一环。
C · 默认开启但 60 s 更低频
成本减半,曲线分辨率也减半;30 s 的成本本已可忽略,再降意义不大。
决策 2 · 阈值触发时自动抓什么
A · 分级:自动只生成轻量内存报告;完整快照仅在用户点击同意后抓 推荐
自动路径零冻结、零隐私风险;重型路径有人类确认兜住。符合 Chromium「线上不抓全量快照」与 Chrome 同意模型。
B · 自动直接抓完整 .heapsnapshot
信息最全,但同步冻结该进程数秒以上、需约 2 倍堆内存(1 GB 堆 → 峰值再 +1~2 GB,可能直接压死进程)、产物含全部明文字符串——自动抓等于未经同意做明文内存转储。
C · 只做轻量报告,完整快照只留开发者手动通道(env / debug IPC)
最安全,但线上疑难泄漏(需要 retainer 图才能定位)就拿不到关键证据,闭环断在最后一环。
决策 3 · 触发阈值口径(初始值,待真实曲线校准)
A · 双口径任一:渲染进程 footprint 持续 > 1.5 GB(约 2 分钟窗口),或 V8 used÷limit > 60% 推荐
故意设在危险区之前(V8 堆上限约 4 GB,60% ≈ 2.4 GB 时抓取仍有余量可行);footprint 口径覆盖「Blink/GPU 涨而 JS 不涨」的情形。
B · 更早预警:> 1 GB 即触发
对齐你报告的水位,但大项目重度使用可能正常达到 1 GB,误报会让通知失去可信度(Discord 的教训:阈值远高于正常使用)。
C · 接近上限才触发(used÷limit > 85%)
最少误报,但此时抓快照大概率失败(2 倍内存开销),只剩轻量报告可用。
决策 4 · 触发后的用户交互形态
A · 非阻断常驻通知条(复用 ScheduleNotification 样式):「检测到内存占用异常,已生成诊断报告」+ [打开反馈] [忽略] 推荐
不打断工作;进反馈弹窗后,内存报告自动附上,完整快照单独勾选并显示隐私说明。每会话最多提示 1 次。
B · 模态弹窗立即询问
触达最强,但内存高≠用户此刻愿意被打断;误报一次就很伤信任。
C · 完全静默,只在用户自己打开反馈时展示「检测到过内存异常」
零打扰,但多数用户不会主动开反馈,「主动提示可发送给开发者」的诉求落空。

8 · 隐私设计(对标 Chrome 同意模型)

产物包含内容处理方式
内存时间序列(第 1 层)仅数字(字节数、计数),无路径、无内容随诊断包默认携带
轻量内存报告(3-A)数字 + 进程/线程名;不含用户内容自动生成,随诊断包默认携带
完整 .heapsnapshot(3-B)等价于明文内存转储:打开文件全文、终端回滚、prompt、URL、可能的密钥——CTF 实证一行 strings | grep 即可提取① 默认不抓;② 抓取前一次确认;③ 永不自动进包,反馈时单独勾选;④ 大白话写明最坏情况;⑤ 本地留存有尺寸上限与最旧清除

脱敏工具(如 heap-snapshot-sanitizer)会同时抹掉「字符串滞留」类泄漏的诊断价值(编辑器类应用最常见的泄漏形态),且残余泄漏面仍在(属性名、作为 key 的路径)——所以不走「脱敏后自动上传」,坚持「知情同意 + 手动发送」。
