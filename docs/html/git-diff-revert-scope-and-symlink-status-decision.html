Git Diff 单文件 Revert 全局刷新 & 软链接 Git 状态缺失

现状机制分析、策略选项对比与复现用例设计 · 分支 20260716-git-state-mirror-and-diff-invalidation

0. 概览：两个问题

问题 1Git Diff 中 revert 单个文件 → 全局刷新

一次单文件 discard 触发 2~3 次全仓库 diff 重算 + 整仓内容缓存清空 + Monaco DiffEditor 整体卸载重建。已在代码层面确认为结构性问题：失效事件不携带文件名，渲染端想只更新一个文件也做不到。

问题 2macOS 软链接进仓库 → Task 不显示 Git 状态

主进程解析全部正确，git 状态数据已经算出来并躺在渲染端 map 里，但「软链接路径 → 真实路径」的别名只在订阅命中热缓存时才建立，冷启动跳过创建 → 从软链接 cwd 出发查不到快照 → 徽章不渲染。Windows junction 同样命中该缺口。

1.3 代码内已有的正确先例

先例 1：保存草稿走本地 patch，不走全量 reload

handleSaveDraft（GitDiffViewer.tsx:5169-5191）在保存后直接原位更新 setDiffResult，注释明确写着避免 loadDiff({force:true}) 往返导致「整个 UI 闪烁」。discard 缺的就是这条快速通道——被 revert 的文件从列表消失，本地移除一行即可。

先例 2：'mirror' 原因的失效已经是文件级

revalidateContentCacheForProject（git-diff-content-cache-wiring.ts:369+）对 watcher 触发的失效逐文件 re-stat、只清真变过的文件——这是 kar-qemu 缓存抖动修复的成果。但 discard 自己的 'manual' 失效反而走整桶清空，比外部随机文件变化还粗暴。

2. 问题1 策略决策点（需用户拍板）

修复涉及三个相互独立的策略点。按项目规则（缓存失效粒度属策略敏感项），每个点都给出现状与候选方案的权衡：

决策点① discard/stage 成功后的列表更新方式

现状：全量 force reload方案：本地 patch + 静默对账
做法成功回调里 loadDiff({force:true})本地 setDiffResult 移除/挪动该行（沿用 handleSaveDraft 先例），再发一次非 force 的静默 reload 对账
优点逻辑简单；列表绝对以 git 为准UI 即时（无 loading 闪烁）；大仓库不付全量 diff 代价；对账仍保证最终一致
缺点大仓库慢（EDR 环境数秒~数十秒）；触发全局闪烁需要正确处理 changeType 迁移（unstage 后 staged→modified 等边界）；本地 patch 逻辑要单元测试锁死
风险控制—对账 reload 兜底：本地 patch 错了最多闪一下回到正确态，不会永久错

决策点② 已知变更（manual）的失效粒度

现状：仓库级整桶清空方案：失效事件携带文件名，文件级清除
做法invalidate(cwd,'manual') + 整桶 wipeinvalidate(cwd,'manual',{files:[...]})；wiring 层只清列出的文件；渲染端只把这些 key 标脏。不带 files 的调用保持现状整桶清空（向后兼容，保守缺省）
优点绝对安全，不会漏清其余文件缓存保温：discard 后点击其他文件仍秒开；EDR 大仓库收益最大；渲染端第一次拿到「能只动一个文件」的能力
缺点一次单文件操作清掉全仓缓存，是本 bug 的核心根因之一失效通道签名变更（invalidator / ipc-handlers / preload / 渲染端 4 处联动）；漏传文件名的新调用点会退回整桶（安全方向的退化）
一致性保障—watcher 的 'mirror' 失效链完整保留，作为独立的最终一致兜底

决策点③ DiffEditor 重挂载策略（generation 是否留在 React key 里）

现状：generation 参与 key方案：从 key 移除 generation，仅保留显式 nonce + 文件标识
语义任何 mirror 状态变化（含后台外部写入、discard 自己引发的重算）都强制整编辑器重挂载。git-state-mirror-types.ts:98-110 注释说明这是「Refresh Changes 级联干净重挂载」的既有设计重挂载只发生在：用户点 Refresh Changes（nonce++，GitDiffViewer.tsx:3284 已存在）、切换文件（nonce++，4406 已存在）、切换 cwd。mirror 数据变化通过正常 React 数据流更新内容，不拆编辑器
优点任何状态漂移都能靠重挂载「重置到干净世界」，是隐式兜底消除可见闪烁的主体；滚动位置/选区/折叠状态天然保留；这是 VS Code 的模型（编辑器实例稳定，模型内容原位更新）
缺点用户每次 revert/外部写入都看到编辑器闪烁——正是本次要修的现象失去隐式兜底：若某个下游层有「靠重挂载才能自愈」的隐藏依赖，会暴露出来（需要回归测试覆盖：staleness 系列 GDS-06..10、chaos-convergence、image-diff 全绿才算安全）
折中变体③-折中：generation 保留在 key 中，但仅当选中文件自身出现在 mirror 变更指纹里时才让它递增进 key（实现复杂度高、语义绕，不推荐但列出供比较）

组合方案对比

方案 A · 最小修复①本地 patch，②③维持现状

  • 只改 handleDeny/handleKeep：本地 patch + 静默对账
  • 去掉全量刷新 #1 与显式 loading
  • 但 #2/#3 的整桶清空与 silent 全量 reload 仍在，generation 重挂载仍在 —— 可见闪烁只减轻、不消失
  • 改动面：1 个文件；风险最低；治标

方案 B · 完整修复（推荐）①+②+③ 全做

  • 本地 patch + 文件级失效 + 移除 generation 重挂载
  • 一次 discard = 移除一行 + 只清该文件缓存 + 编辑器不拆；其余文件保温
  • watcher 'mirror' 链完整保留作最终一致兜底；非 force 静默对账兜列表正确性
  • 改动面：4~5 个文件（invalidator / ipc-handlers / wiring / GitDiffViewer / preload 类型）；需配套 unit + autotest 锁死

待用户决策

① 列表更新：本地 patch + 静默对账 vs 维持全量 reload？
② 失效粒度：文件级（带 files 的 manual 失效） vs 维持整桶？
③ 编辑器 key：移除 generation（显式 nonce 驱动重挂载） vs 维持 generation 重挂载 vs ③-折中？

推荐组合：①②③ 全选新方案（= 方案 B）。方案 B 的每一步都有既有先例或既有机制兜底（handleSaveDraft 先例、revalidate 文件级机制、nonce 已存在且已接线）。

S5查找失败gitStatusIdentity.ts:145-178直查（软链接 key）miss + 别名 miss → mirror=null；legacy 比较（软链接 vs realpath 纯字符串）=false → branch/repoName/status 全 null → 徽章不渲染

为什么「偶尔又好了」

若订阅时 router 缓存恰好是热的（另一个终端已打开过同一仓库、或 30s 退订宽限期内重进），subscribeMirror 返回非 null，别名建立，状态立即恢复显示——与「时好时坏」的现象观察完全吻合。shell 集成关闭时（无 OSC）显示回退到 realpath 的 terminalInfo.cwd，反而正常。

Windows 结论

机制上同样存在：realpathSync 会解析 junction / symlink，产生同样的「上报路径 ≠ 快照 key」失配，且 normalizeTerminalGitPath 连 /private 那样的局部缓解都没有。修复与测试按双平台设计（win32 fixture 用 junction，无需管理员权限；macOS/Linux 用 ln -s）。

3.1 修复方案（接线级 bug 修复，按项目规则可自行实施，此处备案）

让订阅无论冷热都返回规范 key，渲染端始终建别名

  • GIT_STATE_MIRROR_SUBSCRIBE 返回形状从 snapshot | null 改为 { canonicalCwd, snapshot: snapshot | null }（主进程已有 canonicalise()，零额外成本）；
  • 渲染端 subscribeMirror 回调中无条件 mergeMirrorAlias(rawCwd, canonicalCwd)，快照非 null 时照旧合并快照；
  • preload 与类型同步更新；退订路径 removeMirrorAlias 已按 rawCwd 删除，无需变动；
  • 覆盖所有平台（macOS 用户软链接、/var firmlink、Windows junction、Linux symlink）——不依赖任何平台特判。

备选（未选）：渲染端做 realpath —— 渲染进程无 fs 权限，需加 IPC，且每次显示解析都要跑，劣于订阅时一次性建别名；mirror-update 时补建 —— 渲染端不知道 raw→canonical 映射，仍需主进程给答案，绕一圈等价于本方案。

4. 同行产品调研

4.1 问题A同类：单文件 discard 后的刷新范围

VS Code乐观更新 + 后台对账（optimistic-then-reconcile）—— 源码级确认

discard 走 Repository.clean(resources)，两阶段：① 乐观本地更新——getOptimisticResourceGroups() 直接把被 discard 的路径从内存 resourceStates 里过滤掉（零 git 调用）并立即应用，这就是 discard 秒响应的来源；② 权威对账——随后 updateModelState 仍跑一次全仓 git status 换入真实结果，延迟被乐观更新遮住。并发上，新刷新会 cancel 掉 in-flight 的旧刷新（最新者胜），刷新方法带 @throttle。无闪烁的关键：乐观分组复用同一批 Resource 对象（保持对象标识），SCM 树做增量 diff 而非重建；discard 只关掉被 discard 那个文件的 diff 标签页（closeDiffEditors），其他打开的 diff 编辑器一概不动。由 git.optimisticUpdate 设置门控（默认开）。

来源：vscode git repository.ts · SCM provider 指南

JetBrains真正的文件级脏范围（targeted dirty-scope）

revert 单文件只把该路径标脏（VcsDirtyScopeManager.fileDirty(FilePath)），ChangeListManager 异步只复查这个脏范围，不扫全仓；markEverythingDirty() 是显式的「全部重扫」兜底。这是「精确增量刷新」阵营的代表。

来源：VcsDirtyScopeManager API · ChangeListManagerImpl 源码

GitKraken / Sublime Merge / Fork / Tower 均闭源，公开资料只到「按文件 discard + Undo 栈 + watcher 驱动刷新」层面，粒度未公开。共识：两个阵营（乐观对账 vs 精确脏范围），但没有任何一家会重挂载文件树或无关的 diff 编辑器。本文档方案 B 的 ①=VS Code 模式、②=JetBrains 模式、③=两家共同的编辑器稳定性原则。

4.2 问题B同类：软链接路径下的 git 状态

VS Code双路径别名 + 经软链接重构仓库根 —— 源码级确认

该问题类在同行中普遍存在（VS Code #5970 从 2016 开到 2023 才关闭；GitLens 至今继承同类问题）。根因与我们完全一致：git rev-parse --show-toplevel 返回 realpath 而工作区/cwd 是软链接路径，status 本身工作正常、坏在路径匹配（调研代理已实测复核）。VS Code 的修法两条互补：① 经软链接重构根路径——当 toplevel 与输入路径分叉时，改用 rev-parse --path-format=relative --show-toplevel（git ≥2.31）再 path.resolve(输入路径, 相对根)，得到「以用户打开的软链接形式表达」的根；② root↔realpath 别名——存一份 rootRealPath，把任意绝对路径映射成仓库相对路径时两种形式都试。不用 device+inode 比较。Windows junction 是同一问题类（git 同样解析它），VS Code 为此单独留了 Windows 分支。

来源：git.ts getRepositoryRoot · model.ts getRepositoryRootRealPath · issues #5970 / #181676 / #109865 · GitLens #1776

本文档 §3.1 的修复（订阅时无条件建立 raw↔canonical 别名）与 VS Code 的「双路径别名、两边都试」是同一模式——我们的 mirrorSnapshotAliases 机制本来就是为此设计的，缺的只是冷启动时的建立时机。

交付顺序

先落测试（对现状应红）→ 实施修复 → 同测试转绿 → --only 隔离验证 + 触及套件回归（staleness / image-diff / GSM static）→ 汇报。符合「先复现、后修复」的要求与 5-step SOP。

5.5 实施结果（v0.3 附录）

已实施并验证四个决策点全部按推荐方案落地

  • 红色复现确认：修复前构建上，GSY-01/02 红（软链接徽章不渲染，与用户现象完全一致）、GRS-04 红（一次 discard 触发 3 次全量列表加载）、GRS-03 红（整桶清空导致重点击冷读）。
  • 修复后全绿：GSY 4/4、GRS 10/10（含 GRS-02b 探针灵敏度自检——refreshChanges 的真实重挂载会剥落 DOM 标记，证明 GRS-02 的绿不是假阳性）。一次 discard 的列表重算次数从 2~3 次降到 ≤1 次（mirror 回声对账），其余文件内容缓存保温（重点击零拉取），Monaco 编辑器不再因后台状态变化整体重建。
  • 测试期间发现的额外问题：后台静默重载的选中恢复可能在「选中 → 点击 Deny」间隙把选中换成别的文件，导致 discard 误伤（诊断运行的磁盘证据：checkout 实际还原了 alpha 而非目标 beta）。已给 triggerFileAction 增加期望文件名保护；本地 patch + 单次对账本身也大幅缩小了该竞态窗口。
  • 单元层：GLP-01..11（本地 patch 决策表，与主进程 buildGitResourceFields 锁步校验）、IVS-01..04（文件级失效谓词与明细透传）、软链接别名 3 例（identity 测试）。全套 117/117 绿。
