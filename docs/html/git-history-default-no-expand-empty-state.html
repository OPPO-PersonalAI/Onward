Git History 默认不展开 diff — 占位符与 Logo 设计

进入 Git History 时不再自动渲染"第一个提交的第一个文件"的完整 diff，改为占位符引导 · 竞品调研 + 交互/视觉方案 · 2026-07-15

一句话结论：你的想法与业界主流一致——我查证的成熟产品没有一个是"进入历史后自动铺开第一个文件完整 diff"的。 改法在代码上很小：renderDiff() 里"未选中文件"的占位符分支本就存在，只是被一行"自动选中第一个文件"给架空了。去掉那行、把占位符升级成带 Logo 的空状态即可。

1. 背景与问题

现象：进入 Git History 后，左侧默认选中第一个提交，中间列出该提交的变更文件，右侧自动选中并渲染第一个文件的完整 diff。当这个文件很大时，进入瞬间就要做一次重量级 diff 渲染，造成明显卡顿。

触发点（代码）：GitHistoryViewer.tsx:1229 的 return files[0] —— 文件列表一就绪，就自动把 selectedFile 落到第一个文件；随后 selectedFile 变化的 effect（1234-1261）立即发起 diff 加载与渲染。

目标：进入时不自动渲染任何文件 diff，右侧 diff 区显示一个占位符（Logo + 引导文字），提示用户"点击左侧文件查看修改"。这样把"重渲染"从"进入即发生"改成"用户点击才发生"，卡顿消失。

2. 竞品调研结论

成熟产品的默认态分两类，都比"自动渲染重 diff"轻：

产品选中提交后，右侧默认是什么逐行 diff 何时渲染来源
VS Code（内置源代码管理 / Timeline） 不自动打开任何 diff；列出变更文件，点击文件才把 diff 作为标签页打开（git.openDiffOnClick） 点击驱动、按需打开 docs · #209029
GitLens（提交详情 / Inspect） 未选中提交时显示"empty boilerplate"空占位 选中后加载 #2382
JetBrains（Git Log） 选中提交只自动列出变更文件（轻量），看逐行 diff 需再点文件 / Ctrl+D 再点一次才展开 Log tab
Sublime Merge 选中提交默认落在"summary 摘要"标签，而非某个文件 diff 点文件才看 diff #1730
GitKraken / Fork 选中提交 → 显示信息 + 变更文件列表；点文件才看 diff（三段式） 点文件才渲染 GitKraken · Fork
空状态设计规范（GitLab Pajamas，最具体可照搬）：四个组成部分 = 插画/图标 + 标题（≤5 个词、动词开头、结尾不加标点）+ 描述（说明"为什么空 + 下一步做什么"）+（可选）单个行动按钮。 我们的场景属于 "Blank content" 类。来源：Pajamas · Empty States

4. 默认态方案 A / B

方案进入后默认态对应竞品取舍
A 推荐 默认选中第一个提交 + 显示其变更文件列表；右侧 diff 区显示占位符 JetBrains / GitKraken / Sublime Merge 保留"一眼看到最新提交改了哪些文件"的上下文；只去掉重渲染。改动最小、体验最连贯
B 备选 连提交也不默认选中；提交/文件/ diff 三栏都空占位 更接近"完全零状态" 最干净，但进来一片空、要点两次（先选提交再选文件）才有内容，上下文丢失更多
我的倾向是 A。卡顿的根源是右侧 diff 的重渲染，而不是"选中提交"或"列文件"。方案 A 精准砍掉重渲染，同时保留有用的上下文——也和大多数专业 Git 工具一致。B 更激进，除非你希望进来完全空白。

5. 恢复上次选中的处理

现有代码有一段"从 localStorage 恢复上次选中的提交 / 文件 / 滚动位置"逻辑（1134-1178 等）。这里有个隐患：如果上次恰好停在一个大文件，进入时会自动恢复并重新渲染它的 diff，卡顿又回来了——这本质上也是一次"进入即重渲染"。

选项恢复行为取舍
R1 推荐 只恢复提交选中 + 滚动位置，不自动重新打开上次的文件 diff（右侧仍是占位符） 性能表现始终一致，"进入不重渲染"这条规则没有例外，最符合你这次的诉求
R2 备选 完全恢复（含重新打开上次的文件 diff） "接着上次看"体验好，但大文件时会重现卡顿——与本次目标相冲突

6. 占位符设计

按 Pajamas 规范，占位符 = 图标 + 标题 + 描述（本场景无需行动按钮，"点击左侧文件"本身就是行动指引）。下面是提议占位符的真实渲染预览（此处用 Logo 候选 A 的图标示意，最终图标见第 7 节选择）：

点击文件查看修改
从左侧文件列表中选择一个文件，即可在此展开它的差异内容。

复用现有 .git-history-no-selection 容器，扩展成"图标 + 标题 + 描述"三段式；颜色沿用主题变量（--accent / --muted），暗色适配无需额外处理。

7. Logo 候选（4 个）

结合 Lucide 与 VS Code Codicon 两套主流图标库的隐喻，给你 4 个方向（均为原创 SVG，行内绘制、无外部依赖）。每个都同时渲染了大图（空状态用）与小图（列表/工具条用）：

A · 双文档对比 (file-diff) 推荐
两份文档叠放，前页带红"−"绿"+"。最直接表达"查看某文件的修改/差异"，与占位符文案"点击文件查看修改"语义最贴。
语义：文件级 diff
B · 分支对比 (git-compare)
两个提交节点 + 交叉箭头，Lucide git-compare 的隐喻。强调"两个版本之间的比较"，偏 Git 语义而非文件语义。
语义：版本对比
C · 历史时间线 (history)
时钟 + 逆时针回拨箭头，Codicon history。呼应"Git History"这个页面身份，但不直接表达"看差异/点击"。
语义：历史/时间线
D · 提交 + 点击 (commit + cursor)
一排提交节点、中间高亮，下方一个光标箭头。强调"请点选一个提交/文件"的动作邀请，偏引导而非内容。
语义：点击选择
我推荐 A（双文档对比）。占位符出现在右侧 diff 区，文案是"点击文件查看修改"——这里最该表达的是"文件级差异"，双文档 +/− 的隐喻最准。B 偏"版本对比"、C 偏"页面身份"、D 偏"动作邀请"，都可以，但和这个位置的语义没 A 贴。

9. 改动点与测试计划

代码改动（方案 A + R1 为例）

文件改动
GitHistoryViewer.tsx:1216-1231去掉"自动落到 files[0]"：仅保留 prev（本会话已选）与 storedFile（localStorage）匹配分支；都不命中时返回 null（不再默认选第一个文件）

R1 时：恢复逻辑（1134-1178 一带）恢复提交选中与滚动，但不把 selectedFile 恢复成上次的文件（保持占位符）

测试计划（单元 + autotest 成对交付）

  • 单元测试（test/unittest/）：把"默认选中文件"决策抽成纯函数（输入 files / prev / storedFile → 输出应选文件或 null），锁定"都不命中时返回 null"这张决策表。
  • autotest（src/autotest/test-git-history.ts 现有 suite 内扩展）：进入 Git History 后断言右侧渲染的是占位符（.git-history-no-selection / 新类名）、没有 diff 视图节点；再 selectFileByIndex(0) 后断言 diff 出现。属于既有 suite 扩展，无需新增 runner。
  • 性能：进入 Git History 不再触发首个文件 diff 加载，可在进入路径上确认 getHistoryDiff 首帧不被自动调用（诊断 trace 事件按需补一条 renderer:git-history.diff-placeholder-shown）。
