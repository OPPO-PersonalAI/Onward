Git Diff 揭示周期：「隐式状态机」到底是什么问题

面向 src/components/GitDiffViewer/GitDiffViewer.tsx · 代码基线 d93ae6e（master）
这份文档只做一件事：把「揭示周期是个隐式状态机」这句话拆开，讲到能判断该不该动它。
阅读约定
第 1 节把所有名词从零定义，后面每一节都只使用已定义过的词。文中每一处代码断言都带行号，可以对着 d93ae6e 逐条核对。

01先把名词定义清楚

要讲清楚问题，得先有五个精确的名词。它们都不是通用术语，是这份代码里的具体东西。

1.1 Monaco 与 model

定义：model（文本模型）
Monaco 是 VS Code 的编辑器内核，本项目用它渲染 Git Diff。Monaco 不直接持有字符串，它持有 model——一个带唯一标识（URI）的文本文档对象。一个 diff 视图需要一对 model： original（基线侧，比如 HEAD 或索引里的版本）和 modified（工作区侧，你正在编辑的版本）。

1.2 diff 是异步算出来的

定义：diff 计算
Monaco 不在你设置内容的那一刻就算出差异。它把计算排入队列（去抖 200 ms），交给后台线程， 算完后触发 onDidUpdateDiff 事件。在这之前，editor.getLineChanges() 返回的是上一次算出的结果，而不是 null——这一点是后面所有麻烦的起点。

1.3 揭示（reveal）

定义：揭示
用户点开一个变更文件后，视口应当落在第一处改动上，而不是文件开头。把视口移到那一行的动作， 本文称为揭示。它需要知道「第一处改动在第几行」——而这个信息只能从 getLineChanges() 里拿，也就是只能从 diff 计算结果里拿。

1.4 折叠（hideUnchangedRegions）

定义：折叠
Monaco 的 hideUnchangedRegions 会把大段未改动的内容收起来，只留改动附近的上下文。 它同样依赖 diff 结果——没有 diff 就不知道哪些区域「未改动」。

1.5 揭示周期

定义：揭示周期（reveal cycle）
从「用户选中一个文件」到「视口停在正确位置、折叠正确呈现」之间的这一整段过程， 代码里用一个状态变量 diffRevealPhase 管理，本文称为揭示周期。 它的存在理由是：内容和 diff 都是异步到达的，不能在内容刚到时就定位视口， 否则会出现「先跳到开头、再闪一下跳到改动处」的抖动。

1.6 一句话概括这五个名词的关系

// 想把视口放对位置，必须先知道第一处改动在哪
// 想知道第一处改动在哪，必须等 diff 算完
// diff 是异步算的，而且算之前 getLineChanges() 会返回旧答案
//   ↓
// 所以需要一个「等待 → 定位 → 完成」的过程管理，这就是揭示周期

02这个周期要解决什么

把需求写成一句可判定的话：

揭示周期的契约
当揭示周期结束（回到 idle）时，视口的位置和折叠的状态， 必须是根据「此刻两个 model 里实际装的内容」算出来的 diff 得到的。

这句话看着简单，难点全在「此刻」两个字。因为有三样东西在各自独立地变化：

① 用户的选择

点了哪个文件、什么时候点的、点完有没有滚动。

② 磁盘上的内容

agent 随时在改文件，也可能 git add / 提交，改变基线。

③ Monaco 的内部状态

model 里装了什么、diff 算到哪一步、折叠区记录的是哪一版。

三者互不同步。揭示周期的职责就是：在这三者达成一致的那个瞬间做决策， 早了会读到旧数据，晚了用户会看到抖动。

03显式的部分：三个相位

代码里确实有一个显式的状态变量，只有三个取值（GitDiffViewer.tsx:698）：

type DiffRevealPhase = 'idle' | 'waiting-diff' | 'restoring-scroll'
图 1 · 显式相位机：三个状态、两条正向转移、一条回边
这部分设计是清楚的
三个相位、转移边、以及「waiting-diff 期间内容隐藏，避免抖动」的意图，都写在代码里， 有类型约束，读一遍就能懂。问题不在这里。

04隐式的部分：问题所在

问题在图 1 中间那条边上写的「四条路径之一」。waiting-diff → restoring-scroll 这一步，代码里有四个不同的地方可以触发（GitDiffViewer.tsx:232）： 

type DiffRevealTrigger = 'diff-computed' | 'model-bound' | 'warm-ready' | 'timeout'

四个触发点分散在文件的四处，相距数千行：

触发路径行号它代表的意思
diff-computed5386Monaco 通知「diff 算完了」
model-bound5739model 刚绑定好（在点击延迟测量的回调里）
warm-ready1947温重开快速通道：判断「已有可用的 diff」
timeout1881等了 2 秒没等到任何信号，兜底
核心问题，一句话
代码里没有任何一处写着「在什么条件下，允许做揭示决策」。 这个条件被拆散成四份，分别隐含在四个触发点各自的局部判断里； 而它们要保证的是同一个不变量（§2 的契约）。

换个说法。一个显式状态机长这样：状态 × 事件 → 下一状态，转移表写在一处， 所有分支穷举可见。而这里是：四个互不相识的地方各自决定「我现在可以推进了」， 它们唯一的共同约束是一句守卫（GitDiffViewer.tsx:1857）： 

const requestDiffRevealRestore = useCallback((reason: DiffRevealTrigger) => {
  if (diffRevealPhaseRef.current !== 'waiting-diff') return   // ← 唯一的共同约束
  ...
  setDiffRevealPhase('restoring-scroll')
}, [...])

这句守卫只保证「不重复推进」——先到的那条路径赢，其余的静默返回。 它完全不检查「先到的这条路径，此刻读到的 diff 是否对应 model 里的内容」。 那个判断，是每条路径自己的事。

05四条触发路径的真实条件

把四条路径各自实际检查了什么列出来，问题会变得很直观。

5.1 diff-computed — 唯一真正正确的那条

editor.onDidUpdateDiff(() => {
  diffComputedAtRef.current = { seq: modelWriteSeqRef.current, originalUri, modifiedUri }
  requestDiffRevealRestore('diff-computed')
  ...
})

Monaco 亲口说「算完了」，所以此刻 diff 与 model 内容一致。条件正确

5.2 timeout — 明知可能不对的兜底

diffRevealTimeoutRef.current = window.setTimeout(() => {
  requestDiffRevealRestore('timeout')
}, DIFF_REVEAL_TIMEOUT_MS)   // 2000 ms

条件是「时间到了」——与 diff 是否算完毫无关系。它的存在理由是「宁可位置错，也不能永远不显示内容」。 这是合理的工程取舍，但它意味着契约在这条路径上被明确放弃了。 条件与契约无关

5.3 warm-ready — 修复前是错的，现在是对的

修复前（引发 2026-07-26 报障）

editor.getLineChanges() !== null

语义是「这个控件历史上算过某一版 diff」。因为 Monaco 在内容变化时保留旧结果， 这个判断在「答案已经过期」的整个窗口里都成立。

修复后

isDiffCurrentForBoundModels(editor)
// 已绑定 URI 对 + 写入序号都匹配

语义是「已算出的 diff 正是为当前这对 model 算的，且此后没有写入」。

条件已修正 但注意：这个修正只发生在这一条路径上。

5.4 model-bound — 最能说明问题的一条

// GitDiffViewer.tsx:5723-5740（节选）
const active = clickLatencyTrackerRef.current.getActive()
if (!active || active.fileKey !== selectedFileKey || active.stateSetAt === null) return

clickLatencyTrackerRef.current.markModelBound(selectedFileKey)
...
const editor = diffEditorRef.current
if (editor) {
  requestDiffRevealRestore('model-bound')     // ← 推进揭示周期
}
请注意高亮那行的含义
clickLatencyTracker 是性能测量组件——它的职责是统计「用户点击到内容呈现」花了多久。 这里的判断是：「当前是否有一次进行中的点击延迟测量」。

也就是说：视口能否被正确定位，取决于此刻是否恰好有一次性能测量在进行。 没有测量在飞（例如面板重开、程序化选中、测量已封板），这条路径就不触发； 有测量在飞，它就可能抢在 diff 算完之前推进周期。

它检查的东西与「diff 是否对应当前内容」完全无关。 条件与契约无关，且耦合了不该耦合的模块

5.5 汇总：四条路径对同一个契约的保证程度

路径实际检查的条件与契约的关系后果
diff-computedMonaco 事件 保证正确
warm-readyURI 对 + 写入序号匹配 保证（修复后）正确
timeout经过 2000 ms 明确放弃 位置可能属于旧内容；靠事后纠正补救
model-bound有点击延迟测量在进行 无关 位置可能属于旧内容；且行为随「是否在测量」而变
这就是「隐式」的确切含义
契约（§2）是一个；实现它的条件是四份，其中两份不保证契约。 而没有任何一处代码或文档陈述这个事实——你必须把四个相距数千行的地方全部读完， 才能知道「揭示决策可能在 diff 过期时发生」。

06为什么这会系统性产生缺陷

到这里，「隐式」是一个可以精确陈述的属性。但为什么它危险？因为它决定了修改者的提问方式。

隐式状态机诱导的提问

「这个地方要不要加处理？」

这是一个局部问题。回答它只需要看眼前这几十行。 答完就改，改完测试通过，看起来完成了。

显式状态机诱导的提问

「这个缺陷的存在条件是什么？」

这是一个全局问题。回答它必须先说清「在哪些状态组合下会出错」， 答案自然落到转移表的某几格，改动位置也就唯一确定了。

2026-07-27 那轮修复的实测数据
在一次会话里，为修复本报障共引入 8 个新缺陷（全部被测试拦住，无一进入提交）。 其中 4 个直接源于这个面。四个的共同点：都是在回答「要不要加处理」，而没有先问「存在条件是什么」。

第三个数字很重要：测试遏制住了这一类缺陷，但没有消除它。 测试把「带缺陷发布」变成了「修复要花 8 轮」。这是很大的改善，不是治愈—— 利息已经付过一次，下一个改这块代码的人还会再付。

07四个实例逐一解剖

抽象讲完，看四个具体的。每一个都按同样的格式：我加了什么干预 → 忽略了什么前提 → 显式转移表会怎样避免它。

实例 1：清扫的保留集在错误的时刻求值

干预
销毁不再需要的 model，防止内存无界增长
做法
调度时算出「要保留哪些 URI」，100 ms 后执行销毁
忽略的前提
这 100 ms 里可以完成一次「解绑 → 重新挂载」，于是保留集记录的是旧绑定
后果
把新挂载刚绑好的 model 销毁了；探针返回 null，每个等待都烧满预算，单个用例从 35 s 变成 227 s
转移表会怎样避免
「销毁」是一个动作，转移表要求它声明前置状态。写下来就会发现前置状态必须在执行时刻成立，而不是调度时刻

实例 2：中间态的事件把一次性纠正吃掉

干预
若揭示是在 diff 未确证时做出的，武装一次纠正，等下次 onDidUpdateDiff 重做
做法
if (provisional) { provisional = null; if (条件成立) 执行纠正 }
忽略的前提
onDidUpdateDiff 每次计算都会触发一次，不是每次都是终态。中间态那次条件不成立，却已经把纠正清空了
后果
真正的 diff 到达时无枪可用，视口永久停在错误位置
转移表会怎样避免
「一次性纠正」是一个状态位，转移表必须为它写出置位和清位两组条件。一旦分开写，「收到事件」和「纠正已用掉」是两件事就显而易见了

实例 3：防御性判断在另一条路径上反噬

干预
为避免实例 1 复发，改为「保留活控件当前持有的 model」
忽略的前提
面板模式下 detachDiffEditor 故意不清空 diffEditorRef，所以「非空」不等于「控件还活着」
后果
解绑路径上读到已卸载控件持有的旧 model，把它们保护了下来——正好保住了清扫本该回收的那一对，原 bug 复活
转移表会怎样避免
转移表要求为每个状态写判定依据。写「控件是否存活」时就必须回答「用什么判定」，而 ref !== null 会立刻暴露为不充分

实例 4：重建条件过宽，破坏了首次载入

干预
全量写入内容后重建 diff 视图模型，让折叠区从头计算
做法
只要有一侧内容变化就重建
忽略的前提
缺陷的存在条件是「有旧折叠状态可继承」。首次填充内容时根本没有旧状态，重建纯属破坏——它把揭示周期正在等待的那次计算一并丢掉
后果
冷启动那次试验反复走 timeout 兜底，揭示落到第 1 行
转移表会怎样避免
这是最直接的一例。转移表的每一格就是一个存在条件。填格子的动作强制你回答「哪些状态下需要重建」，而不是「写入后要不要重建」
四个实例的共同结构
  • 每一个都是正确的意图加在了条件不完整的位置上
  • 每一个的错误前提，都是一句没人写下来过的隐含假设
  • 四个假设分别关于：时刻（实例 1）、事件语义（实例 2）、判定依据（实例 3）、存在条件（实例 4）
  • 它们全都是转移表天然会强制你填写的字段

08显式化之后是什么样

「显式化」不是加注释，也不是重写渲染逻辑。它是把「什么时候允许做揭示决策」这个判断， 从四个触发点里抽出来，收成一个纯函数，然后让四条路径都去问它。

8.1 结构上的变化

现在

L1881  timeout       → 时间到？ → 推进
L1947  warm-ready    → URI+序号？ → 推进
L5386  diff-computed → Monaco 事件 → 推进
L5739  model-bound   → 有测量在飞？ → 推进
              ↓
       requestDiffRevealRestore
         只查「是否已在推进」

四份条件，两份不保证契约，无处陈述。

显式化后

L1881  timeout       ┐
L1947  warm-ready    ├→ resolveRevealAction(
L5386  diff-computed │     phase, trigger,
L5739  model-bound   ┘     diffCurrent,
                          contentReady, ...)
              ↓
   'apply' | 'defer' | 'apply-provisional'
              ↓
       单一执行点

一份条件，穷举可见，可单测。

8.2 转移表的形状（示意，不是最终设计）

下表只为说明「表长什么样」。真正的取值集合需要在实现前和你逐格确认， 因为每一格都是一个产品行为决定，不是实现细节。

触发diff 是否对应当前 model内容是否就绪决策理由
diff-computed是是apply唯一无条件正确的组合
warm-ready是是apply温重开快速通道，保留 4891fc9 的收益
任意是否defer正文还在取，签名会与占位内容比较
model-bound否是apply-provisional先给用户看到东西，武装一次纠正
timeout否是apply-provisional同上；兜底不能变成永久错误
timeout否否需要你决定：继续等（可能永不显示），还是显示空态？
这张表本身就是交付物
注意最后一行——它是一个今天代码里没有答案的组合。现在的行为是「碰巧怎样就怎样」。 把表填出来的过程，会把这类「从未被决定过」的格子全部暴露出来。 这比任何重构都更有价值：它把未知变成已知。

8.3 与已有工作的衔接

  • shouldCompleteWarmReveal() 已经是这个形状的四分之一——纯函数、有单测（WRG-01..07）。显式化是把它扩展成完整的表，而不是从零开始
  • 时序敏感的端到端覆盖已就位：MT-01..08 覆盖「文件在揭示周期任意时刻被改动」的八个相位，GDS-52/54/55 覆盖跨 git 状态重开。重构有护栏
  • renderer:git-diff.warm-ready-gate 已经在上报 diffCurrent，线上能观察到「决策时 diff 是否过期」的真实分布

09代价、风险与取舍

收益
  • 把「4/8 的缺陷注入率」的结构成因去掉
  • 暴露「从未被决定过」的状态组合（见 8.2 最后一行）
  • 解开 model-bound 对性能测量组件的耦合
  • 转移表可单测穷举，不需要构建应用
风险
  • 动的是已经修好并验证过的代码——引入新回归的可能真实存在
  • 四条路径的现有行为里，可能有我尚未理解的意图（尤其 model-bound 为何与测量耦合）
  • 填表过程会问出若干产品决策，需要你的时间
诚实的判断
这不是紧急项。用户当前看到的行为是正确的（回归 108 通过 / 0 失败 / 零抖动）。 这笔债的成本不落在用户身上，落在下一次改这块代码的人身上。

所以合理的时机是：在下一次需要改揭示逻辑之前做，而不是现在为了做而做。 如果短期内没有触及这块的计划，把这份文档留在库里、等到那时再读，也是完全站得住的选择。

10你需要决定什么

选项成本说明
先只填表，不改代码 低 我把 8.2 那张表按真实取值集合完整列出，逐格标「现有行为 / 应有行为 / 未定义」，交给你审。看完你再决定要不要动代码。这一步没有回归风险。
填表 + 抽纯函数 + 单测 中 把决策抽成 resolveRevealAction() 并单测穷举，但四个触发点暂不改——先让新函数与现有行为并行运行、比对差异并上报。零行为变更，能拿到真实分歧数据。
完整显式化 高 四个触发点全部改为查表，删掉各自的局部条件。需要跑完整回归 + MT 矩阵 + 稳定性重复验证。
暂不处理 — 本文档留库。等下次需要改揭示逻辑时先读它。这是一个合理选择，不是拖延。
我的建议
选第一项。理由：这笔债的核心危害是「隐含假设无处陈述」，而填表直接消除这个危害—— 哪怕代码一行不动，下一个人读到表就不会再踩实例 1–4 那四种前提。 代码层面的显式化可以等到真正要改那块逻辑时再做，届时收益最大、边际成本最低。
