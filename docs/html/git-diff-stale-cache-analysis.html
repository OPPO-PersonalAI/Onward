Git Diff 缓存陈旧 & 打开慢 —— 根因分析与缓存策略选型

数据来源：用户诊断包（perf trace + 遥测 + 应用状态）+ 代码走读 + 对抗式复核 + 同类产品调研。缓存策略属于敏感改动，本文只做分析与方案对比，不含任何已落地的代码改动，等你拍板。 Sources: the user's diagnostic bundle (perf trace + telemetry + app state) + code walk-through + adversarial verification + peer research. Cache strategy is a sensitive change, so this document is analysis + options only — no code has been changed; awaiting your decision.

TL;DR

陈旧内容（症状 A）不是"缓存从不失效"，而是新鲜度授权只有一条链路且会漏：所有缓存层都只用路径做 key（不带 mtime/内容哈希），能自动失效的信号只有文件监听器（FS watcher → git-state-mirror → 失效）。这条链路一旦漏掉一次编辑（Windows EDR 下监听事件被丢弃/合并/worker 降级），30 分钟 TTL 的请求缓存就把上一次的快照当成命中返回，直到你手动强制刷新。
打开慢（症状 B）：这个仓库的 git status 本身就要 2.6 秒（中位）、最高 10.6 秒，所以设计上完全靠缓存来"显得快"——而这个缓存正是返回陈旧内容的那个。二者相互制约：粗暴地多失效 = 更多冷启动 = 更慢。

Stale content (symptom A) is not "the cache never invalidates" — it is a single, miss-prone freshness authority: every cache layer is keyed by path only (no mtime / content hash), and the only automatic invalidation signal is the FS watcher (FS watcher → git-state-mirror → invalidate). When that chain misses one edit (a watcher event dropped/coalesced, or degraded worker health under Windows EDR), the 30-minute-TTL request cache returns the previous snapshot as a hit until you manually force-refresh.
Slow open (symptom B): git status on this repo itself takes 2.6 s (median), up to 10.6 s, so the design leans entirely on caching to "feel fast" — and that cache is exactly what serves stale. The two are in direct tension: naively invalidating more = more cold opens = slower.

4 · 根因 / Root cause

根因（对抗式复核后的定论）/ Root cause (post-adversarial)

请求缓存（L1）以 30 分钟 TTL、仅路径 key 命中，而它唯一的亚-TTL 新鲜度授权（FS 监听 → mirror 失效链）没有为第二次编辑触发。打开路径故意用 force:false（GitDiffViewer.tsx:3216），且注释承诺的"下次打开自愈"实际已被移除（RC-2）。于是监听一漏，30 分钟内逐字返回旧快照。
注：代码走读最初把"陈旧层"指向渲染层内存早退（3599），被 trace 否定——trace 里没有 renderer-memory-hit，陈旧内容是经真实 IPC 由 main-content-cache 返回的。层级归属已修正为 L1 请求缓存 + L3 内容缓存。更宽的论断（仅路径 key + 单一会漏的授权 + 长 TTL）不变。

The request cache (L1) returns a hit under a 30-minute TTL on a path-only key, while its only sub-TTL freshness authority (FS watcher → mirror invalidate chain) never fired for the second edit. The open path deliberately uses force:false (GitDiffViewer.tsx:3216) and the "self-heal on next open" the comment promises was removed (RC-2). So when the watcher misses, the previous snapshot is returned verbatim for up to 30 minutes.
Note: the code walk-through first blamed the renderer-memory early-return (3599); the trace refuted it — there are no renderer-memory-hit events, and the stale content came via a real IPC served by main-content-cache. The layer attribution was corrected to L1 request cache + L3 content cache. The broader thesis (path-only keys + a single miss-prone authority + long TTL) stands.

为什么"第一次对、后面错"：干净→改动会改变 git status 的文本输出（一个不会漏的粗信号），所以第一次能刷新；但同一状态下的再次编辑（都是 "modified/unstaged"）只能靠 mtime 指纹这个脆弱信号——它一漏，就一直陈旧。

Why "first view right, later views wrong": clean→modified changes the git status text (a coarse, unmissable signal), so the first view refreshes; but a subsequent same-status re-edit (still "modified/unstaged") relies solely on the fragile mtime fingerprint — miss it once and it stays stale.

5.1 新鲜度 vs 延迟：核心矛盾 / The freshness-vs-latency tension

为什么不能"简单粗暴地多失效" / Why "just invalidate more" is wrong

因为 status 是秒级，设计上靠缓存 + 预热来"显得快"。任何"每次事件就整片清缓存 / 缩短 TTL / 每次打开强刷"的做法，都会把下一次打开从微秒级命中变成秒级冷启动（cat-file 进程）——这正是当初 RC-2 的由来。所以正确方向是精准失效（只失效真正变了的那一项），而不是把失效做粗。

Because status is O(seconds), the design leans on cache + prewarm to feel fast. Any "wipe the whole cache on every event / shorten the TTL / force on every open" turns the next open from a microsecond hit into a second-scale cold recompute (cat-file spawns) — which is exactly what caused RC-2. So the correct direction is surgical invalidation (evict only the entry that actually changed), not blunter invalidation.

同类共识 / Peer consensus

工作区那一侧永远按需/按 mtime 校验，绝不放进"仅路径 + 长 TTL"的缓存里靠一个可能漏的监听事件来保新鲜。不可变的 git 对象（oid 寻址）才可以长缓存。

The working-tree side is always validated on read (by mtime) or re-read on demand — never parked in a "path-only + long-TTL" cache whose freshness hinges on a watcher event that can be missed. Only immutable git objects (oid-addressed) may be cached long.

7 · 建议策略 / Proposed strategy

推荐 / Recommended · 读时 stat 校验 + 按 ref 可变性分级

保留现有的快速路径命中，但在每次命中"工作区侧"时做一次极廉价的 fs.stat（mtime+size），与缓存条目里存的戳比对：一致才用缓存，不一致就只重取这一项。"原始(git)侧"用 HEAD/index 的 oid 做 key、可以长缓存（仅在 index/HEAD 移动时失效）。这样监听器降级为"预热/加速"的手段，而不再是唯一的正确性来源。

Keep the fast path-keyed lookup, but on every hit for the working-tree side do one very cheap fs.stat (mtime+size) and compare it to a stamp stored on the cache entry: serve cached only if the stamp matches, otherwise re-fetch just that entry. The "original (git)" side is keyed by the HEAD/index oid and may stay cached long (invalidated only on an index/HEAD move). This demotes the watcher to a prewarm/latency optimization instead of the sole correctness authority.

为什么能修好陈旧Why it fixes staleness

fs.stat 直接问磁盘真相，不依赖监听器。监听漏了也没关系——下次打开一 stat 就发现文件变了，强制重取。确定性地关掉陈旧窗口。

fs.stat asks disk ground-truth, independent of the watcher. Even if the watcher missed the event, the next open stats the file, sees it changed, and re-fetches. Deterministically closes the stale window.

为什么不拖慢打开Why it doesn't slow opens

fs.stat 是微秒级、不创建进程（不吃 EDR 进程税）。文件没变 → 照样瞬时命中，预热缓存原样保留，不会重演 RC-2。只有真的变了才付一次重取。

fs.stat is microseconds and spawns no process (no EDR tax). Unchanged file → still an instant hit, prewarm cache preserved, no RC-2 regression. Only a genuinely changed file pays one re-fetch.

互补项（非本次决策）/ Complementary (not this decision)

为什么第二次编辑的监听事件会漏？值得单独查（原子保存的临时文件过滤、rename 识别、EDR 下 worker 健康/reconcile 退避）。但按稳健设计原则，监听器不该是唯一的正确性来源——所以无论监听多可靠，A 的 stat 兜底都应该做。症状 B（打开慢）大部分是这个仓库 status 本身秒级 + EDR 进程税的固有成本；A 不会让它变差，但要显著提速是另一件更大的工作，可另行评估。

Why did edit #2's watcher event get missed? Worth a separate look (atomic-save temp-file filtering, rename detection, EDR worker health / reconcile backoff). But by robust-design principle the watcher should not be the sole correctness authority — so regardless of watcher reliability, A's stat backstop should exist.
