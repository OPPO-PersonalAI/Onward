GDS-07 永久陈旧缓存 — 根因与修复决策

git-diff 预热 status 复用缺少"失效代际门"导致的持久 staleness · 2026-07-11

1. 摘要

缺陷（与本次三分支合并无关，master 基线 faec049 上可复现）： 对同一仓库执行「强制 diff → 约 50ms 后外部写文件 → 非强制读 diff」时，非强制读取会永久 返回写文件之前的陈旧结果——在 90 秒的轮询窗口内 3/3 次迭代均不收敛（ageMs 单调增长到 90s）。

失效链本身工作正常（save 的 manual 失效正确触发、请求缓存有代际栅栏）。问题出在 失效触发的"重预热"步骤复用了失效之前捕获的预热 status（15 秒年龄门内）， 用变更前的数据把刚清空的缓存重新填满；父仓库此时无 mirror 订阅、不会再有第二次失效，陈旧状态从此固化。

2. 证据链（trace 时间线，perf-0009）

时刻事件含义
2315msdiff.cache-invalidate {reason:manual} + snapshot.invalidatesave 的失效正确触发，各缓存被清空 正常
2381mswatcher-fire {kind:update, src/main.txt}watcher 看到了 save 的磁盘写入 正常
2390msdiff.warm-status-reuse {ageMs: 2016}重算复用了约 2 秒前（save 之前）捕获的预热 status 毒化点
2401ms≈（请求缓存条目出生）用陈旧 status 组装的 diff 写回缓存，代际栅栏无法拦截（栅栏只护请求缓存本身，不护其输入）
2506ms → 90s+diff.cache-hit ageMs 105 → 29 000+此后零失效、零 mirror 增量，轮询永远命中同一条目 永久陈旧
归因排除（A/B 实验）：7 月 8 日 master（422a73e 及更早）3 次全量 PASS；7 月 10 日 keep worktree（faec049+keep）FAIL；7 月 11 日合并树 4/4 FAIL；纯 faec049 的 release-candidate worktree 同签名 FAIL。faec049 只改测试基建 → 缺陷为预热复用机制（G2 C-i，7 月 5-6 日引入） 的潜伏窗口在本机当前时序下被 GDS-07 的 50ms 偏移稳定命中。三个合并分支全部无关。

3. 根因：当前策略

外部写文件（GIT_SAVE_FILE_CONTENT）成功
↓ 主进程 invalidateGitDiffAfterKnownMutation
失效总线：请求缓存 key 删除 + 代际++ / 单仓库缓存清空 / 快照丢弃（主进程与 worker 两份副本都到位）
↓ repoPrewarmCoordinator.onCwdInvalidated（静默窗口重预热）
worker warmDiffCache：携带 mirror 上一次（save 之前）的 presupplied status
getSingleRepoDiff 复用门：只查年龄 ≤ 15s（git-utils.ts:1972），不知道"这份 status 早于最近一次失效"
↓
陈旧 diff 写回请求缓存（store 时代际未再变 → 栅栏放行）→ 无订阅 → 无后续失效 → 永久陈旧

复用门代码注释（G2 C-i）声称"捕获之后的任何变更都会 watcher → invalidate → re-warm，不牺牲正确性"—— 漏判了re-warm 本身就是那次 invalidate 触发的、而它拿到的 status 恰在变更之前捕获这一自指情形。

4. 提议修复：失效代际门（方案 A，推荐）

在 git-utils.ts 增加每实例注册表：lastDiffInvalidateAtByProject: Map<string, number>（FIFO 上限 64）
↓ invalidateGitDiffCache(cwd) 内（主进程与 worker 各自实例都会执行）
lastDiffInvalidateAtByProject.set(normalized, Date.now())
↓ getSingleRepoDiff 复用门（git-utils.ts:1972）
复用条件从「ageMs ≤ 15s」收紧为「ageMs ≤ 15s 且 presupplied.capturedAt > lastInvalidateAt(repoRoot)」； 不满足则走既有 fallback：现场 spawn git status，并以 result:'invalidated' 记入既有 trace 事件
// getSingleRepoDiff reuse gate (git-utils.ts)
const invalidatedAt = lastDiffInvalidateAtByProject.get(normalizedRoot) ?? 0
if (ageMs >= 0 && ageMs <= WARM_STATUS_REUSE_MAX_AGE_MS && presupplied.capturedAt > invalidatedAt) {
  parsedFiles = presupplied.files   // reuse（原路径）
} else {
  // fallthrough：现场 git status（原路径），trace result: 'stale' | 'invalidated'
}

顺序保证：main 的失效转发（一次性控制信封）先于重预热请求进入 worker 消息队列，worker 顺序处理 → 门先更新、重预热后到达，竞态封死。时钟为同机 Date.now()，跨进程可比。

5. 权衡清单

维度方案 A：失效代际门（推荐）方案 B：只改测试（GDS-06/07 退役/改契约）方案 C：失效时直接丢弃预热 status
正确性封死"重预热吃到变更前 status"整类；外部编辑无订阅时的既有语义不变（由 GDS-08/09 契约覆盖）产品缺陷保留：任何"已知变更后的重预热"仍可能固化陈旧缓存（潜伏足枪）同 A（等效封死）
性能仅在"status 早于最近失效"时多付一次本就该付的 git status；预热收益全保留零开销略差于 A：mirror 稍后送来的新 status 也被丢弃，重预热必然 spawn
侵入面1 个 Map + 2 处小改（同一文件），不动订阅/mirror 权威设计（P1-1 结构保持）只动测试文件需在 coordinator/worker 间传递"由失效触发"的标记，链路更长
风险低：门只会"更保守地放弃复用"，失败方向安全无代码风险，但测试网撤除中：改动跨 coordinator 协议

6. 验证计划（方案 A）

① 单测（配对交付）：新增 test/unittest/git-diff-warm-status-invalidation-gate.test.mts，锁复用门决策表（新鲜+未失效→复用；新鲜+已失效→拒绝；过龄→拒绝；无记录→复用）。纯函数化提取门判定以便 Node 直测。

② autotest：已加固的 GDS-06/07（非强制轮询 + 自适应上限）就是端到端锁——修复后应在首个轮询周期内收敛。--repeat 3 证稳定。

③ 全量回归 --build 全绿收口。

④ trace 事件复用既有 MAIN_GIT_DIFF_WARM_STATUS_REUSE，新增 result:'invalidated' 取值并更新 infra/trace.md 行说明——无新事件名注册。
