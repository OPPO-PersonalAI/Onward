同一个 Windows 仓库路径，在“规范化之前”被当成两个目标

The same physical Windows repository is treated as two invalidation targets because raw strings are deduplicated before path normalization.

建议只调整 GitStateMirrorRouter 的目标生成顺序：先用已有的路径解析规则统一 D:\repo 与 D:/repo，再建立 Set。不改变 cache scope、TTL、mirror debounce、刷新优先级或 watcher authority。

现状：2 次 force reload 目标：1 次 authoritative reconcile 策略项：invalidation fan-out 跨平台：Windows / macOS / Linux

关键链路

  • msg.cwd = D:\...\repo：router 的 realpathSync 产物。
  • msg.state.repoRoot = D:/.../repo：worker 的 Git root 规范为正斜杠。

3. 当前策略 Current strategy

问题不在缓存失效粒度。 file-scoped invalidation 已经正确；重复发生在 mirror update 的 fan-out 目标去重顺序。

4. 建议策略 Proposed strategy

const targets = normaliseGitDiffInvalidationTargets([
  msg.cwd,
  msg.state.repoRoot
])
for (const target of targets) gitDiffCacheInvalidator.invalidate(target, 'mirror')

5. 方案权衡 Trade-offs

方案正确性风险结论
A · router 先规范化，再去重
Normalize before dedupe		router 调用可由 Node unit test 验证的纯函数；只合并等价路径，保留真实不同目标低；纯身份修正，不改变时间或缓存策略建议
B · invalidator 加时间窗口去重
Temporal debounce		可能把两次真实 mirror update 合并高；引入时间语义、TTL 与新鲜度风险不建议
C · renderer 丢弃 queued force load
Drop queued reload		可能漏掉首轮读取后到达的新变化高；改变并发与 freshness authority不建议
明确不改：invalidation scope、缓存层次、TTL、eviction、prewarm、mirror debounce、load queue、线程模型。
