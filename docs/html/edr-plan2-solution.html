这台 Windows 主机受企业 EDR（终端检测与响应）防护，每一次进程创建（git.exe、conpty、rg.exe、electron）都被同步的按需扫描征收 1.3–12.9 秒 的"税"。当全量回归跑到几十个套件之后，累积的进程税让那些"写一次值、读一次值、立刻断言"的定时逻辑在某一次抖动里读到尚未就绪的中间态——于是每一轮挂的套件都不一样（shifting failure set），三次连续全绿始终无法达成。 This Windows host runs under corporate EDR. Every process spawn (git.exe, conpty, rg.exe, electron) is taxed 1.3–12.9 s by a synchronous on-access scan. After dozens of suites in a full regression, the accumulated tax makes any test that "writes a value, reads it once, asserts immediately" observe a not-yet-settled intermediate state on some jittery run — so a different set of suites fails every run (the shifting failure set), and three consecutive green runs never landed.

结论Bottom line
这不是几十个独立 bug，而是同一个元缺陷换了不同马甲。把它拆成 6 个竞态子类，每个都用"轮询真实最终状态、而不是读过期/过早/代位快照"修复；外加 2 个 Windows 环境固化。最终全量回归 连续三次 81 PASS / 0 FAIL。 This was never dozens of independent bugs — it was one meta-bug wearing six costumes. Each was fixed by polling the deterministic outcome instead of a stale/early/proxy snapshot, plus two Windows environment-hardening fixes. Result: three consecutive 81 PASS / 0 FAIL full regressions.

3 · 核心原则3 · Core Principle

✗ 反模式Anti-pattern
// write, then sleep a fixed window, then read ONCE
await saveFile(...)
await sleep(200)
const v = await read()
assert(v.ok)   // flakes when 200ms < EDR window
✓ 方案2Plan 2
// poll the GROUND TRUTH until it settles
await saveFile(...)
await waitFor(() => read().hasChange,
            adaptiveBudget())
assert(...) // returns instantly when healthy

两条铁律Two rules

① 轮询真值，不读快照。等待条件必须编码"真正就绪的最终状态"，而不是一个空列表也能满足的代位信号；轮询在健康主机上命中即返回，因此宽容的上限永远不拖慢正常运行。 Poll ground truth, not a snapshot. A wait predicate must encode the genuinely-settled state, not a proxy an empty list also satisfies. A poll short-circuits on success, so a generous ceiling never slows a healthy run.

② 分离正确性与性能。正确性门禁（用宽松的"挂起检测"上限轮询结果）；性能测量但不门禁（或用 N=3、≥1/3 达标的聚合）。在 EDR 主机上，单样本的毫秒级延迟是无法作为硬门禁的。 Separate correctness from performance. Correctness gates (poll the outcome with a generous hang-detector ceiling); performance is measured, not gated (or aggregated as N=3, pass-if-≥1-of-3). A single-sample millisecond latency cannot be a hard gate on an EDR host.

4.1 延迟当门禁 → 门禁判正确、延迟只测量4.1 Latency-as-gate → gate correctness, measure latency

把延迟比较当成断言的 ok 布尔，是 EDR 下最常见的假失败源。修法因 case 而异： Using a latency comparison as an assertion's ok boolean is the #1 false-failure source under EDR. The fix varies by case:

XP-13/14git 调用 median < 阈值median < threshold门禁 allSucceeded；延迟 latencyGates:falsegate allSucceeded; latency non-gating
SD-03暖/冷比值 ≤ ×1.5warm/cold ratio ≤ ×1.5门禁 loaded && fileCount>0；比值单列非门禁gate loaded && fileCount>0; ratio non-gating
DSM-02/RSM-02shell 延迟 < 阈值shell latency < threshold单样本非门禁；正确性由 shell-visible 门禁non-gating single sample; correctness via shell-visible
TP-03 / TP-01单批 p95 / 均值 < 预算single-batch p95 / avg < budget保留门禁，改 N=3、≥1/3 达标即过stays gated, now N=3 pass-if-≥1-of-3
为什么 TP 保留门禁？输入响应延迟是产品最高优先级信号（CLAUDE.md），不能丢。但单批是一次"随机过程的观测"，一次被调度饿死的按键就击穿预算。N=3、≥1/3 达标在健康主机首批即过（零额外耗时），又能在 3/3 全超时真正失败（系统性回归而非瞬时尖峰）。 Why keep TP gated? Input latency is the highest-priority product signal (CLAUDE.md) and must not be dropped. But a single batch is one observation of a stochastic process; one scheduler-starved keystroke blows the budget. N=3 pass-if-≥1 passes on the first batch on a healthy host (zero extra cost) yet still fails 3-of-3-over-budget (a systematic regression, not a transient spike).

4.2 空列表瞬态：把"仓库存在"折进等待条件4.2 Empty-while-not-loading: fold repo-presence into the wait

最隐蔽的一类。!isSubmodulesLoading() 在仓库列表瞬时为空时也成立——没东西自然没在加载。旧代码"等 !loading，再断言 repos"，于是在那个空窗里读到 repoCount: 0。 The subtlest one. !isSubmodulesLoading() is also true while the repo list is momentarily empty — nothing present ⇒ nothing loading. The old split (wait on !loading, then assert on repos) caught that empty window and read repoCount: 0.

✗ Before (DSM-04)
await waitFor(() =>
  api.isOpen() && !api.isSubmodulesLoading())
const repos = api.getRepoList()  // transiently []
_assert(repos.length > 1 && ...)  // FAIL: 0
✓ After
await waitFor(() => {
  if (!api.isOpen() || api.isSubmodulesLoading()) return false
  const r = api.getRepoList()
  return r.length > 1 && r.some(isSub) && r.every(notLoading)
})  // waits THROUGH the empty transient

真正塌成空的最终态仍会超时失败——所以这不是"放宽"，而是把模糊的代位信号换成确定的真值。 A genuinely-collapsed final state still fails by timeout — so this is not "loosening," it is replacing an ambiguous proxy with the deterministic truth.

4.3 写入→可见竞态：轮询 callDiff 直到变更出现4.3 Write→visible race: poll callDiff until the change appears

GDS-13 写父文件后固定 sleep(200) 再取一次 diff。EDR 下"写入→git 可见→diff 加载"窗口 > 200ms，于是拿到空 diff（reposCount: 0）。改为轮询 callDiff(force) 直到父文件变更出现，再在已就绪的 diff 上断言那些"否定项"（不应出现幽灵子模块）。 GDS-13 wrote the parent file then took one diff after a fixed sleep(200). Under EDR the write→git-visible→diff-loaded window exceeds 200ms, yielding an empty diff (reposCount: 0). Now it polls callDiff(force) until the parent change is visible, then asserts the negatives (no phantom submodule) on the settled diff.

4.4 模型滞后于内容：轮询幂等的 setter4.4 Model-lags-content: poll the idempotent setter

GDS-33 中，选中文件的内容文本已就绪，但解析出的行选择模型（供 setSelectedLineRangeForTest 索引）由更晚的一次提交携带，EDR 下滞后 → 单次调用返回 false。改为把这个幂等调用放进 waitFor 轮询直到提交成功。 In GDS-33 the selected file's content text was ready, but the parsed line-selection model that setSelectedLineRangeForTest indexes into is carried by a later commit and lags under EDR → a single-shot call returned false. Now the idempotent call is polled inside waitFor until it commits.

4.5 列表抖动 / 车道饿死：轮询 + 重投递4.5 List-churn / starvation: poll + re-drive

图像 diff 套件最脆弱（预览取数走并发为 1 的 worker 车道）。两处修复： The image-diff suite is the most fragile (preview fetch goes through a concurrency-1 worker lane). Two fixes:

  • ID-12：findFileIndex 单次读到 -1（前一文件的重载让列表瞬时空窗）→ 改轮询直到文件出现。 ID-12: single-shot findFileIndex read -1 (a prior file's reload left the list mid-refresh) → poll until the file appears.
  • ID-04：预览取数被峰值 EDR 饿死超过 30s 预算 → 超时后重投递一次（把选择切走再切回，强制发起新请求），而不是死等一个可能被丢弃的请求。 ID-04: the preview fetch starved past its 30s budget under peak EDR → re-drive once on timeout (toggle selection away and back to force a fresh request) instead of waiting on a possibly-dropped one.

4.6 重夹具 cwd 预算4.6 Heavy-fixture cwd budget

GHMS-04 的终端 B 要跑 git init + 3 次 commit 才进入夹具目录。每次 commit 都被 EDR 重税，默认 12s 的 cwd 等待远远不够 → 给 90s（命中即返回，健康主机零代价）。 GHMS-04's terminal B runs git init + 3 commits before landing in the fixture dir. Each commit is heavily EDR-taxed, so the default 12s cwd wait is far too tight → 90s (returns the instant cwd settles, zero cost when healthy).

5 · 两个环境固化（跨机器持久）5 · Two Env-Hardening Fixes (durable across machines)

5.1 Windows EPERM：rename-aside 兜底5.1 Windows EPERM: rename-aside fallback

三个 GDS 子运行器共用一个 runtime/ 夹具目录。前一个运行器残留的 EDR/git 句柄会把目录占住，超过 robustRmSync 的 10 次 / 5.5s 重试窗口 → 下一次建夹具时 EPERM 删不掉。 Three GDS sub-runners share one runtime/ fixture dir. A prior runner's lingering EDR/git handle holds it open past robustRmSync's 10×/5.5s retry window → the next fixture build can't delete it (EPERM).

关键洞察：Windows 上你通常无法删除一个含被锁子文件的目录，但在 NTFS 上你可以改名它（目录项重命名，被锁句柄继续指向被改名的 inode）。于是把锁住的目录改名挪开，腾出干净路径让本次构建继续；残壳下次运行 best-effort 清扫，/runtime.stale-*/ 已加入 gitignore。 Key insight: on Windows you usually cannot delete a directory with a locked child, but on NTFS you can rename it (a directory-entry rename; the locked handles keep pointing at the renamed inode). So rename the locked dir aside to free the canonical path for a fresh build; the husk is swept best-effort next run, and /runtime.stale-*/ is gitignored.

5.2 Windows shell 引号保留：平台感知的命令构造5.2 Windows shell quote-retention: platform-aware command building

pdf-epub 套件用裸 POSIX 习语 printf '%s' '…' > '${NAME}' 创建标记文件。在非 bash 的 Windows shell 下，重定向目标外层的单引号不被剥离，于是磁盘上真的生成了一个名字带引号的文件 '__autotest_pdf_epub_marker.txt'——它绕过了所有以 __autotest_ 前缀匹配的清扫逻辑，永久泄漏进工作树，而每次清扫都报告"干净"。 The pdf-epub suite created its marker via a raw POSIX idiom printf '%s' '…' > '${NAME}'. Under a non-bash Windows shell the single quotes around the redirect target are not stripped, so a file literally named '__autotest_pdf_epub_marker.txt' (quotes in the name) is created — it evades every __autotest_-prefix sweep and leaks permanently into the working tree while each sweep reports "clean."

修法：与已有的 copy/delete 构造器一致，改用平台感知的 platformBuildWriteMarkerCommand（win32 显式调用 powershell -Command "Set-Content -LiteralPath …"）。教训：任何发往自动化测试终端的夹具命令，都必须按平台显式构造、显式指定 shell，绝不能假设终端默认 shell 会剥离 POSIX 引号。 Fix: a platform-aware platformBuildWriteMarkerCommand (win32 explicitly invokes powershell -Command "Set-Content -LiteralPath …"), matching the existing copy/delete builders. Lesson: any fixture command sent to the autotest terminal must be built per-platform with an explicit shell; never assume the terminal's default shell strips POSIX quotes.
