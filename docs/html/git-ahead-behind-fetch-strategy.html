Terminal Git 徽章 — ahead/behind + 后台 fetch 策略设计

分支 20260715-git-stats-ahead-behind · 版本 2.0.1 · 基线 commit 9df2b3b · 状态:已确认(待实现)

已定方向: ① ahead / behind 都用「箭头方向 + 数字」表达(↑N / ↓M);② ahead 时圆点用亮草绿 #4ADE80;③ 引入 App 首个网络操作 —— 后台 git fetch 让 behind 变准。本文档只解决"怎么 fetch"这层策略,拿到你确认后再动代码。

① 背景与现状架构

当前每个 Task 终端格子上有一个 Git 徽章(彩色圆点 + 分支名)。状态只有 6 种(clean/added/deleted/modified/mixed/unknown),全部由 GitStateMirror 子系统在一个 worker 线程里跑本地 git status 算出来,全程无任何网络操作。

关键:--branch 参数现在就已经在请求,输出里已含 # branch.ab +A -B(领先 A / 落后 B),只是解析器把这行丢弃了。所以 ahead 解析出来零成本、无需新进程、无需网络。

② 核心机制回顾:为什么 behind 必须 fetch

维度ahead(领先)behind(落后)
定义本地有、本地记录的 origin/xxx 没有的提交本地记录的 origin/xxx 有、本地 HEAD 没有的提交
数据来源都来自本地 refs/remotes/origin/xxx(上次 fetch 写下的快照),不是实时问远端
准确度永远准(只依赖本地提交)只和"上次 fetch"一样新;不 fetch → 别人 push 后仍显示 ↓0
成本零 · 读已有输出需 git fetch · 网络

对标:VS Code / GitKraken / JetBrains / Fork 全部如此 —— ahead 免费,behind 靠后台 fetch 刷新本地 remote 引用。这不是工具局限,是 Git 模型本身。

③ 提议架构:fetch 独立成链,绝不阻塞本地 status

核心原则:fetch 是慢的网络操作(秒级),本地 status 是快的(毫秒级),两者必须解耦。新增一个独立的 fetch 调度器(主进程),它只负责按周期发起 git fetch;fetch 成功后触发一次现有的 status 重算,让 # branch.ab 的 behind 数刷新,再沿现有 IPC 链路更新徽章。fetch 本身永不进入那条快的 status worker 路径。

fetch 命令硬化(防卡死 / 防弹窗)—— 实现细节,已按最佳实践定

# 只更新 remote 追踪引用,不动工作区/本地分支;非交互,失败快速返回
GIT_TERMINAL_PROMPT=0 # 禁止 https 凭证交互提示
GIT_OPTIONAL_LOCKS=0 # 不抢锁,避免和用户命令竞争
GIT_SSH_COMMAND="ssh -o BatchMode=yes -o ConnectTimeout=10" # SSH 无密码则快速失败,不静默卡死
git fetch --no-write-fetch-head --prune=false <remote> <当前分支的 upstream>
# 外层再套一个硬超时(如 20s),超时 kill 子进程

这几项直接消除了对标调研里最严重的两个坑:私有仓凭证弹窗、SSH 带密钥静默卡死。失败一律快速返回、静默重试,不打扰用户。

④ 策略参数(需要你拍板的部分)

下面每一项都标了我的建议默认值(建议),稍后用选择题逐项确认。

4.1 fetch 周期 —— 多久 fetch 一次。
对标:VS Code 3min、GitKraken 1min、JetBrains/Fork 20min。你之前提到 5~10 分钟。
建议 10 分钟 —— 本 App 可能同时开多个 Task/多仓,周期长一点降低总开销;behind 有 10 分钟延迟对"是否落后"这种信息完全够用。
4.2 fetch 范围 —— 给哪些仓库 fetch。
建议:按"唯一仓库"去重后全部 fetch;App 窗口隐藏/最小化时暂停;无 upstream 的分支跳过。
多个 Task 指向同一个仓库只 fetch 一次;App 不在前台时不 fetch(省电省网,回到前台立即补一次)。备选:只 fetch 当前聚焦 Task 的仓库(更省但其他徽章 behind 会滞后)。
4.3 默认开 / 关 + 开关位置 —— 对标里 VS Code 默认关(因为怕弹窗),但我们已把 fetch 硬化成"绝不弹窗、绝不卡死"。
建议:默认开;同时给一个环境变量 kill switch ONWARD_DISABLE_GIT_AUTOFETCH=1。
因为 fetch 已经不可能弹窗/卡死,默认开是安全的。是否还要在设置界面加可视开关(需配 en+zh-CN 双语文案)是可选项。
4.4 失败退避 —— 某仓 fetch 失败(网络断/无凭证)后怎么办。
建议:单仓指数退避,从 10min 起翻倍,封顶 1 小时;成功后复位。
避免对一个连不上的私有仓每 10 分钟白试一次。该仓 behind 显示为"未知"(见视觉表)。

⑤ 徽章视觉状态表(圆点颜色 + 箭头)

已定:ahead/behind 都用箭头+数字(↑N 绿 / ↓M 蓝),ahead 时圆点亮草绿 #4ADE80。下表把所有组合列全,其中 behind-only / diverged 的圆点颜色需要你确认(4.5)。

clean仅 behindemeraldmain ↓1远端领先,本地无改动 → 圆点保持 emerald,方向交给 ↓ 箭头

4.5 已确认 —— 圆点语义:「绿点 = 你有本地提交要 push」(与 GitLens 一致):只要 ahead>0 且 clean 就用亮草绿,behind 完全交给 ↓ 箭头;behind-only 时圆点保持 emerald;diverged(都>0)因为也 ahead 所以是绿点 + ↑↓ 双箭头。

⑥ 权衡与风险(对标数据)

风险说明我们的缓解
凭证弹窗私有仓后台 fetch 会弹凭证框(VS Code 官方 FAQ 记录)GIT_TERMINAL_PROMPT=0 → 直接失败,不弹
SSH 静默卡死带密码的 key 没加载会挂起、像假死BatchMode=yes + ConnectTimeout → 快速失败
多仓开销多仓 × 短周期 = 网络/进程压力大去重 + 10min 周期 + 隐藏暂停 + 失败退避
网络失败fetch 只碰 remote 引用和 FETCH_HEAD,不动工作区失败静默吞掉、退避重试,安全
锁竞争和用户手动 git 命令抢 .git 锁GIT_OPTIONAL_LOCKS=0 + 只读 fetch

⑦ 诊断埋点(按项目硬性规则)

fetch 链路的每个控制流拐点都要能在用户上报的 trace 里看到。计划新增事件(先注册进 src/utils/perf-trace-names.ts,再埋点,再更新 infra/trace.md):

  • main:git-autofetch.scheduled —— 某仓被排入本轮 fetch
  • main:git-autofetch.started / .succeeded(span,带耗时)/ .failed(带原因分类:auth / network / timeout)
  • main:git-autofetch.backoff —— 某仓进入退避,带下次间隔
  • main:git-autofetch.skipped-hidden —— App 隐藏跳过本轮
  • main:git-autofetch.triggered-recompute —— fetch 成功后触发 status 重算
  • worker:git-state-mirror.branch-ab-parsed —— 解析出 ahead/behind(instant)
