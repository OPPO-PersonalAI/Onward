GPU 崩溃正面解决方案 — 设计说明

终端花屏 / 白屏(ANGLE-Metal GPU 进程崩溃)的根因、四层修复架构、三层测试证明与舰队遥测闭环

1 · 方案总览

本方案的目标不是"缓解花屏",而是正面消除 GPU 进程崩溃这一根源,并用可复现实验证明消除有效。设计分四层防线 + 三层证明 + 一条遥测闭环:

防线四层修复

  • 消除源头:Electron 43.2.0 升级(带走 ANGLE-Metal 缺陷)
  • 崩溃自愈:两阶段恢复(共享图集重建)+ N=2 会话熔断
  • 退出安全:watcher 原生操作记账 + 静默屏障
  • 链路容错:退出清理链逐步容错,单点异常不再截断

证明三层测试

  • 崩溃门禁:全量回归零 .ips / 零退出超时才算过
  • 真杀恢复:SIGKILL 真实 GPU 进程,验证恢复与熔断
  • 配方浸泡:按事故日志测得的配方高强度复现压测
最终验证状态(2026-07-24):103 个 runner 全量回归 — 101 过 / 1 跳过 / 1 无关偶发(standalone 2/2 过);整轮零崩溃证据、零退出超时。39 vs 43 A/B 浸泡对照进行中。

1.1 问题与症状

生产版本 v2.1.0-daily.20260722.1(Electron 39.8.5,macOS arm64)上,用户在升级后 + 应用从后台不可见拉回前台时高概率出现:终端内容花屏或整块变黑(文本仍可选中,说明 DOM 活着、WebGL 纹理死了),切换 tab 无法恢复,必须重启。三份诊断包(两台机器)+ 一次活体复现均指向同一条链:GPU 进程在"隐藏→可见"翻转瞬间崩溃,而共享字形图集在崩溃后持有脏引用,导致渲染永不自愈(BUG-0003)。

2 · 根因链

occlusion 翻转隐藏 ≥17.6s 后唤醒
→
渲染管线重配eglReleaseTexImage
→
ANGLE-Metal 缺陷mPendingSignalEvents 含 nil
→
NSArray insert 抛出mtl_command_buffer.mm:1158
→
GPU 进程崩溃白屏/花屏
  • 崩溃点:CommandEncoder::reset 向 NSMutableArray 插入 nil(mtl_command_buffer.mm:1158),经 eglReleaseTexImage → IOSurfaceImageBacking EndAccess 到达;
  • 缺陷由 2026-04-08 的 Electron 35.7.5 → 39.8.5 升级(提交 532fe49)引入;上游 electron#49904 已关闭(Completed),修复进入更高版本;
  • 放大器(BUG-0002):不可见窗口卡死 + watchdog 在不可见窗口上误触发(electron#50250 佐证),已在 f84b481 修复;
  • 崩溃后果(BUG-0003):共享字形图集脏引用 → 切 tab 也无法自愈 → 两阶段恢复修复。

3 · 修复架构(四层)

3.1 第一层:Electron 43.2.0 升级(消除源头)

  • ANGLE-Metal 的 nil-insert 缺陷在 Chromium 上游已修,43.2.0 携带修复;
  • 升级适配:node-abi 4.33.0 override、better-sqlite3 13.0.1、Electron 二进制下载分支;
  • Chromium 150 行为变化逐一处理:occlusion 检测默认启用(autotest 窗口保持不被遮挡)、CDP Target.getTargets 需要 filter、iframe 脱离/重挂时滚动位置重置。
红线约束:43 升级在 watcher 退出崩溃被证明修复(零崩溃全量回归)之前不得提交 —— 该证明已于 2026-07-24 达成(§4.4)。

3.2 第二层:两阶段恢复 + N=2 会话熔断(崩溃自愈)

GPU 进程 gonechild-process-gone
→
阶段一:全部 dispose图集 owner 归零 → 脏缓存驱逐
→
阶段二:全部重建首个 ensure 分配全新图集
→
渲染恢复
  • 旧实现按会话"边 dispose 边重建",共享图集始终有 ≥1 个 owner,脏图集永远存活 —— 两阶段化是 BUG-0003 的根修;
  • 页面不可见时崩溃 → 恢复推迟到可见(pendingGpuCrashRecovery),避免在 hidden 状态下做无效 WebGL 工作;
  • N=2 熔断:同一会话第二次 GPU 崩溃后,永久切换 DOM 渲染器(sticky fallback)+ TabBar 横幅提示 —— 降级但绝不再花屏;Chromium 自身 ~3 次崩溃后也会降软件光栅,熔断先于它到达稳定态。

3.3 第三层:watcher 退出崩溃修复(退出安全)

用户报告的第二类崩溃:退出时 @parcel/watcher 的 napi_fatal_error(worker_threads 环境销毁时 uv 工作落入已死环境)。2.6.0 升级不能修复(UUID 实证)。修复为结构性三件套:

  • 原生操作记账收口:所有 subscribe/unsubscribe 经 trackNativeWatcherOp(调用时记账)/runGatedNativeWatcherOp(关停闸门 + 拒绝痕迹)进入 pendingNativeWatcherOps 集合 —— 在途 subscribe 对屏障不可见的缺口被关闭;
  • 静默屏障扩展:awaitWatcherQuiescenceWithSettle — 屏障 + 沉降 + 复验循环,总时限有界(2×deadline + 2×settle);
  • 兜住未捕获异常:worker 侧 drainThenExit(10 s 封顶后 process.exit(1)),异常路径也先排干再退。

3.4 第四层:退出链容错(2026-07-24 由门禁逼出)

门禁第一天就付了自己的成本:hard-floor 检测抓到 3 个套件退出悬置 20 s,追查发现 RipgrepSearchManager.dispose() 在"有过搜索的会话"退出时同步抛异常,把 cleanupIpcHandlers 拦腰截断 —— GitStateMirror drain 在这条路径上数周从未执行(昨日日志证实异常早已发生,只是无人可见)。这几乎确定就是用户所贴 watcher SIGABRT 的暴露路径。
  • ripgrep dispose() 幂等化、不再抛(terminate 本身已取消一切,dispose 不再绕道 cancel→request);
  • request() 同步异常改为 rejected promise,.catch() 真正能接住;
  • 清理链逐步容错(safeDispose):任何子系统 dispose 异常 → 记录 main:app.quit-cleanup-step-failed 事件并继续,永不再跳过 watcher drain。

5 · 遥测设计(PostHog 舰队观测)

目标:升级发布后,无需用户回报即可在全网数据里回答 —— 崩溃率是否下降、恢复是否有效、熔断是否在触发、哪个版本最健康。

事件触发点关键属性通道
error/gpuProcessCrash 主进程 child-process-gone(type=GPU) reason、exitCode、msSinceLastWindowShow / Focus / ThrottleToggle / Nudge(把每起崩溃分类为 wake-crash / throttle-crash / organic) Tier-2 live
error/gpuCrashRecovery 渲染器恢复各出口(模拟崩溃一律不上报) outcome ∈ recreated / partial / failed / deferred / sticky-fallback(枚举钳制),crashCount、sessionCount、failedCount、durationMs Tier-2 live
session/end 增强 会话结束 gpuCrashCount、rendererCrashCount(会话累计,crashFree 推导保留) Tier-2 live
error/recovered(既有) WebGL 降级等恢复类事件 kind ∈ unresponsive / webgl-fallback / watcher-degraded Tier-2 live
  • Tier-2 live 通道 = 低频高信号事件原样批量上传(确认门控),不等日报聚合 —— 崩溃类事件天然属于此类;
  • 快照脚本 scripts/metrics/pull-posthog-snapshot.mjs 已追加 gpuCrashesByVersion、gpuRecoveryOutcomes 两条 HogQL 查询(append-only);
  • 发布后的判读路径:按 appVersion 分组的崩溃率曲线(39 舰队 vs 43 舰队)→ outcome 分布(recreated 占比应 ≫ sticky-fallback)→ msSince* 直方图(wake-crash 是否随 43 消失)。

6 · A/B 对照方法(39.8.5 vs 43.2.0)

变量控制

  • 两个构建只差 Electron 本体(39 基线 = 当前全部代码修复 + electron 39.8.5 / better-sqlite3 12.8.0;watcher 2.6.0 为 NAPI 模块,两侧同版);
  • 同一台机器、同日交错运行(热状态 / 系统负载对照);
  • 每会话独立 userData,配方参数完全一致。

统计口径

  • 度量:会话是否出现 ANGLE 签名 GPU 崩溃(遇崩即停,cycles-to-first-crash 为强度参考);
  • 每版本 5 会话交错(39→43→39→…);
  • 单侧 Fisher 精确检验:4/5 vs 0/5 → p ≈ 0.024,足以在小样本下下结论;
  • .ips 必须命中 ANGLE 帧签名(CommandEncoder / mtl_command_buffer / insertObject)才计数 —— 排除无关崩溃污染。
