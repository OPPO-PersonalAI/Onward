Space 切回后终端整体白屏 1–3 秒

诊断包 onward-diagnostic-2026-07-13_12-34-50 分析 · 版本 2.1.0-daily.20260711.1 · macOS arm64 · Electron 39.8.5

1. 问题概述

现象从另一个 macOS 桌面（Space）切回 Onward 时，全部 6 个终端的内容区域显示一种"像浏览器无内容可显示时的占位提示"（白色），1–3 秒后自行恢复正常。

频率偶发、条件不明；用户在升级到 20260711 版本后 30 分钟内首次注意到（升级前版本 20260629 未见）。

用户猜测"程序内容不可见的时候，销毁了信息"。

结论先行：用户猜测方向正确，但被销毁的不是终端缓冲区内容，而是渲染器资源——应用在窗口被遮挡时主动销毁全部 WebGL 上下文（这是 2026-05-01 为修"Spaces 切换后 Task 空白"引入的刻意设计）；切回时的"重建 + 字形图集清空风暴"让渲染进程在 1–3 秒内交不出任何一帧，Chromium 合成器只能显示无内容占位（白色）。新版本 f05fe9b 补丁把恢复成本放大了约一个数量级，使原本一闪而过的间隙变得肉眼可见。

2.2 关键的"证据缺席"

整个 49.76 MB、跨两个会话的 trace 中，renderer 侧事件只有 renderer:ipc.terminal.write 一种。注册表中与本问题直接相关的 renderer:window.visibility-change、renderer:xterm.renderer.dispose-webgl、 renderer:xterm.renderer.ensure-webgl、renderer:xterm.renderer.context-lost 一条都没有——它们全部走 opt-in 的 perfTrace() 通道（需 ONWARD_PERF_TRACE=1），生产环境默认不记录。详见 §7。

因此本分析的机制部分来自代码级取证（下文逐条给出 file:line），时序部分来自 telemetry 与 trace 中主进程侧的旁证。

3. 现有机制：窗口遮挡时挂起渲染器，可见时恢复

这套机制由三次历史修复层层演化而来：

提交日期内容
309f7702026-04-21surface 丢失后的渲染器恢复
30ec82d2026-05-01修"macOS Spaces / Win 虚拟桌面切换后 Task 空白"：引入挂起/恢复管线
e496fed2026-05-06WebGL 回退语义对齐 VS Code（context-loss 后 DOM 回退 + 冷却）
746e1172026-05-29共享图集页版本号碰撞修复（6+ Task 乱码）

当前代码路径

  • 挂起：TerminalGrid.tsx:1351-1357 监听 visibilitychange，document.hidden 时调 suspendVisibleRendererSurfaces('document-hidden')（terminal-session-manager.ts:1242）→ 对每个可见会话 renderer.deactivate() → disposeWebgl()（terminal-renderer-lifecycle.ts:277）→ xterm 退到 DOM 渲染器。
  • 隐藏期间：Electron backgroundThrottling 为默认 true，rAF 停摆 → DOM 渲染器实际上从不绘制；PTY 数据进入 pendingData 缓冲（terminal-session-manager.ts:1014-1045）。
  • 恢复：切回触发 document-visible + window-focus → 80ms 防抖（darwin 策略，terminal-renderer-lifecycle.ts:71-80）→ restoreVisibleRendererSurfaces（terminal-session-manager.ts:1266）。

4. 根因链条（切回瞬间发生了什么）

1
切回 Space，窗口重新可见
合成器上一帧内容已随 WebGL canvas 销毁而失效；DOM 渲染器在隐藏期间从未绘制过 → 此刻没有任何可显示的帧。白色占位从这一刻开始。
2
80ms 防抖后，恢复第 1 轮
对 6 个终端逐个：ensureWebgl() 新建 WebGL 上下文（共享字形图集为空）+ forceFit + terminal.refresh(0, rows-1)；同时 flush 隐藏期间缓冲的 PTY 数据（agent 洪峰输出）。
3
下一帧，恢复第 2 轮（postResumeFrameCount=1）
schedulePostFrameSurfaceRestore（terminal-session-manager.ts:1290）对 6 个终端再次调 restoreSurface——此时 addon 已存在，走 Path B = 6 次 clearTextureAtlas()（terminal-renderer-lifecycle.ts:184）。6 个终端共享同一个图集：每次 clear 都把全部已光栅化字形清空，前一个终端刚重建的字形被下一个 clear 再次摧毁。
4
f05fe9b 放大器（本次升级新增，见 §5）
每次 clearTextureAtlas 都 bump 共享 _modelEpoch → 全部 6 个 owner 各自强制 _clearModel(true) + 全视口 _updateModel(0, rows-1)；叠加 022e3f2 的 merge-retry 循环（单次渲染 ≤32 次重试），成本从 O(N) 涨到 O(N² × 重试)。6 宫格 × 密集 TUI 输出 × retina DPR=2 → 渲染主线程连续忙碌数百 ms 至数秒。
5
白色窗口期：1–3 秒
在第一帧干净内容提交之前，合成器对每个 canvas 区域绘制"无内容占位"（白）。首帧提交后一切恢复 → 用户看到"过一会儿才恢复"。
次生场景（偶发性的另一半）：若遮挡期间 macOS 真的回收了 GPU surface（或该轮挂起未及触发），切回时 webglcontextlost 在多个 canvas 上触发 → fallbackAfterContextLoss（terminal-renderer-lifecycle.ts:342）→ 进入 5000ms WebGL 冷却并退 DOM 渲染；冷却期内所有恢复请求被 restore-deferred 拒绝。这条路径下白色窗口期更长。"偶尔出现、条件不明"正对应这两条路径叠加负载高低的组合。

5. 放大器：f05fe9b 的 epoch 广播（为什么升级后才注意到）

版本区间 20260629 → 20260711 共 10 个提交，其中唯一触及渲染器的是 f05fe9b（2026-07-02，"per-owner model-epoch to seal multi-Task WebGL atlas garble"）。它本身是正确的乱码修复，但改变了 clearTextureAtlas 的传播语义：

升级前（20260629）

共享图集的 _requestClearModel 是单个布尔：clear 之后只有第一个渲染的终端做全量模型重建，其余 5 个继续用旧模型（这正是乱码根源，但恢复路径上"便宜"）。

恢复风暴成本 ≈ O(N) 次全量重建。窗口期短，肉眼难察觉。

升级后（20260711，含 f05fe9b）

每次 clear bump 共享 _modelEpoch，每个 owner 的 beginFrame() 都返回 true → 6 个终端各自全量 _clearModel + _updateModel；merge-retry 循环在 epoch 连续推进时反复整轮重建。

恢复风暴成本 ≈ O(N² × 重试) 次全量重建 + 图集反复清空重光栅化。窗口期拉长到 1–3 秒，肉眼可见。

注意：f05fe9b 不是 bug，恢复路径的"每终端各 clear 一次共享图集"才是浪费的源头——6 个终端共享一个图集，一个恢复批次里 clear 一次就够了。f05fe9b 只是让这个既有浪费从"隐性"变成"显性"。

6. 为什么是"白色"，而不是黑屏或花屏

  • 窗口原生背景色已设置为深色（electron/main/index.ts:457，backgroundColor: '#1e1e1e'），主题 Amethyst 也是深色 → 排除"窗口级白底闪现"。
  • 用户描述"像浏览器无内容可显示时的提示，是渲染内核主动显示的，不是渲染出错"——这与 Chromium 合成器对失效 canvas 层 / 死 GPU tile 的占位绘制一致。docs/lessons.md 2026-04-30 条目记录过同一视觉："Chromium's compositor showed the dead GPU tile as a 'broken image' placeholder"。
  • 占位出现在每个终端的内容区域（canvas 层级），而非整窗——与"6 个 canvas 同时无有效内容"吻合。

7. 诊断盲区（无论选哪个方案都必须修）

问题：渲染器生命周期全部 9 个事件（visibility-change / dispose-webgl / ensure-webgl / context-lost / context-loss-fallback / restore-deferred / failure 等）都走 opt-in 的 perfTrace()，生产诊断包里为零。这正是 src/utils/perf-trace.ts:29-37 注释里点名警告过的失效模式（2026-07-04 Git Diff 诊断包同样的教训）。

修法：把这些低频、用户动作级的生命周期事件迁移到 default-on 的 perfTraceDiagnostic() 通道。它们每次 Space 切换才发十几条，完全符合 diagnostic tier 的频率约束。修复后，用户再报同类问题时，诊断包能直接回答"挂起了吗、恢复用了多久、有没有 context-loss、冷却触发没有"。

另外两个注册即未发射的事件（RENDERER_XTERM_RENDERER_CONTEXT_RESTORED / REFRESH_AFTER_RESTORE，perf-trace-names.ts:370,372）应一并补上发射点，量化"恢复耗时"。

8. 同行产品调研

一句话结论：所有成熟同行在窗口遮挡时都"暂停渲染、保留 GPU 上下文"，没有任何一家采取"销毁再重建"。本应用的 dispose-on-hidden 设计是同类产品中的孤例。

8.1 VS Code（xterm.js 最大的使用方）：只在真丢失时销毁

VS Code 不会在窗口隐藏/遮挡时销毁 WebglAddon。xtermTerminal.ts 中唯一的销毁路径是真正的 onContextLoss 回调（_disposeOfWebglRenderer()）；不存在任何 visibility/occlusion 触发的销毁。隐藏终端的处理靠 xterm.js 内建的 IntersectionObserver（PR #1144、issue #880）：元素完全不可见时停止渲染帧，但WebGL 上下文保持存活——是暂停，不是拆除。

而且"在存活终端上重建 WebglAddon"这条路径本身是已知脆弱面：VS Code issue #263159（"terminal goes invisible"，webglcontextrestored 后报 INVALID_OPERATION: object does not belong to this context，以 not-planned 关闭）、#76940（唤醒后损坏，隐藏/显示不能恢复，只能新建终端）——正是我们每次 Space 切换都会主动走的机制。

8.2 Chromium / Electron 在 macOS 的遮挡行为

  • Electron 文档确认：macOS 上 visibility 状态跟随窗口遮挡——切到别的 Space 使窗口被完全遮挡即 document.hidden=true；backgroundThrottling: true（默认）会同时压制 rAF（electron#9567、#4925）。这与 §3/§4 的机制推演一致。
  • 新发现的风险面：Chrome 对单页 WebGL 上下文数有约 16 个的上限，超限时最老的上下文被强制 webglcontextlost。每次 Space 切换翻搅 6 个上下文（销毁 6 + 新建 6），一旦销毁侧回收滞后就逼近上限——与"偶尔出现、条件不明"的观测吻合（触发即落入 §4 次生场景的 5s 冷却路径）。
  • 重新显示时，若 canvas 合成层还没有有效内容，合成器显示空白/白色层直到第一次重绘提交——与用户描述的白色占位一致。（Electron BrowserWindow 文档）

8.3 xterm.js 恢复路径的已知伤疤

  • 官方 README 推荐的 onContextLoss 处理就是 dispose()——这个 API 不是为"日常反复重建"设计的。
  • 在存活终端上新建 WebglAddon 会让字形图集从空开始重新光栅化（issue #4065："图集清空后重来"），重建后的最初帧可能渲染空白/残缺字形，直到图集重新填充——与 §4 第 2-4 步的推演一致。相关脆弱面：#2623、#3548。
  • 未证实项（诚实声明）：调研未能确认 @xterm/addon-webgl 0.19/0.20 是否修复了"重建后首帧空图集"行为——"升级新版 addon 能解决"目前是未验证假设。

8.4 原生 GPU 终端：一致的"暂停循环、保留资源"

产品遮挡时策略
Alacritty / WezTerm基于 winit 的 WindowEvent::Occluded（macOS NSWindow occlusionState）：遮挡期间跳过重绘，GPU surface/上下文保留（winit 仅在 iOS 因应用生命周期释放资源，macOS 不释放）
Ghostty原生 AppKit + Metal：不可见时降频/暂停重绘，Metal layer 保留
iTerm2（Metal）遮挡/离屏窗口暂停绘制，不拆除 Metal device

来源：winit 文档（docs.rs/winit）、gpu-terminal-wars（unixy.io）、Terminal Emulator Comparison 2026（blog.luminoid.dev）。

调研对方案的影响：同行共识使方案 2（不再遮挡即销毁）从"激进选项"升级为"长期正确方向"——它同时消除重建风暴、空图集首帧、以及 16 上下文上限翻搅三个风险面。但它的回归验证成本仍然最高（须证明 2026-05-01 phantom-blank 不复发，而当年那个 bug 的真正根源——contextlost 里同步 dispose、缺 preventDefault——已由 lessons 2026-04-30 的修复解决，挂起机制可能是在治"已被治好的病"）。方案 1 仍是本次回归的最短止血路径。

9. 修复方案选项

方案 0 · 必做诊断通道迁移（不改行为）

§7 的修复：生命周期事件迁到 perfTraceDiagnostic + 补齐 restored / refresh-after-restore 发射点。不改变任何渲染行为，为后续验证和未来诊断提供数据。风险：无。

方案 1 · 推荐恢复路径去重：共享图集每批次只 clear 一次

改动：(a) 恢复第 2 轮（post-frame Path B）按共享图集实体去重——一个恢复批次内只对图集 clear 一次，其余终端只 refresh；(b) Path B 跳过"第 1 轮刚由 Path A 重建过上下文"的终端（新图集本来就是空的，再 clear 纯属浪费）。

效果：恢复成本从 O(N²×重试) 回到 O(N)，f05fe9b 的正确性收益保留。风险：低——不动挂起策略，2026-05-01 的 phantom-blank 防护原样保留；TFA-10..18 现有断言直接回归验证。

方案 2 · 策略变更不再在 document.hidden 时销毁 WebGL

改动：取消 suspend-on-hidden；上下文常驻，只暂停写入/渲染；真正的 GPU 回收交给 keep-alive 的 context-loss 恢复路径（lessons 2026-04-30 已确立：contextlost 时保留 addon + preventDefault，contextrestored 后重建）。

效果：切回时零重建成本，白色窗口期从机制上消失。风险：中高——需要重新验证当初引入挂起机制要防的"GPU surface 回收后 phantom-blank"不回归；依赖同行调研结论（VS Code 是否保持上下文存活）。改动面大，需要完整的 5 次往返稳定性验证。

方案 3 · 体验平滑错峰恢复（可与方案 1 叠加）

改动：恢复不再 6 个终端同帧进行——聚焦终端最先恢复，其余每帧一个错开，保证渲染主线程每帧都能提交。

效果：即便未来终端数增加，首帧时间有上界。风险：低-中——恢复期间不同终端有短暂视觉不同步。

决策请求：方案 0 属于诊断基建，无行为变化，建议直接实施；方案 1/2/3 属于渲染器生命周期策略调整，按项目规则需要用户显式决策。推荐组合：方案 0 + 方案 1（先消掉本次回归的直接放大器，低风险、可快速验证），方案 2 待同行调研结论与方案 1 实测效果后再评估，方案 3 视 1 的实测残余窗口期决定是否叠加。
用户决策（2026-07-13）：选定 方案 0 + 方案 2（对齐同行：遮挡时保留 WebGL 上下文、只暂停渲染），恢复延迟测试预算 200ms（3 次取样、≥1 次达标）。实施要点：document.hidden 不再触发 suspendVisibleRendererSurfaces（该方法移除，改为 noteDocumentHiddenKeepAlive() 诊断面包屑）；restoreSurface 接入纯决策表 decideSurfaceRestoreAction——存活 addon 走 refresh-only（不再 clearTextureAtlas，方案 1 的去重收益被方案 2 自然覆盖）；真实 context-loss → DOM 回退 → 冷却 → 重建的安全网原样保留；tab 切换（setVisibility(false)）的 WebGL 释放行为不变。生命周期事件全部迁移 perfTraceDiagnostic（默认开启），新增 document-hidden-keepalive 与 surface-restore-batch（时长 span）两个诊断事件。
