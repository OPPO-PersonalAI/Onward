Git 同步新鲜度的呈现与恢复

BUG-0005 的 R3 返工 · 竞品调研与方案决策 · 2026-08-07

0 · 结论摘要

调研结论:↓? 是所有做法里唯一没有先例的那一条

我把「未知」塞进了计数原本的位置(同一个槽位换个字符)。查遍 git 本体、git-prompt.sh、posh-git、 GitHub Desktop、GitLens、VS Code、JetBrains,没有任何一个工具这么做。它们无一例外地 换一个类别的表达:换成空字符串、换一个专用符号、换整个控件、或者换成一句话。

更要命的是:? 在 git 的语境里已经被占用了。 git status 里 ?? = 未跟踪文件,子模块的 ? = 含未跟踪文件, git-prompt.sh 里 ? = sparse checkout。你说的「概念困惑」不是错觉, 是这个符号在这个领域里真的另有所指。

正确的形状

调研 7 个产品后,最硬的一条共识不是「该用什么符号」,而是: 没有任何一个产品把陈旧标记放在 ahead/behind 计数本身上。 有信号的两家都放在别处——GitKraken 放在 REMOTES 分区标题,Fork 放在 Activity Manager。 另有两家(GitHub Desktop、GitLens)用一条独立的时间戳承载新鲜度。 而「怎么恢复」的普遍答案是:指示器本身就是动作——Sublime Merge 的 ahead/behind 指示器可直接点击 push/pull, VS Code 状态栏点击即同步,GitHub Desktop 的主按钮就是 Fetch/Pull/Push。 我们既没有独立信号位,也没有任何动作,却在计数位上放了一个符号。

三条跨来源共识(按证据强度排序)

① 陈旧信号绝不放在计数上最强

7 个产品,零个把陈旧标记做进 ahead/behind 计数里。 有信号的两家都放在别处:GitKraken 在 REMOTES 分区标题,Fork 在 Activity Manager。

这条直接否定 ↓?——我做的正是所有人都没做的那件事。

② 没人渲染 0

git 用 =,posh-git 用 ≡,GitHub Desktop / VS Code 不渲染,GitLens 用一句话。

我们已经符合(showBehind = behind > 0)。

③ 恢复 = 指示器本身可点最一致

Sublime Merge 的 ahead/behind 指示器点击即 push/pull;VS Code 点状态栏即同步; GitHub Desktop 的主按钮就是 Fetch/Pull/Push;Fork / Tower 有常驻 Fetch 按钮。

9 个产品里,只有我们一个连手动 fetch 都没有。

一条我第一版说过头、现已更正的结论

我原本写「竞品普遍用独立常驻时间戳」。实际是 7 个里只有 2 个 (GitHub Desktop、GitLens);Fork、Sublime Merge、GitKraken、Tower 全都没有任何「上次同步于」显示。 时间戳仍是最好的解法之一,但称不上行业惯例——真正的惯例是上面第 ① 条。

唯一一条「解释 + 重试同处一个界面」的明确先例

来自 AWS Cloudscape 设计体系(不是 git 工具):刷新部分或完全失败时, 「use a warning status indicator to inform users. Include in the popover additional information to explain the failure and provide actions to support users, such as retry」。 这正好是我们需要的形状——一个既说明原因、又能就地重试的悬浮层。

VS Code 是反面教材,不是范本

它和我们得的是同一个病

3 · 我们的真实缺口

先纠正我自己之前的一个表述

我一直把问题说成「↓0 是撒谎」。但代码事实是:我们从来没渲染过 ↓0 (gitSyncDisplay.ts:66 showBehind = behind > 0)。 真正的歧义在箭头的缺席上——「没有 ↓」既可能是「真的没落后」,也可能是「压根没查过」。 竞品消除这个歧义的办法是加一条常驻的时间戳,而不是给空位补一个符号。我补符号补错了方向。

缺口竞品的解法我们现在
数据有多新,不可见 常驻 Last fetched X ago / Never fetched 只有 stale 时 tooltip 才多一行,且不含时间
没有恢复入口 指示器本身可点击 = 立即同步 全应用零个手动 fetch 入口, 用户只能切到终端敲命令(诊断包里那位用户正是这么做的)
失败原因不可见 GitHub Desktop 会把失败状态显示出来 主进程已经有 classified / stderrTail / remoteScheme(BUG-0005 R4 刚加的),但没有送到界面

5 · 方案选项

A · 徽章可点击 + 常驻新鲜度推荐

删掉 ↓?。计数位回到「没落后就不显示」。 tooltip 常驻一行「上次同步:X 前 / 从未成功」,失败时追加已经采集到的原因。 单击徽章 = 立即 fetch,带进行中状态。

三条竞品共识全部命中

一次性补齐「不知道多旧」和「不知道怎么办」两个缺口

复用已有的 classified / stderrTail,不用新采数据

要新开一条用户可触发的 fetch IPC(主进程侧很小,渲染层要做进行中/结果反馈)

单击与现有「双击复制分支名」冲突,需先解(见 § 6)

B · A 的基础上加持久失败标记

在 A 之上,连续失败时给徽章一个低调的持久标记(整体去饱和,或加一个断连图标)。

离线/长期失败在不悬停时也能看见

有反面证据:OneDrive 的灰化图标被用户误读为「出问题了」, 微软社区里有以此为标题的求助帖。灰化在界面里同时还表示「禁用/次要/非活跃」

徽章只有 11px,再叠图标会挤

C · 只做「诚实」,不做「可操作」

删掉 ↓?,tooltip 加常驻时间戳,不加点击。

改动最小,不碰 IPC,无交互冲突

你提的第二个问题原样保留——用户看到「从未同步成功」, 仍然只能自己切终端敲 git fetch

等于把 VS Code 的坑抄了一半

D · 维持现状

保留 ↓?。

已知与 git 符号体系冲突

无先例支持

你已经反馈它令人困惑

6 · 需要一并决定:交互位冲突

徽章的双击位已经被占了

当前 TerminalGrid.tsx:3401 上挂着 onDoubleClick = 复制分支名。如果再加单击, 双击的第一下会先触发单击,导致「想复制,结果先发了一次 fetch」。必须二选一。

i · 单击=同步,复制移到右键菜单推荐

与 VS Code 状态栏同步项、GitHub Desktop 主按钮一致——最主要的动作占最易触达的位

仓库已有右键菜单实现与规范(SVG 图标 + span + 统一 CSS),挂「复制分支名」很自然

改变了一个已存在的用户习惯(双击复制)

ii · 保留双击复制,同步进右键菜单

不动任何既有习惯,零冲突

恢复动作藏在右键里,发现性差——而「用户不知道怎么恢复」正是这次要解决的问题

iii · 两个都进右键菜单,单击不绑定

语义最干净,徽章回归纯指示器

同样发现性差;且徽章看起来可点却不可点,反而更困惑
