基础设施失效韧性设计

线程池卡死(故障 A)与渲染可见性冻结(故障 B)的彻底解法 — 基于 2026-07-20 生产事件的活体取证 + 上游调研 + 代码库勘察

1. 事件与根因

2026-07-20 生产实例(v2.1.0-daily.20260713.1,Electron 39.8.5,macOS 26.2,经 Jump Desktop 远程使用)在远程会话断开/熄屏边界(01:17:50)后出现两个互相独立的永久卡死态:

01:17:50 — Jump Desktop 远程会话断开,显示器熄屏(pmset 日志)
↓ 同一触发点,两条独立故障链
故障 A — 主进程 libuv 线程池"丢唤醒":4 个 worker 永久停在 uv_cond_wait(内核 __psynch_cvwait),队列有任务也不醒;fs/dns/zlib/crypto 四类异步操作全部永久挂起。定时器、IPC、uv 流、同步 fs 均正常。进程内不可恢复,上游无修复。
故障 B — 渲染进程 document.visibilityState 卡在 hidden 约 10 小时:rAF 停、绘制停,但事件与 DOM 更新正常。把窗口带回前台时恢复"看运气"(10:52 前台点击未恢复,11:21 恢复)。

故障 A 最致命的下游:终端输入静默死亡

node-pty 1.1.0 的 CustomWriteStream(上游 PR #831 引入)在 posix 上用 callback 版 fs.write(fd) 串行冲刷键击队列 — fs.write 走 libuv 线程池。线程池死 → 键击永久堆在 _writeQueue,而 API 返回 void、IPC invoke 返回 true、无任何报错。实证:注入回车后 invoke 成功但所有 tty 设备 mtime 不变。

2. 设计原则

环境异常是常态输入,不是意外。熄屏、远程桌面断开、显示器增删、进程被降优先级——一个长驻程序必须把这些当作正常输入来设计。触发源在 OS/Chromium/libuv 层,但"被触发后无法自愈、无法感知、无法取证"是程序自身的设计缺陷,必须由程序自身修复。(用户定调)

  • 自我检测:基础设施(线程池、可见性/绘制)失效时程序第一时间知道。
  • 自动恢复:能自愈的自动恢复(可见性);不能自愈的隔离损害并引导用户重启(线程池)。
  • 优雅降级:关键路径(键击、诊断日志、状态落盘、退出)不得建立在"异步 fs 一定会回调"的假设上。
  • 可观测:失效的全过程有同步落盘的 trace 证据(trace-store 已是全同步,天然满足)。

3. P1 — 终端输入写路径去线程池化(核心)

上游历史(PR #831)已查证:老的 socket.write 路径有真实缺陷(>1KB 粘贴损坏、macOS 挂死、EAGAIN 被流包装层吞掉),回退不可行。上游改用 fs.write 线程池并明确承认了线程池交错风险("accepted for paste, unvalidated for keystrokes")。VS Code 用同款 node-pty 未打补丁,仅靠 pty-host 独立进程隔离爆炸半径——同样的 OS 缺陷打到它的 pty host 上,终端输入一样会死。我们要做的是机制级修复,比 VS Code 现状更彻底。

关键可行性事实

pty master fd 是非阻塞的(CustomWriteStream 自己处理 EAGAIN 即为铁证)。在非阻塞 fd 上,fs.writeSync 永远不会阻塞线程——要么立刻写入(键击场景微秒级),要么立刻抛 EAGAIN。上游"同步写会拖慢其它 pty"的顾虑只对阻塞 fd 成立,对非阻塞 fd 不适用。已知反例(jcansdale 实验)只证明无 EAGAIN 处理的裸 writeSync 会坏 — 保留原队列 + offset 推进 + EAGAIN→setImmediate 重试语义即可规避。

3.1 三条路线对比

1a 常态同步写(推荐)1c 看门狗切换回退1d pty-host 进程隔离
做法补丁 CustomWriteStream:fs.write → fs.writeSync + EAGAIN 捕获 + setImmediate 重试,队列语义原样保留正常走上游 fs.write;看门狗判死后切到 writeSync 冲刷pty 全部迁入 utilityProcess(VS Code 架构)
故障 A 下终端输入免疫检测窗口内(约 15-35s)仍丢失不免疫pty host 自己的线程池同样会死
正常态行为改变写系统调用移到主线程(非阻塞,键击 ~1-2µs;大粘贴按 EAGAIN 分片让出)零改变全链路重构(IPC 多一跳)
复杂度/风险低;单一路径,无模式切换;需处理部分写入的字节偏移(沿用上游逻辑)中;模式切换时在途 fs.write 是否已写入不可知 → 有重复写/乱序隐患高;数月级工程,且不解决本故障类
补丁位置patches/node-pty@1.1.0.patch(现有补丁文件追加 posix 段)src 架构改造

1d 可作为长期架构方向(隔离主进程负载),但它与本故障正交,不纳入本次修复。

4. P2 — 线程池看门狗

现状

唯一的健康监测是事件循环卡顿检测(performance-trace.ts:788,250ms 定时器)——对故障 A 完全失明(事件循环全程健康)。线程池死亡 10 小时无任何感知。

方案

周期探针(默认 15s):提交一个 1 字节 zlib.gzip(纯 CPU,必走线程池、不碰磁盘)与 5s 定时器赛跑;连续 2 次超时 → 判定线程池死亡。powerMonitor 的 resume/unlock 后立即加测一次(高危边界快检)。

判死后的动作(按序):

  1. 同步落盘取证:main:threadpool-watchdog.stall-detected 经 trace-store(同步)写入;
  2. 广播降级:遥测 writeQueue 停止追链(丢弃并计数,防 Promise 链无限增长);诊断包切同步归档;app-state 切主线程 writeFileSync;
  3. 通知用户:复用 tabBar.updateReady.* toast 模板(en+zh-CN),文案"内部服务已失效,建议尽快重启应用",按钮走有界退出链(P3);
  4. 外部可观测:/api/health 增加 threadpool: ok|stalled 等字段;
  5. 探针继续运行,若线程池意外复活(理论可能)则解除降级并落盘 recovered 事件。

不做自动重启:终端应用重启会杀死用户所有运行中的 shell/任务,该决定必须留给用户(待决策点 2)。

6. P4 — 可见性看门狗与恢复推送

现状:零 powerMonitor、零 screen 事件接入;渲染侧恢复完全押注 visibilitychange→visible 会到来(TerminalGrid.tsx:1404)——事件不来就永久冻结。上游在 Electron 40+ 才修复遮挡状态机(#50579),且未必覆盖我们的场景。

检测(主进程):powerMonitor resume/unlock-screen + screen display-added/removed/metrics-changed 触发即时校验;另有 30s 慢周期兜底(本次事件无系统睡眠事件,只有显示器熄屏——必须有周期兜底)。校验 = 主进程认为窗口可见(win.isVisible() && !win.isMinimized())时,向渲染进程发 visibility-probe IPC,渲染进程回报 document.visibilityState + 2 帧 rAF 存活测试
↓ 失配持续 > 5s
恢复推送(复用 GPU 崩溃恢复模板 gpu-crash-recovery.ts):主进程主动 nudge — 依次尝试 ① wc.setBackgroundThrottling(false)+恢复 ② win.hide()+win.show()(上游 issue 群实证有效,代价一次闪烁);渲染侧收到推送后走既有 notifySurfaceEvent('document-visible') 路径重建渲染面
↓ 全程
取证:mismatch-detected / nudge-applied / recovered 三事件同步落盘

附带清理:启动参数里的 --disable-features=MacWebContentsOcclusion 在 Electron 39 是无效重复(E35 起内部已强制禁用,#45776),移除以免升级后语义漂移(升级到 E42+ 时该内部禁用被撤销,是否重新显式禁用见待决策点 4)。

8. P6 — Electron 升级(独立事项)

Electron 43.1.0(Chromium 150 / Node 24.18 / libuv 1.52.x):对故障 A 无帮助(线程池仍是 pthread condvar,上游无修复);对故障 B 有遮挡状态机修复(#50579,E40+)。建议作为独立事项排期(Chromium 142→150 需完整回归),不与本修复捆绑。P1–P5 在任何 Electron 版本上都成立且必要(纵深防御)。
