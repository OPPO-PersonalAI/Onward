# Lessons Learned

## 2026-03-26: Multi-terminal output performance optimization and end-to-end stress testing

### 1. Test methods must reflect real user scenarios instead of only system metrics
- **Problem**: The initial evaluation only measured terminal output FPS and `xterm.write` latency, then concluded that performance was fine (`fps=32`, `writeMax=0.4ms`), even though typing still felt visibly laggy to the user.
- **Cause**: The analysis mixed up terminal output performance with user input performance. The real pain point was Prompt input responsiveness while terminals were flooding output, not whether terminal rendering itself was smooth.
- **Lesson**: Performance testing must start from the user experience. First identify which operation feels slow, then measure the latency of that operation. Internal metrics such as FPS or write duration are diagnostic signals, not acceptance criteria.

### 2. Stress-test intensity must match real load instead of stopping at a light sample
- **Problem**: The initial stress test only ran for 30 seconds and 25,000 lines, far below the sustained high-throughput scenario produced by Claude Code in real usage.
- **Cause**: The test optimized for fast feedback instead of representing real load characteristics. Claude Code can produce continuous output across multiple terminals for a long time, which is far heavier than a simple loop.
- **Lesson**: Stress tests should run for at least 10 to 20 minutes and use an infinite loop such as `while ($true)` to simulate sustained output. Short tests only expose startup issues and will miss long-run problems such as memory accumulation, GC pressure, and resource leaks.

### 3. Do not rely on overly indirect or fragile end-to-end test methods
- **Problem**: The attempt to automate everything through `app-state.json`, API calls, and background process tricks repeatedly ran into file locks, process-management issues, and terminal ID formatting problems such as stray `\r`.
- **Cause**: The approach aimed for full automation without considering the current infrastructure limits. The API server does not expose terminal creation or layout switching, so mutating state files directly is brittle.
- **Lesson**: Prefer the most direct path. Let the user perform the UI-only step when necessary, then drive the rest through the API. Do not try to bypass every UI step with hacks when the platform does not support it cleanly.

### 4. When editing `useEffect`, always evaluate cleanup impact on initialization flow
- **Problem**: After adding a `setVisibility` effect, the cleanup ran when `visibleTerminals` changed from 1 to 6 terminals, set the old terminals to `visible=false`, and disposed the WebGL context. The next effect immediately recreated WebGL with `visible=true`, and that dispose-plus-create cycle within one frame froze the 6-panel initialization.
- **Cause**: The implementation did not fully account for React `useEffect` cleanup timing. When dependencies change, cleanup runs before the new effect, and that ordering is dangerous for cleanup logic that releases resources such as WebGL contexts.
- **Lesson**: Be especially careful with cleanup in effects that touch GPU resources, DOM state, or other side effects. If cleanup releases a resource that the new effect will immediately recreate, the cleanup may be unnecessary and harmful.

### 5. Performance optimization must start at the source of the data flow instead of patching only the tail
- **Problem**: The first optimization only throttled renderer-side writes to 50ms. That reduced writes per second from 18,000 to 96, but user input latency barely improved (`2212ms` versus the original `1900ms`).
- **Cause**: Renderer-side throttling reduced `terminal.write()` frequency, but the main process still emitted IPC messages every 16ms to every terminal. The renderer main thread still paid the cost of each IPC callback, including map lookups, queue pushes, and scheduling checks.
- **Lesson**: Follow the entire data path from source to sink: `PTY -> TerminalDataBuffer(main) -> IPC -> renderer callback -> pendingData -> rAF -> terminal.write()`. Optimizing only the final write step leaves upstream costs in place. IPC frequency and renderer write frequency both need to be addressed.

### 6. Process management must use exact names and never wildcards
- **Problem**: Using wildcard matches with `taskkill` and `Get-Process` risked terminating unrelated user processes.
- **Cause**: The commands optimized for convenience and ignored the possibility that multiple Onward variants could be running at the same time.
- **Lesson**: This is now a hard rule. Use exact process names only with `taskkill`, `Get-Process`, and `pkill`. On Windows, prefer `wmic process where "name='ExactName.exe'"` for precise querying and control.

### 7. Windows bash variable and PowerShell escaping requires extra care
- **Problem**: When PowerShell commands were sent through `curl`, bash expanded PowerShell variables such as `$i` and `$_` as bash variables, which broke command delivery in most terminals. Python-generated terminal IDs also contained `\r`, which corrupted URL construction.
- **Cause**: Cross-shell invocation chains such as `bash -> curl -> JSON -> PowerShell` introduce multiple escaping layers, and each layer can rewrite or consume special characters.
- **Lesson**: When commands cross shells, prefer heredocs such as `<< 'EOF'` or file-based payloads to avoid multi-layer escaping bugs. Always normalize external command output with `tr -d '\r'` when Windows line endings may be present.

## 2026-04-02: Markdown migration regressions and incomplete first-pass fixes

### 1. Migration review must include shell-level files such as `index.html`, not only component logic
- **Problem**: Markdown images appeared to be wired correctly in the renderer and worker, but the packaged app still failed to display them.
- **Cause**: The migration review focused on `ProjectEditor.tsx` and `markdownPreviewWorker.ts`, but did not compare the source project's `index.html`. The source project allowed Markdown images through CSP with `img-src 'self' data:`, while this repo's initial `index.html` omitted `img-src`, so the browser blocked image rendering even when the generated HTML was correct.
- **Lesson**: When porting a working feature from another project, compare the full execution path end to end: HTML shell and CSP, preload boundaries, renderer state, worker output, and DOM behavior. Do not assume root-level files match the source project unless they have been explicitly diffed.

### 2. End-to-end validation must check visible behavior, not only generated HTML
- **Problem**: The first repair looked successful because the Markdown preview HTML already contained `<img src="data:image/...">`, yet the user still saw broken images.
- **Cause**: The verification standard stopped at internal state and rendered HTML strings. That proved the data path was partly correct, but it did not prove that the browser actually loaded and displayed the image.
- **Lesson**: For UI rendering bugs, autotests must verify the user-visible outcome. In this case the correct assertion is not just "the HTML contains an `<img>` tag" but also "the preview DOM contains images whose `naturalWidth > 0` and whose broken count is zero."

### 3. When a user says the bug still exists, assume layered failures until disproven
- **Problem**: The first Markdown image fix restored the missing re-render after image caching, but the overall issue still remained because a second independent failure was still active.
- **Cause**: The debugging process converged too early on a plausible internal cause and treated that as the whole bug. In reality there were two separate regressions: the missing re-render path and the missing CSP `img-src` allowance.
- **Lesson**: If a user reports that the visible bug still exists after a fix, immediately test for stacked regressions instead of defending the first explanation. Re-check every layer of the pipeline and look for independent blockers that can mask each other.

## 2026-04-02: Settings closing logic must distinguish tab switches from task switches

### 1. Do not apply a tab-switch fix blindly to task switching in the same tab
- **Problem**: After introducing conditional Settings closing, the implementation also closed Settings during `focusTerminal` task switching inside the same tab. In the user flow `Prompt -> manually open Settings -> use task-switch shortcut`, the Settings button and panel disappeared unexpectedly.
- **Cause**: The fix correctly identified that cross-tab navigation needed contextual handling, but it overgeneralized that rule to all shortcut-driven focus changes. Task switching and tab switching are different UX operations and should not share the same closing behavior by default.
- **Lesson**: When a bug report is specifically about cross-tab state, keep the fix scoped to cross-tab transitions unless there is explicit evidence that same-tab task switching should behave the same way. Validate each shortcut path independently.

### 2. Reproduce the exact user interaction sequence before finalizing a state-management fix
- **Problem**: The first revision looked logically correct against the review comments, but it still broke a real user edge case that combined Prompt, manual Settings opening, and task-switch shortcuts.
- **Cause**: The implementation was optimized around inferred state transitions instead of replaying the exact UI sequence the user would perform. That missed a behavior regression in a neighboring path.
- **Lesson**: For UI state fixes, convert the user report into a concrete step-by-step scenario and verify the implementation against that scenario before treating the change as complete. Review comments are useful signals, but they do not replace end-user flow validation.

## 2026-04-05: Git Diff split-view persistence must follow the real drag path

### 1. Do not treat preference writes as proof that the UI interaction works
- **Problem**: The first attempt claimed the Git Diff split width was "remembered" because the code wrote a ratio into `localStorage`, but the user could still drag the sash manually and see no persistence after re-entering Git Diff.
- **Cause**: The validation path only proved that a stored value existed. It did not prove that the manual sash drag path updated that value, nor that reopening Git Diff restored the same visual ratio.
- **Lesson**: For UI persistence bugs, test the exact user path end to end: drag the real control, leave the page, reopen it, and compare the restored layout against the stored value. A stored preference alone is not an acceptance signal.

### 2. Prefer editor layout APIs over DOM guessing for third-party UI state
- **Problem**: Split-width measurement sometimes returned obviously wrong values such as `5px / 5px`, which made the stored ratio meaningless and caused false confidence during debugging.
- **Cause**: The implementation relied on DOM structure and private editor elements that were unstable across render states. Hidden or not-yet-laid-out editors could still satisfy the selector but report garbage geometry.
- **Lesson**: When reading layout state from Monaco or similar editors, prefer public APIs such as `getLayoutInfo()` first, and use DOM probing only as a fallback. The persistence pipeline is only as good as the measurement source.

### 3. Remove experimental self-healing logic before trusting packaged validation
- **Problem**: The intermediate implementation mixed real persistence with simulated drag-on-mount behavior and dangling references from earlier experiments. That made the code harder to reason about and increased the chance of renderer regressions.
- **Cause**: The debugging flow tried to "force" the UI into the desired state instead of first fixing the measurement and persistence chain. Experimental scaffolding remained in the packaged app path for too long.
- **Lesson**: When a UI fix starts accumulating simulated interactions or recovery hacks, stop and simplify. Fix the state source, delete experimental code paths, then rebuild and rerun the packaged end-to-end suite before reporting success.

## 2026-04-08: Subpage navigation UI needs structural analysis before patching visuals

### 1. Visual inconsistency in a shared header usually signals a structural split, not a missing CSS tweak
- **Problem**: The first rounds kept adjusting individual button styles for `Diff`, `Editor`, `History`, and `ESC`, but the user still immediately saw mismatches. The `Save` button in `Editor` exposed that the top area was not truly unified.
- **Cause**: The implementation only shared some CSS classes while each page still assembled its own header actions. That left multiple button structures and style sources alive at the same time.
- **Lesson**: When multiple subpages are supposed to share one top bar, do not stop at "matching classes." Build a real shared header action system with shared button components and shared layout slots. If one button still needs page-local styling, the unification is not finished.

### 2. When the user reports flashing during page switches, inspect the mount lifecycle before proposing cosmetic fixes
- **Problem**: Early fixes reduced some flicker but `Diff -> History` and `Editor -> History` still flashed, because the content area briefly exposed an initialization gap.
- **Cause**: The debugging process focused too much on visible styling and not enough on the actual switch lifecycle. The pages were still responsible for closing themselves before the target page fully opened, which created a body-level empty window during navigation.
- **Lesson**: For flashing or redraw complaints, analyze the DOM and mount order first. Confirm whether the shared shell is stable, whether the body host is reused, and who controls open/close sequencing. Only add transition animation after the lifecycle gap is understood, and use the animation to mask a known initialization window rather than as a blind guess.

### 3. Shared subpage navigation must be orchestrated from one host instead of by each page independently
- **Problem**: Each page initially dispatched the target open event and then immediately closed itself. That made the switching behavior hard to reason about and easy to regress when adding more shared UI.
- **Cause**: Navigation ownership remained distributed across `GitDiffViewer`, `GitHistoryViewer`, and `ProjectEditor`, even after the shell started becoming shared. That meant there was no single place to guarantee "open target first, then retire source."
- **Lesson**: Once multiple subpages share a fixed shell, navigation should be centralized in the host container. Let the host coordinate subpage activation, body transitions, and teardown timing. Do not leave lifecycle ordering scattered across leaf pages.

## 2026-04-25: Git porcelain v2 sub field has four flags — never read just the leading 'S'

### 1. The `<c><m><u>` flags must each be parsed before any submodule UI decision
- **Problem**: Git Diff UI surfaced a parent file-list entry for a submodule whenever the parent's `git status --porcelain=2` reported one, even when the parent's recorded HEAD pointer for that submodule was unchanged. The user then saw "submodule directory was modified" while every file inside the submodule was untouched at the parent level.
- **Cause**: `parseStatusPorcelainV2Z` only inspected `sub.charAt(0)` (`'S'` to detect submodule kind) and discarded `sub.charAt(1..3)` (`<c>`, `<m>`, `<u>`). Any `S.M.` / `S..U` from the parent was treated as a parent-side change, even though those flags describe the submodule's internal worktree, not the parent's index.
- **Lesson**: Porcelain v2's submodule sub field is a 4-character status — `S<c><m><u>`. `c` (commit pointer changed in parent index) is the only flag that is a parent-side change; `m` (work tree dirty) and `u` (untracked content) belong to the submodule's own diff section. Always parse all three flags and gate parent-side surfacing on `commitChanged === true`. `--ignore-submodules` is too coarse — it would also drop legitimate `c=C` events.

### 2. Time-based caches alone cannot deliver "see latest changes after FS mutation"
- **Problem**: A 250 ms request-level Git Diff cache returned stale results when the user modified a file and immediately re-entered the Diff view. Even with the inner fingerprint cache being mtime-aware, the outer time cache short-circuited before the fingerprint check.
- **Cause**: Time-based TTLs answer "how stale am I willing to be" without knowing whether anything actually changed. The fingerprint cache is correct in isolation but is reachable only when the outer cache misses, so the time TTL effectively bounded freshness from above.
- **Lesson**: Real-time-sensitive caches need an *event* invalidation source, not a *time* invalidation source. Pair the cache with a recursive `fs.watch` per active cwd (LRU-bounded so inotify limits stay safe on Linux), debounce raw events, and clear the request-level + fingerprint caches on each window. Keep `force=true` available as a deterministic backstop for subpage entry where the watcher may not yet have observed an FS event before the call lands.

### 3. Subpage entry should always trigger a freshness fetch, not rely on the cache
- **Problem**: Re-entering Git Diff for a cwd already cached returned the cached snapshot, so a user who edited a file in Project Editor and switched to Diff sometimes saw the pre-edit state.
- **Cause**: The mount effect passed `force: !reset`, which meant first-ever opens (the most common entry) did NOT bypass the cache. Re-renders within the panel did. The semantics were inverted relative to user expectation.
- **Lesson**: For UI surfaces whose entire purpose is "show me the current state," always fetch fresh on entry. The watcher-driven cache invalidation is the steady-state freshness mechanism; force-on-entry is the cold-boot guarantee. The two layered together cover both transient race windows (file just changed, watcher hasn't fired) and long sessions (file changed while view was on screen).

### 4. Never static-import `electron` from a module that runs inside a worker_threads context
- **Problem**: After commit `c4625ef` added `import { app } from 'electron'` to `perf-trace-logger.ts`, every git-diff autotest was failing with `Git IPC worker exited with code 1` on the first IPC call. Worker stderr was silent. This silently blocked the staleness regression suite and was the single largest debugging detour in this round — it took aggressive bundle patching (injecting an uncaughtException handler before the require) to surface the underlying `Cannot find module 'electron'` error.
- **Cause**: `git-utils.ts` imports the perf-trace-logger, and `git-utils.ts` is loaded inside the `git-ipc-worker` thread. Electron's worker_threads runtime cannot resolve `require('electron')`; the synchronous require at module-eval time threw before any uncaughtException handler the entry script registered could attach, so the worker died silently.
- **Lesson**: For any module that may be loaded inside a Node Worker thread (anything in `git-utils.ts`'s import graph), `electron` must be resolved lazily via `require('electron')` at call time and gated by `worker_threads.isMainThread`. A static `import { app } from 'electron'` will load fine in main and crash invisibly in the worker. The same rule applies to other Electron-only modules. When debugging silent worker exits, the first diagnostic to add is a `process.on('uncaughtException', …)` handler at the very top of the worker entry, written **before** any other `require()` — and remember TypeScript / esbuild hoist all `import` statements above subsequent statements, so to truly run handlers first you must edit the bundled output or the entry's `require` order directly.

### 5. Per-thread perfTraceLogger singletons must not race on the same `latest.txt`
- **Problem**: After fixing the worker crash, the runner's trace inspection silently picked up the wrong trace file. Main wrote one trace; the worker overwrote `latest.txt` to point at its own (which was missing the main-side `fs-watch-event` records). The GDS-12 assertion failed despite the event firing correctly.
- **Cause**: Each Node Worker has an independent module cache → its own `perfTraceLogger` singleton. Both main and worker called `start()`. The shared trace-root resolver honored `ONWARD_REPO_ROOT` from inherited env, so both wrote into `<repoRoot>/traces/perf/`, racing for `latest.txt`.
- **Lesson**: Process / thread-scoped singletons that touch a shared output directory must hard-pin their output by context. Worker traces should always go to a worker-specific directory (e.g., `${TMPDIR}/onward-traces-perf-worker`) regardless of env vars; only the main thread should write to the project's `traces/perf/`. Test runners that inspect traces should know about both sides and accept events from either trace file.

### 6. Bug-fix work that unblocks a broken test runner WILL surface previously-hidden regressions
- **Problem**: After the worker fix, three additional subpage-navigation assertions (SN-05, SN-06, SN-11) started failing — none of them were in the v0.3 known-failure list. Initial reaction was to suspect the new code; closer read showed the failures were unrelated to my changes.
- **Cause**: Before the fix, every git-diff autotest crashed at the first `git:get-diff` IPC call, so the SN-05/06/11 assertions were never reached. They had likely been red since whichever commit introduced them.
- **Lesson**: When you ship a fix that lets a previously-broken test runner advance further, you will inherit a wave of "new" failures that were always there. Triage them quickly — adopt them into the known-failure list with a clear "newly surfaced after X" note rather than treating them as your bug. The honest accounting ("my fix didn't cause this, but my fix is what surfaced it") protects the next debugger from chasing the wrong cause.

### 7. Subpage-active state must derive from "is target panel still open", not from "panel transition edges"
- **Problem**: The `activeSubpage` sync effect in `TerminalGrid.tsx` was an edge-detector: when a panel transitioned `false → true`, it called `setActiveSubpage(targetId)`. But when the user clicked Diff while autotest's Editor auto-open was still resolving its async cwd lookup, Editor's `false → true` edge fired AFTER Diff's, so the effect clobbered `activeSubpage='diff'` with `'editor'`.
- **Cause**: Edge-detection assumes panels open one at a time. In practice, async auto-open + user clicks routinely overlap. The "latest edge wins" semantics are wrong when the latest edge isn't the user-intended target.
- **Lesson**: Sync effects that mirror state into a derived value should validate that the current value is *still valid* (i.e. its panel is still open) before considering re-derivation. Only sync when the current value is stale. This preserves explicit user intent across racing async opens. The pattern looks like: `if (current is still valid) return; else pick from open panels by priority`.

### 8. SubpageSwitcher button "current" prop must come from the authoritative source, not via a callback round-trip
- **Problem**: SN-05's diff-button-disabled assertion failed because the SubpagePanelShell received `current` from a `panelShellStates[activeSubpage]?.current` lookup. When the destination panel had not yet published its panel-shell state via `useLayoutEffect`, the lookup returned the previously-active panel's state (with its own `current='editor'`), so the diff button rendered as not-current.
- **Cause**: The codebase round-tripped a piece of state — "which subpage is current" — through each panel publishing its own `current` field via a callback. The authoritative source (`activeSubpage` in TerminalGrid) was already known synchronously; routing it through a publish-subscribe sequence introduced a one-frame lag that broke the test's synchronous read.
- **Lesson**: When you have a single source of truth (here, `activeSubpage`), pass it directly to the consumer instead of letting each subordinate component re-derive and publish it. Reserve callback round-trips for state the parent cannot synthesize itself.

### 9. Per-runner `mktemp ONWARD_USER_DATA_DIR` isolation is the FIRST thing to verify when an autotest passes locally and fails in a re-run
- **Problem**: After fixing the SubpageSwitcher race, SN-02/SN-04 started failing on a *re-run* even though they passed on a *first run*. The first run set `tab.activeSubpage='diff'`, persisted that to the user-data dir, and the second run loaded it back via `subpageRestoredRef`, restoring Diff while Editor was also auto-opening — exactly the multi-panel race the new effect was designed to handle, but with the user's intent now ambiguous (was Diff or Editor the target?).
- **Cause**: The runner did not set `ONWARD_USER_DATA_DIR=$(mktemp -d ...)` per the v0.3 hard rule; it shared the global Onward dev user-data dir across runs. State from one test polluted the next.
- **Lesson**: Before chasing app-side behavioral fixes for a "flaky" autotest, run `grep ONWARD_USER_DATA_DIR test/run-<suite>-autotest.sh`. If the runner doesn't `mktemp -d`, that is the bug — not the app. Isolated user-data dirs are how the regression suite stays deterministic; runners that skip it are landmines that turn unrelated PRs into "test broke things" investigations.

### 10. Worker → main perf-trace aggregation: postMessage envelope + per-thread tid lane in main's logger
- **Problem**: After fixing the per-worker trace file race (lesson #5), the next pain point appeared: each worker still wrote its OWN trace file under `${TMPDIR}/onward-traces-perf-worker/`, so a single autotest's events landed across N files (one per worker). Runners had to grep multiple paths, and Perfetto SQL couldn't analyze the workers' work in the same timeline as main.
- **Cause**: Each worker's `perfTraceLogger` was a separate module instance with its own writeStream. There was no aggregation point.
- **Lesson**: For trace systems that span main + workers, the worker should NEVER write its own file. Have the worker's `record()` lazy-detect the worker context and forward via `parentPort.postMessage({event:'trace', name, data, source})`. The main-side worker-client (where the worker was instantiated) listens, replays through main's `perfTraceLogger.record(name, data, {tid: WORKER_TID.X, threadName: 'X-worker'})`. Allocate a stable per-worker `tid` so each worker shows up as its own thread track in Perfetto UI. The pattern was already proven for the ripgrep worker — it just needed to be generalized to the rest of the worker family.

### 11. Process-wide singletons that carry FS watchers belong on the main thread; mark worker-side calls as no-ops with a one-time warning
- **Problem**: After moving the `git-diff-cache-invalidator` `registerWatch` call to the main IPC handler (so the FS watcher could fire IPC notifications to the renderer), the worker's `wireGitDiffCacheInvalidatorOnce` still tried to attach a listener to its OWN copy of the singleton. That listener could never fire (no watcher on the worker side), but it was also a quiet trap — a future refactor calling `registerWatch` from the worker would hit dead code.
- **Cause**: A naive global singleton doesn't know which thread it lives in. Both the main and worker module instances expose the same API surface, but only one of them can functionally register watchers (the main one) because only main can talk to the renderer.
- **Lesson**: For singletons that depend on main-process-only resources (BrowserWindow, ipcMain, the app's IPC channels), gate every public method with `isMainThread`. Worker-side calls become no-ops with a `console.warn` on first invocation per cwd/listener. The warning is the difference between "silently inert" (next debugger spends 30 minutes hunting) and "obviously misconfigured" (next debugger reads the warning and moves on).

### 12. Don't trust the user's literal description as the full bug surface — go look at the actual repo state
- **Problem**: The user reported "submodule appears modified when only the parent was modified" in `/Users/yingyun/Projects/Project_Forward`. I parsed `git status --porcelain=2`'s `<c><m><u>` flags and shipped a fix that handled the three documented scenarios (parent-only, submodule-internal-only, both). The fix was correct *for the scenarios it covered* and passed the synthetic GDS-* fixture. But Project_Forward's actual shape was a fourth scenario I hadn't enumerated: the submodule was declared in `.gitmodules`, the parent commit referenced it, but `git submodule deinit -f` had emptied the working tree and removed the inner `.git` pointer. The directory existed; it was just no longer a git repo. My parent-side filter was correct, but a separate code path in `collectSubmodulesFromGitmodules` was discovering the path from `.gitmodules` and falling back to "treat as a submodule entry" because the only check was `existsSync(subRepoRoot)`. Codex's review caught this in seconds by walking the actual repo state; I had not.
- **Cause**: My loop was: (a) read user's literal phrasing → (b) read porcelain v2 docs → (c) write fix for the documented states → (d) validate on a synthetic fixture I built myself. The synthetic fixture mirrored my mental model of the bug, not Project_Forward's actual shape. Step (d) cannot catch step (a/b/c) blind spots — by design, my fixture validated my understanding, not the world.
- **Lesson**: For bug fixes anchored to a specific real-world repo state, the validation loop must include reading that real-world state, not just synthetic fixtures. Concretely: before designing the fix, run `git status --porcelain=2`, `git submodule status --recursive`, `cat .gitmodules`, and `ls -la modules/<sub>` on the user's reported directory (or ask them to). Then enumerate which states differ from "happy submodule" and write fixture cases for each. The synthetic fixture then covers the OBSERVED state space, not just the documented one. Two minutes of reading the user's repo would have surfaced "this is a deinit-ed submodule" before any code was written. The cost of skipping that step here was a follow-up review round, an extra fixture variant, and a real-world false positive that would have shipped to the user.

### 13. The Git read-side surface needs unification — `getGitRepoMeta`, `parseStatusPorcelainV2Z`, `collectSubmodulesFromGitmodules` each carry partial submodule semantics that drift apart
- **Problem**: The submodule false-positive bug had at least three independent code paths that needed agreement: (a) `parseStatusPorcelainV2Z` decides which entries are submodule rows from `git status` output; (b) `collectSubmodulesFromGitmodules` discovers submodules by parsing `.gitmodules` and `getGitRepoMeta(subRepoRoot)`-validating; (c) `filterMeaninglessSubmoduleEntries` decides whether a parent-side entry is "meaningful" based on `<c><m><u>`. Each of these functions has its own conception of "is this a submodule?" Codex's fix to (b) was orthogonal to my fix to (a) and (c) — each fix patches a different node in the same conceptual graph, with no enforcement that they agree.
- **Cause**: The codebase has accumulated submodule logic incrementally as features (Git Diff, Git History, Project Editor scope, Quick Open) discovered they each needed slightly different views. There is no single `GitRepositorySnapshotService` (or similar) that owns the answer to "given a working tree path, what is the canonical list of (parent, submodule, children, status, sha) tuples?" Each caller cobbles together its own version, and the divergence shows up exactly here — when a corner-case state (deinit-ed submodule) breaks on whichever paths happened not to converge.
- **Lesson**: This is architectural debt, not a bug. The right long-term move is to introduce a unified `GitRepositorySnapshotService` (or equivalent) on the main thread that produces an immutable, fingerprinted snapshot of `{ parent, submodules: [{ path, isInitialized, isRepo, parentSha, headSha, flags }], …}` for any working tree path. All read-side consumers (Diff, History, Editor scope, Quick Open) ask the service rather than re-implementing porcelain-v2 parsing. The snapshot becomes the single place where corner cases like "declared in .gitmodules but not initialized," "initialized but unborn HEAD," "submodule with submodule-of-its-own pointer skew," etc. are enumerated and tested. Until that exists, expect this exact pattern of "fix one path, miss another" every time a new submodule scenario shows up. Track this debt explicitly so the next regression in this area gets the unification done rather than another patchwork fix.

### 14. Phased architectural refactors: ship the service + a compatibility wrapper before migrating individual consumers
- **Problem**: After lesson #13 identified the fragmentation, the temptation was to migrate every read-side consumer (Diff, History, Editor scope, Quick Open) to the new service in one big atomic change. That would have required coordinated updates across ~8 regression suites and risked weeks of ratcheting through unrelated test breakages.
- **Approach taken**: Extract `electron/main/git-repository-snapshot-service.ts` as the canonical answer-owner. Migrate ONLY `loadGitDiff` end-to-end (the highest-value consumer, fully covered by GDS regression). Convert `detectSubmodulesRecursive` into a thin compatibility wrapper that pulls the legacy `GitSubmoduleInfo[]` shape from a snapshot — every other consumer (`getGitHistory`, the `getSubmodules` IPC, etc.) keeps working unchanged because the wrapper preserves the API. Wire the snapshot's own cache into the existing `invalidateGitDiffCache` watcher fan-out so a single FS event invalidates request cache + single-repo cache + snapshot cache in lockstep — there is no second freshness invariant to maintain.
- **Lesson**: For high-blast-radius unification, "phase 1 = new service + behavior-preserving compatibility wrapper" is the right shape. It establishes the architecture, lets the new service grow independent test coverage, and lets later phases migrate one consumer at a time as small, independently verifiable changes. The compatibility wrapper is NOT technical debt as long as it's a shim (zero logic, derives from the canonical answer); it BECOMES debt the moment someone adds branching logic to it. A test like GDS-16 that only asserts "the new service was actually invoked" (via trace event) is enough to gate-keep against regressions where someone accidentally bypasses the service for performance or convenience.

### 15. Dynamic `require()` does NOT survive electron-vite/Rollup output renaming — use static circular imports instead
- **Problem**: The first attempt at the `loadGitDiff` → snapshot service migration used `require('./git-repository-snapshot-service')` inside a function body to sidestep a circular import between `git-utils.ts` and the new module. Source-level typecheck passed; dev build packaged successfully; but the FIRST `git.getDiff` IPC call at runtime crashed with `Cannot find module './git-repository-snapshot-service'`. Every subsequent GDS test failed for the same reason. Required two clean rebuilds + a circular-import audit to recover.
- **Cause**: esbuild content-hashes output chunks (`git-utils.ts` becomes e.g. `git-utils-B-4InHnx.js`). Static `import` statements participate in the dependency graph and the bundler rewrites their resolved paths to match the renamed chunks. Dynamic `require(path)` is opaque to the bundler — the path string is a runtime input, never analyzed, so it gets emitted verbatim. At runtime the resolver tries to find a literal `./git-repository-snapshot-service.js` in `out/main/` and fails because that name no longer exists.
- **Lesson**: For circular dependencies in this codebase's electron-vite + Rollup pipeline, ALWAYS use static `import` statements. ESM live bindings handle circular imports correctly as long as the imports are accessed inside function bodies (not at module-eval time) — both modules finish evaluating before the first call lands, and bindings resolve lazily. Reserve dynamic `require()` only for cases where the path is genuinely runtime-determined (plugin loading, etc.), and verify those work in production builds. `pnpm typecheck` won't catch this — it reads source files, not bundled output. The fast smoke test for a module-resolution issue is "does the dev build's first IPC call succeed?" — these failures explode at first call, never at module-eval, because module-eval-time code paths happen to not reach the bad require.

## 2026-04-30: WebGL context lost/restored lifecycle for the "blank Task after desktop swipe" bug

### 1. Never dispose the WebglAddon synchronously inside the `webglcontextlost` handler
- **Problem**: The original recovery path called `disposeWebgl()` the instant `webglcontextlost` fired on the WebGL canvas. Eighty milliseconds later it tried to recreate the addon. The new addon attached to a canvas whose GL context was still in `isContextLost() === true`, every draw call silently no-op'd, and Chromium's compositor showed the dead GPU tile as a "broken image" placeholder. macOS Spaces and Windows virtual desktop swipes hit this path probabilistically — once the GPU reclaimed the surface, recovery never escaped.
- **Cause**: Disposing the addon causes xterm to swap its renderer service back to the DOM renderer, which detaches the WebGL `<canvas>` element from the DOM. Any listeners we'd attached to that canvas (including `webglcontextrestored`) die with it. The browser's later `webglcontextrestored` event fires on a destroyed node and reaches no one. Even if we tried to recreate immediately, browsers don't synchronously restore the GL context — `restoreContext` is async, so the new addon always lands on a still-lost surface.
- **Lesson**: Keep the addon alive on `webglcontextlost`. While the GL context is lost, xterm's render calls become silent no-ops (the last frame stays on the compositor as the user-visible state) — that is acceptable. Defer dispose-and-recreate to the `webglcontextrestored` handler, then immediately call `terminal.refresh(0, terminal.rows - 1)` to force a draw. The canvas + our listeners survive the entire round trip, so recovery is reliable. This pattern applies to every consumer of GPU surfaces (xterm WebglAddon, Mermaid pan/zoom, future viewers) whose dispose path tears down a parent renderer.

### 2. `event.preventDefault()` on `webglcontextlost` is what makes Chromium attempt restore
- **Problem**: Even after restructuring the lifecycle, the autotest's lost→restored round trip never completed — `webglcontextrestored` simply never fired. The canvas stayed in lost state forever; manual `restoreContext()` was the only way to drive the recovery.
- **Cause**: The default action for `webglcontextlost` in Chromium is to NOT attempt restoration. The browser interprets "no listener called preventDefault" as "consumer has given up on this context." Without our code calling `event.preventDefault()` inside the canvas-level listener, the browser never schedules a restore, and `webglcontextrestored` is never emitted.
- **Lesson**: Any GPU surface that needs lifecycle recovery must call `event.preventDefault()` synchronously inside the `webglcontextlost` listener. This is a one-line requirement that is easy to forget and silent when missing — there is no console warning, no error, just permanent stuck state. Add it to every canvas you attach a context-loss listener to, even if the listener seems otherwise harmless.

### 3. `clearTextureAtlas()` flags rows dirty — it does not paint
- **Problem**: After a host surface event (visibility change / window focus), our `restoreSurface` path B called `webglAddon.clearTextureAtlas()` and considered the recovery done. The autotest's pixel probe stayed all-white intermittently — `clearTextureAtlas` had run, but xterm never actually drew the buffer.
- **Cause**: `clearTextureAtlas` only invalidates the cached glyph atlas and marks the line cache as needing rebuild. The actual render fires later, when xterm's render scheduler runs — typically driven by a PTY data write or a `terminal.resize()` resulting in `_onRender`. In a test (or a real idle terminal) where neither happens before the user looks again, the canvas stays as-of-last-render, which after a phantom-blank or compositor invalidation is empty.
- **Lesson**: After any host-surface event (`window-focus`, `document-visible`, `page-show`, `webgl-context-restored`), follow `clearTextureAtlas` with an explicit `terminal.refresh(0, terminal.rows - 1)`. The refresh queues a real render of every visible row. xterm/WebglAddon coalesce repeated refresh requests, so the cost is bounded and idempotent. The naming asymmetry is the trap: the API reads like a paint-and-clear, but it is closer to "invalidate atlas; rely on next render to repaint."

### 4. Test simulators must drive the real failure path, not a private no-op shortcut
- **Problem**: The previous renderer-surface regression (`TFA-09 / simulateRendererSurfaceLoss`) had been green for nine days while the actual bug — blank Task after desktop swipe — kept reproducing in production. The test simulated "loss" by calling `lifecycle.deactivate('manual-debug')` which synchronously disposed the addon. On the next surface event the lifecycle saw `webglAddon === null`, hit path A, recreated cleanly. The real bug lives in path B (addon still alive, GL context lost beneath it) and path A's lifecycle never even visits it. The simulator silently bypassed the bug it was meant to catch.
- **Cause**: The simulator was written against the lifecycle's internal API instead of the browser primitive that produces the real failure. Real Spaces / virtual-desktop swipes deliver a `webglcontextlost` DOM event on the canvas; the existing simulator never went through that path, so the lifecycle's actual context-loss handler — and all the bugs in it — never executed in tests.
- **Lesson**: When a simulator wraps a fragile boundary (browser GPU events, OS-level signals, IPC handshakes), drive that boundary directly. For WebGL, that means the `WEBGL_lose_context` extension's `loseContext()` and `restoreContext()` — they synthesize the real `webglcontextlost` / `webglcontextrestored` events through the same Chromium pipeline a real GPU event takes. Cache the extension reference *before* calling `loseContext()` because Chromium can return null from `gl.getExtension('WEBGL_lose_context')` after the context is lost, which would otherwise strand the test in the lost state forever. A "simulation" that takes a different code path than the real failure is not a regression test — it is a feel-good no-op that hides the bug it claims to cover.

### 5. Diagnostic instrumentation is not a fix — re-read the patch against the design before claiming it is shipped
- **Problem**: An earlier round of work documented a thorough root-cause analysis ("path B has no `terminal.refresh`; cooldown threshold of 1 strands Win/Linux; canvas-level preventDefault is missing") and shipped 200 lines of `console.warn` instrumentation. Code review (Codex) flagged it: the analysis described the fix correctly but the patch only added logs. None of the four corrective code changes named in the analysis actually existed in the diff. Refactor took an extra full review cycle to land the fix the design already specified.
- **Cause**: The development loop conflated "I now understand the bug well enough to instrument it" with "I have implemented the fix the instrumentation would prove out." The diagnostic phase produced a clear PR description; the implementation phase produced log statements that did not change behavior. Without diffing the patch against the analysis bullet-by-bullet, the gap was easy to miss because every log line *referenced* the missing fix.
- **Lesson**: Before declaring a fix done, perform a one-pass read of the patch with the design doc / analysis open side by side. For every concrete corrective action named in the analysis ("add canvas listener X", "call API Y", "loosen threshold Z to N"), point to the line in the diff that implements it. Logs are not implementations, comments are not implementations, perfTrace events are not implementations. If the answer to "where is the fix for analysis bullet 2?" is "in the next iteration", the patch is not ready for review.

### 6. Run flaky regression candidates 5+ times before drawing conclusions
- **Problem**: A first autotest run showed `TBT-04 / TBT-05` passing and `TBT-06` failing, which suggested H1 (path B no-refresh) was wrong and H2 (real context loss) was the bug. That conclusion led to dropping the `terminal.refresh(0, rows - 1)` fix in path B. A subsequent rebuild showed those same two assertions failing intermittently — they had been timing-flaky all along, depending on when xterm's RAF fired relative to the test's pixel-read. Restoring the refresh stabilized them at 5/5.
- **Cause**: Pixel-probe assertions on WebGL surfaces are inherently timing-sensitive: render scheduling is RAF-driven and varies with GPU pressure, autotest harness load, and any other RAF consumer in the renderer. A single green run is consistent with both "fix is correct" and "we got lucky on RAF cadence."
- **Lesson**: For any assertion that reads pixel state, GPU compositor state, render-scheduling state, or any other RAF-coupled output, the bar for "stable" is ≥ 5 consecutive green runs (in this codebase, `for i in $(seq 1 5); do bash test/autotest/run-X-autotest.sh; done`) before drawing a fix-vs-no-fix comparison. A single green run is a noise-bounded data point, not a stability claim. Apply the same bar before reverting a candidate fix because it "wasn't needed."

### 7. Scope autotest-only WebGL flags narrowly, and gate destructive debug hooks behind autotest mode
- **Problem**: The first patch enabled `preserveDrawingBuffer: true` for every `ONWARD_AUTOTEST=1` run (so any pixel-probe test could read back the framebuffer) and exposed `window.__blankTaskRepro = { phantomBlank, triggerWebglLoss, ... }` unconditionally on every Onward instance. The first leak made perf/latency/stress suites measure non-production WebGL behavior; the second meant any renderer script with `window` access (extensions, devtools snippets, future bundled tooling) could blank a user's terminal at will.
- **Cause**: "It's only enabled in autotest" turned out to be too coarse — autotest is not a single suite, it's a family, and most of those suites measure performance against production-like context options. And "expose useful debug helpers globally during a bug investigation" is the seed of a security boundary erosion that survives long after the investigation closes.
- **Lesson**: Two complementary rules: (a) WebGL context options that affect performance characteristics (`preserveDrawingBuffer`, `antialias`, `powerPreference`, `desynchronized`) should be opt-in per suite, not per autotest mode — keep an explicit whitelist of "pixel-probing" suite names and require new suites to opt in. (b) Any debug-only API that mutates user-visible state must be gated behind `window.electronAPI?.debug?.autotest` (or a stricter dev-only flag). The cost of a one-line gate is far below the cost of a bug filed by a user whose terminal went blank because a paste from the wrong DevTools session called `__blankTaskRepro.phantomBlank()`.

## 2026-05-28: Task surface bugs — OSC phantom cwd leak and cross-tab mirror staleness

### 1. Fire-and-forget IPC paired with speculative renderer state must include a reject / rollback channel
- **Problem**: `electronAPI.git.pushCwd` was implemented as `ipcRenderer.send` (no reply). The renderer's OSC handler dispatched `onward:terminal-cwd-detected` synchronously and committed the cwd to `oscDetectedCwds` + `lastCwd` persistence, *then* fired the IPC. When the main process rejected the raw cwd (`resolveExistingTerminalCwd` returned null for `/Claude is waiting for your input` because the directory doesn't exist), it emitted only a perf-trace event (`MAIN_GIT_STATE_MIRROR_CWD_IGNORED`) and silently returned. The renderer's speculative value was never withdrawn, so the phantom cwd showed in the task header forever and survived across sessions through the persisted `lastCwd`.
- **Cause**: The original speculative-render design covered only the happy path. Any time a renderer makes a optimistic state update gated on a main-process semantic check, the rejection path needs its own back-channel; "no reply" implicitly means "always accepted", which is wrong for any IPC that can be rejected.
- **Lesson**: Whenever a renderer commits state speculatively before a main-process IPC completes (the `<50ms perceived latency` pattern), main MUST emit a reject IPC (e.g. `GIT_STATE_MIRROR_CWD_REJECTED`) carrying enough payload (`terminalId`, `rawCwd`) to identify the speculative entry. Renderer subscribes and rolls back when the still-pinned value matches the rejected one. Audit every existing `ipcRenderer.send` for this pattern — `send` without a reject channel is a NACK miss waiting to happen.

### 2. Observability events that drive UI rollback must travel via IPC, not just perf-trace files
- **Problem**: The main-process rejection was being recorded as `performanceTrace.record(MAIN_GIT_STATE_MIRROR_CWD_IGNORED, …)` only. That writes to `<repoRoot>/traces/perf/*.ndjson`. The renderer cannot read those files, the UI cannot react to them, and they're only useful to a human reading a diagnostic zip after the bug already happened.
- **Cause**: The same event was used as both a "human-readable debugging breadcrumb" and an "implicit signal for the renderer to act on". Those are two different consumers with different transport requirements. Trace events serve forensics; IPC serves live behaviour.
- **Lesson**: Decide explicitly which events are post-mortem-only (perf-trace ndjson) and which gate live UI behaviour (IPC). When a behaviour depends on a signal, send that signal through IPC. Trace files are not a sidechannel the renderer can poll; they are an append-only forensic stream. If you find yourself thinking "the trace already has this", ask "but does anything that reacts to it actually subscribe?"

### 3. External-input parsers cannot fully validate in the renderer — combine syntactic gate (renderer) + semantic gate (main) + reject-IPC loop
- **Problem**: `parseOsc7Cwd` decodes `file:///<path>`; `normalizeTerminalCwdCandidate` rejects relative paths and control characters but accepts any string that starts with `/`. So `file:///Claude is waiting for your input` parses cleanly into `/Claude is waiting for your input`, which the renderer cannot prove is bogus because `statSync` is main-side only. The renderer is structurally incapable of catching free-text-pretending-to-be-a-path.
- **Cause**: Renderer can only do syntactic validation (well-formedness, prefix rules); semantic validation (existence on disk) requires main. Without a feedback loop between the two, every raw OSC payload that survives syntactic checks lands in renderer state, even when main will reject it.
- **Lesson**: For any external-input parser whose output flows into renderer state, design three layers from the start: (a) renderer syntactic gate — cheap, fast, rejects obvious garbage; (b) main semantic gate — `statSync` / network reachability / authority checks; (c) reject IPC — main → renderer notification when (b) rejects, so renderer can undo (a). Document the three layers in the same comment block so the next maintainer doesn't drop one.

### 4. Test assertions on storage / model state are not equivalent to assertions on the visible / rendered layer
- **Problem**: `test/autotest/test-terminal-state-persistence.ts` literally already had `TSP-04b-invalid-osc-cwd-ignored` that pushed `/Claude is waiting for your input` and asserted "AppState's `lastCwd` is not the phantom". The test was green for months because **storage WAS being protected** — what wasn't protected was the renderer's `oscDetectedCwds` map and the resulting `.terminal-grid-adaptive-cwd` visible label, both of which still showed the phantom. The user saw the phantom; the test didn't catch it.
- **Cause**: The test author asserted on the layer that was easiest to read (`appState.load()`), not the layer the user sees (DOM text content). One layer (storage) was correctly guarded; the layer above it (speculative renderer state → DOM render) had no guard at all. The assertion stopped one floor short of the user.
- **Lesson**: When testing a "value X must not appear" property, write the assertion against the most-visible-to-user surface — typically a DOM query against the rendered label, not the data layer behind it. Use `document.querySelector('.terminal-grid-adaptive-cwd').getAttribute('title')` style probes for cwd, branch chip, status colour, task title. Storage assertions are necessary but never sufficient; they prove a fence, but not that no value escaped over the fence into the renderer's optimistic cache.

### 5. Speculative state in renderer (mirror snapshots + cwd aliases) is not atomic across React ticks, and the race amplifies across multi-instance React trees
- **Problem**: `resolveTerminalGitDisplayState` prefers `mirrorSnapshots[canonicalCwd]` over `terminalInfo` and resolves the canonical key through `mirrorSnapshotAliases`. When `/var/...` ↔ `/private/var/...` mapping and a state transition (clean → modified → clean) update in different React ticks, the DOM can read a stale snapshot via the still-old alias even though `terminalInfo` has the fresh truth. Single tab: ~10% of trials in this codebase hit the race. Cross-tab (two `TabTerminalGrid` instances, two independent `mirrorSnapshots`/`mirrorAliases` Records, two effect chains): the race window doubles and reproduces much more often (GSM-18e baseline failed mid-run after GSM-17 cleanup left mirror with stale `added`).
- **Cause**: Two reactive state maps drive one derived rendering decision (`mirror snap` + `alias map` → `gitState`). React batches updates within a tick but does not guarantee atomicity across `setMirrorSnapshots` + `setMirrorSnapshotAliases` calls that originate from different IPC events or different reducer paths. Multi-instance components compound the problem: each instance has its own pair of maps, so consistency must be enforced per-instance.
- **Lesson**: Treat (mirror snapshot, alias map) as a single semantic unit. Either (a) combine them into a single `useReducer` whose action atomically updates both, or (b) drive renders off a `useMemo` that has BOTH maps in its dependency array and returns `null` (= "data not consistent yet") when the snapshot lookup result and the alias map disagree on the current generation. For multi-instance React trees that share a backend pub/sub source, prefer (a) — duplicated state inside a component is a known race, but multiplied state across siblings is a race per sibling.

### 6. Window-global debug APIs that are rebound by `useEffect` must be re-read on every test access — never cached into a local variable
- **Problem**: GSM-18c initially failed because the test did `const appDebug = window.__onwardAppDebug` once, then polled `appDebug.getTabIds()`. After `appDebug.createTab()` fired, the `state.tabs`-dependent `useEffect` in `App.tsx` re-ran and **reassigned `window.__onwardAppDebug` to a new api object with a fresh closure**. The test's local `appDebug` variable still pointed at the old object whose `getTabIds()` returned the stale closure (`[only the original tab]`), so the `waitFor` polled the stale snapshot forever and timed out.
- **Cause**: Two compounding facts. (1) The renderer publishes the debug API by writing it to `window.X` inside an effect, and re-runs the effect (which re-creates the api object) whenever the closed-over state changes — so the api object identity is intentionally unstable. (2) Test code destructured `appDebug = window.X` once and then treated it as a stable handle. JavaScript closures pin the old api object's old closure forever.
- **Lesson**: Tests that interact with `window.__onward*Debug` globals must define a `getApi = () => window.__onward*Debug` helper and call `getApi()?.method()` on every access — never `const api = window.X; api.method()`. The same rule applies to any global that publishes through React effects (most debug APIs in this repo). When designing new debug APIs, document this constraint at the type definition, or use a stable wrapper (`__onwardAppDebug.current`-style proxy) that internally indirects to the latest closure.

### 7. Bug attribution must be evidence-driven, not symptom-narrative-driven — verify which subsystem actually fired
- **Problem**: The user's bug report and the diagnostic zip's `feedback.json` framed the issue as "Claude CLI's OSC 0/1/2 title sequence corrupts the task label". I started reading the OSC 0/1/2 surface (`onTitleChange`, `terminal.title`) and found Onward never subscribes to any of it — locking in TTM-29/30/31 was easy. The real leak was through OSC 7 (`file:///...`), a completely different OSC code that happens to be in the same numerical neighbourhood and that nobody had named in the bug report. Without grepping the perf-trace for `cwd-switched` events and noticing `repoKey: "/Claude is waiting for your input"` being used by `main:git.exec`, I would have shipped a "fix" for OSC 0/1/2 (which weren't broken) and missed OSC 7 (which was).
- **Cause**: Bug reporters describe the program that emits the bytes ("Claude CLI") and the kind of byte it usually emits ("title sequence"), not the actual OSC dialect code (`0` vs `7` vs `633` vs `1337`) that landed in Onward. The bug name acquires inertia and biases the investigator toward the wrong subsystem.
- **Lesson**: When a bug report names a subsystem ("OSC 0/1/2 title"), verify with primary evidence — a perf-trace event, an IPC log, or a `console.log` inserted at the parse site — *which subsystem actually fired*, before designing a fix. Quote the verifying event in the PR description so reviewers can cross-check. Symptom-named bugs ("commit not switching to clean", "task showing wrong title") need root-cause naming ("mirror snapshot stale across alias update", "OSC 7 phantom cwd with no main-rejection rollback") before the fix surface is chosen.

### 8. `run-full-regression.py`'s 180s default `PER_SCRIPT_TIMEOUT_SEC` silently truncates long-running runners
- **Problem**: When `git-state-mirror-latency` was first hooked into the orchestrator with a default timeout, the baseline pass alone takes 80–670s (5 trials × ~10 phases × waitFor budget). The orchestrator killed the runner mid-baseline-pass, leaving a non-empty `traces/test-logs/git-state-mirror-latency-autotest.log` that an unaware reviewer might think "completed" — when in reality the test was guillotined before reaching GSM-13 / GSM-18.
- **Cause**: The orchestrator's `PER_SCRIPT_TIMEOUT_OVERRIDES_SEC` dictionary is a manual whitelist. New long-running runners are silently subject to the 180s default until someone adds an entry. The orchestrator does emit a TIMEOUT result row, but if the consumer only looks at the runner's local log (truncated mid-stream), they miss it.
- **Lesson**: Any new runner that legitimately exceeds 180s end-to-end MUST add an entry to `PER_SCRIPT_TIMEOUT_OVERRIDES_SEC` in the same change set that registers the runner in `SCRIPTS`. Run a one-shot baseline timing measurement (`time bash test/autotest/run-X-autotest.sh`) before deciding the override value; pad by 30–50% to absorb variance. Reviewing the orchestrator's TIMEOUT-row count after each change is a cheap defense.

## 2026-06-01: Idle ~8% CPU render storm — wrong first fix, field-level diagnosis, and test-harness hangs

### 1. A real *mechanism* is not the *root cause* — and a fix is not done until the SYMPTOM is re-measured
- **Problem**: For "idle renderer pinned at ~8% CPU" I saw `setTimeout(500)` armed ~1300×/s whose stack traced to `saveState ← updateState ← AppStateProvider render`, plus React committing ~122×/s. I concluded the loop was "no-op updates" defeating React's `Object.is` bail-out (because `updateState` stamps `updatedAt: Date.now()` + spreads a fresh object), shipped a bail-out (`return prev` when content-equal), declared it fixed — and the CPU was still pinned. The real loop wrote a *genuinely different* value each iteration, so the bail-out was bypassed.
- **Cause**: Two compounding errors. (a) `updatedAt` defeating `Object.is` is a real mechanism and a necessary condition, but I *assumed* the trigger was no-op updates without ever checking whether each update actually changed content. Confirmation bias: a textbook anti-pattern (`updatedAt: Date.now()`) plus a frequency/stack correlation felt like "the" root cause, so I stopped looking. (b) I "verified" with unit tests (which only prove the bail-out logic) and a synthetic autotest where I fed it no-ops myself — neither could fail for the real bug. I never re-measured the actual symptom (renderer CPU) on the fixed build.
- **Lesson**: Distinguish "a mechanism that is real" from "the root cause that is sufficient". Before declaring any perf fix done, re-measure the original symptom on the fixed build (here: relaunch + sample renderer-thread CPU / churn — it must actually drop). A synthetic test that exercises your *assumption* is not verification; only the symptom is. This extends `2026-04-30 #5` (instrumentation ≠ fix) one step: verify against the symptom, not just re-read the patch.

### 2. For a React re-render storm, ask "WHICH state field changes, between WHICH two values" before "who/how often"
- **Problem**: Frequency probes ("setTimeout(500) 1300/s") and call-stack probes ("runs during AppStateProvider render") told me updateState was hot and *where* it ran, but not *why every call was a real change*. I spun on those signals and misdiagnosed.
- **Cause**: Frequency and stack are necessary for scoping but say nothing about the content delta — and the content delta was the entire story.
- **Lesson**: To diagnose a re-render storm, instrument the reducer to log the *field-level `prev → next` diff* (which top-level key changed + the first leaf-level `path: old -> new`), aggregated per second to stay off the hot path, read via CDP `Runtime.consoleAPICalled`. It instantly printed `tabs[0].terminals[0].lastCwd: "D:/x" -> "D:\\x"` — a path-separator flip — which no amount of frequency/stack analysis would have revealed. The root cause was a Windows-only `/` vs `\` mismatch: the OSC writer persisted `/`, the git-watcher writer persisted `\`, and `normalizePersistedTerminalCwd` only validated (never canonicalized), so the two writers ping-ponged forever. Fix: canonicalize the persisted cwd to `/` at the boundary (+ the `Object.is` bail-out). macOS/Linux were unaffected (no `\`).

### 3. Don't couple a focused autotest to the heavyweight "Project Editor must open" suite harness — it hangs
- **Problem**: My first autotest registered an in-app suite. The suite harness only starts after the Project Editor panel opens and its file tree loads; PE didn't open in that run, so the harness logged `waiting-for-open-root` forever and the test "ran" 20+ minutes without ever starting a single assertion.
- **Cause**: The standard E2E harness gates EVERY suite on PE being open. A test whose subject (AppState churn) has nothing to do with PE inherited that gate, and an unbounded `waiting-for-open-root` wait.
- **Lesson**: When a behaviour can be observed without the full PE/suite harness, drive it directly via CDP from a standalone Node orchestrator with HARD deadlines on every wait and a `finally` that always kills the app — so it is structurally incapable of hanging. Reserve the in-app suite harness for things that genuinely need PE open. Bound every external wait; never wait on "PE opened" without a timeout.

### 4. Test infra must not hardcode a CDP port — a leaked zombie can hold it un-killably; and apply data-first to test infra too
- **Problem**: After redesigning the autotest, it failed twice with "CDP renderer target not reachable". My first reaction was to *guess* "cold start of a fresh 200MB exe is slow" and bump the timeout 30→60s — it failed again. Only then did I measure: a zombie process (PID with no resolvable name, un-killable by `taskkill /PID /F`, rc=128) was stuck holding the hardcoded port 9344, so every freshly-spawned app failed to bind its CDP server.
- **Cause**: (a) Hardcoding a fixed debug port means one leaked/zombie process bricks all subsequent runs. (b) I repeated the exact mistake from lesson #1 in this same session — guessing a cause ("cold start") and acting on it before measuring.
- **Lesson**: Pick a dynamic free ephemeral port per run (`net.createServer().listen(0)`), so a leaked process on an old port can never collide; also kill stale same-name instances before launch (single-instance lock would otherwise forward-and-exit, binding nothing). And the data-first rule applies to test infrastructure exactly as it does to product bugs: when a test flakes, measure (who holds the port? did the app bind it? launch it manually on a fresh port to isolate build-vs-environment) before changing knobs.

## 2026-06-02: Git Diff slow on large repos — the cost is process COUNT, not git internals; and fixed-TTL caches are a lie when the op outlasts the TTL

Context: on a corporate Windows machine, opening Git Diff on a large repo (`kar-qemu`: 8145 files, 794 MB `.git`, 1 submodule, **clean working tree**) took ~25 s (root-only 14 s + full 11 s) to show "no changes". CDP-driving the renderer's real `git.getDiff(repo)` under `ONWARD_PERF_TRACE=1` showed a single open fired **69 `git.exec` spawns** (cumulative 139 s, median 923 ms/spawn) and **12 `git.snapshot.capture`** runs — each running the shell-script `git submodule status --recursive`.

### 1. On Windows under EDR/antivirus, the bottleneck is per-process CREATION, not the git work — so the lever is fewer spawns, not faster git
- **Problem**: I first assumed a "more efficient git binary" or git config tuning would help. It would not have.
- **Cause**: An EDR/DLP kernel minifilter stack (here Sangfor aTrust + IsaAgent + `Fp*.sys`/`Ws*.sys` filter drivers — NOT Windows Defender, which already excluded `D:\` and Git) intercepts EVERY `CreateProcess` synchronously: bare `git --version` (touches no repo) measured ~400 ms, `hostname` ~620 ms, `cmd /c echo` ~980 ms. Meanwhile the *internal* work of one `git status` was ~5 ms (trace: `unpack_trees` 0.96 ms, `diff-index` 1 ms). So ~99% of each `git status`'s wall time was process startup tax, and `git submodule status --recursive` was slow purely because it is a POSIX **shell script that forks ~15 helper processes** (`sh-i18n--envsubst` shows in `GIT_TRACE`).
- **Lesson**: Bundling/replacing the git binary (dugite-style) does NOT fix an EDR per-spawn tax — the tax is on process creation, version-independent (and git is GPLv2, adding a source-offer duty). The only true fixes are (a) **reduce the number of spawns** and (b) **eliminate spawns entirely (in-process git)**. We chose (a) for now: replace `git submodule status --recursive` with pure-filesystem discovery (read `.gitmodules` + stat `<path>/.git`; `git-submodule-disk-discovery.ts`) → structural discovery went from ~15 spawns to ZERO; and skip `git diff --numstat` passes when the porcelain status shows no files of that kind (clean repo → 0 numstat spawns). Peer evidence: GitKraken publicly **migrated away from libgit2 back to the native git executable**; VS Code's git extension also shells out per-command and fights the same Windows process storm — so "fewer, cheaper spawns + a real cache" is the industry-validated path, and git's built-in `fsmonitor--daemon` (≥2.37) is the one mechanism that makes a *native* status cheap (it does not reduce spawn count).

### 2. A fixed-TTL cache is worse than no cache when a single production of the value can take longer than the TTL
- **Problem**: The structural snapshot cache used a 5 s TTL. On this repo a single capture took 8–14 s, so by the time the next phase/open asked, the entry was already expired — the cache could never hit (12 captures for 5 opens). The two-phase Diff load (root-only then full) also passed `force: true` to BOTH phases, re-running the expensive capture twice per open.
- **Cause**: Time-based TTLs answer "how stale am I willing to be," which is meaningless when the producer is slower than the staleness budget. They also conflate two independent freshness axes: diff *content* (changes when files change) vs repo *structure* (changes only when `.gitmodules` changes). `force` was being applied to both.
- **Lesson**: For any cache whose value-production can outlast the intended TTL, do NOT use a clock. Use an **event/fingerprint invalidation** keyed on what actually changes: here, the snapshot is valid as long as the repo's `.gitmodules` `mtimeMs:size` token is unchanged (one `fs.stat`, zero spawns), with the FS watcher fan-out as the backstop — no TTL at all. And keep the two freshness axes separate: the Diff `force`-on-entry now refreshes content only and lets both phases reuse ONE structural capture. This generalizes lesson `2026-04-25 #2` ("real-time caches need an event source, not a time source") to its sharper form: a TTL shorter than the operation is not just imprecise, it guarantees a 0% hit rate. (Caches whose producer is foreground-and-background-shared must also share the *result*, not just the policy — true cross-thread sharing between the GitStateMirror worker and the diff worker remains follow-up debt; for now both use fingerprint/no-TTL caches within their own thread.)

### 3. Read-only git on the Diff path was re-triggering the background watcher — harden it with GIT_OPTIONAL_LOCKS=0
- **Problem**: The trace showed 7 `git-state-mirror.recompute-status-done` (3–7 s each) firing concurrently DURING the 5 diff opens, contending for the same EDR-throttled spawn lane.
- **Cause**: By default `git status`/`git diff` opportunistically take `.git/index.lock` and rewrite `.git/index`'s stat cache. The GitStateMirror watcher observes that index write as a change event and schedules a status recompute — so the foreground Diff read was kicking off the very background recompute that then competed with it. The mirror worker already set `GIT_OPTIONAL_LOCKS=0` (its `hardenReadonlyGitEnv`), but the foreground diff/status read path did not.
- **Lesson**: Every strictly read-only git invocation (`status`/`diff` against the worktree) should run with `GIT_OPTIONAL_LOCKS=0` so it cannot mutate `.git/index` and self-trigger watchers (git ≥2.15; cross-platform; this is what VS Code's read path does). Keep normal locking ONLY for write paths (hunk `apply`/`checkout`/`add`). Added `getReadonlyExecEnv()` in `git-utils.ts` and routed `getGitStatusPorcelainV2` / `getGitDiffNameStatus` / `getGitDiffNumstat` through it. Note `git diff base head` (commit-to-commit, History) does NOT refresh the index, so it does not need the flag.

### 4. Profile the actual program, not just shell micro-benchmarks — drive the real IPC via CDP
- **Problem**: Shell-timing `git` commands proved the per-command cost but not how the app *composes* them per open.
- **Lesson**: Launch the existing packaged dev build with `ONWARD_PERF_TRACE=1` + `ONWARD_REPO_ROOT=<repo>` (so traces land in `<repo>/traces/perf/`) + `--remote-debugging-port=<dynamic>`, connect a raw-WebSocket CDP client (Node 22 has global `WebSocket`), and call `window.electronAPI.git.getDiff(repo, {scope, force})` / `git.getFileContent(repo, file, repoRoot)` directly via `Runtime.evaluate`. This exercises the exact program path against the exact slow repo with zero UI gymnastics, and the perf trace records the internal spans (`git.exec` count, `git.snapshot.capture` count) that turn "feels slow" into "69 spawns, 12 captures." Beware `Out-File -Encoding utf8` in Windows PowerShell adds a BOM — read the CDP `webSocketDebuggerUrl` straight from `/json/list`, don't round-trip it through a BOM'd file. To measure file-CLICK latency, profile against a DIRTY repo (a clean repo has no files to click) and pull the file list from `getDiff().files`, then call `getFileContent` on a few entries (first-click vs re-click).

### 5. Background prefetch that shares a priority + concurrency lane with foreground requests is a priority-inversion time bomb
- **Problem**: After the snapshot-storm fix, the FIRST file click in Git Diff still took 18-29s on the EDR box (subsequent clicks + re-clicks were instant — the content cache worked). The diff content cache has a `gitDiffPrecomputeScheduler` that eagerly prewarms ALL changed files' bodies in the background. The user's click was queuing behind that prewarm burst.
- **Cause**: TWO layers conspired. (a) `git-ipc-worker-client.ts::getFileContent` hardcoded `priority: 'high'` for EVERY caller — foreground click AND background precompute alike — and gave them ONE shared `repoConcurrencyLimit: 1` per-repo slot. The precompute enqueued ~N file fetches first (during enter/list), so the later foreground click sat FIFO behind all of them through the single slot. (b) Even the inner worker `getGitFileContent` → `readGitFileByRef` `cat-file` spawns carried NO scheduling meta (defaulted to `priority:'normal'`), so the git-runtime couldn't prioritize them either. The trace was unambiguous: during the 18s click, 10 `cat-file/low` ran but only 1 `cat-file/high`, and the single get-file-content IPC span ate the whole window.
- **Lesson**: Any eager background prefetch MUST run in a strictly lower priority AND a SEPARATE concurrency lane from foreground requests, or it will starve the very interaction it was meant to accelerate. Concretely: (1) thread a `priority` through the request options end-to-end (foreground defaults 'high', precompute passes 'low'); (2) give the low-priority lane its OWN per-repo key (`${repoKey}::precompute`) so a foreground 'high' request always finds a free concurrency-1 slot instead of queuing behind the prewarm; (3) scope dedupe keys by priority so a 'high' request never coalesces onto a QUEUED 'low' task and silently inherits its priority. Result on the EDR box: first-click 18-29s → ~1.1s, with 56 background `cat-file/low` still running concurrently and not blocking the 6 foreground `cat-file/high`. The fix is the renderer-scheduling rule from CLAUDE.md ("Prompt input has the highest priority … background output must not continuously promote") applied to the git read path: background prewarm is the lowest-priority lane, always.

### 6. When `repoRoot` is already known, re-validating the repo on every file read is pure EDR tax
- **Problem**: `getGitFileContent` ran `checkGitRepository` (`git rev-parse --is-inside-work-tree`) on every single file-content request even though the Diff list path always passes a resolved `overrideRepoRoot`.
- **Lesson**: Trust a caller-supplied repo root and skip the validation spawn — a bad root just makes the subsequent `cat-file` fail with a clear error, so the rev-parse is redundant. On a normal machine this is noise; under an EDR per-spawn tax of ~1-3s it is a visible per-click cost multiplied across every prefetched file. Audit every "defensive re-check" on a hot path for "does the caller already know this?"

## 2026-06-02: Sub-second Git Diff ENTER on EDR via warm-cache-serve (background does the work, foreground reads it)

Goal: open Git Diff in <1s even on a big nested-submodule repo (kar-qemu: 480 changed files incl. a submodule), on the EDR box where every git spawn is ~1-3s. The only way to <1s is ZERO git spawns on the visible path → serve a background-warmed cache. Cold open (nothing warmed yet, or just-invalidated) recomputes — the explicitly-accepted exception.

### 1. A warm cache is useless if (a) it expires before the user reaches it, (b) the open forces past it, or (c) the warm key ≠ the open key
- **Problem**: `warmDiffCache` already existed (fired ~2s after a terminal's git state changed) but the open was still 6.8s. Three independent defeats: the request cache TTL was **250 ms** (warm gone instantly), subpage entry passed **`force:true`** (bypasses the cache), and the warm warmed only `scope:'full'` while the entry's two-phase asks `scope:'root-only'` first (**key mismatch** → cold first paint).
- **Lesson**: For a warm-then-serve design, all three must align: (a) make the cache EVENT-invalidated (watcher) with a long TTL backstop, not a short clock — a TTL shorter than "time from warm to open" guarantees a 0% hit rate; (b) serve on entry WITHOUT force (stale-while-revalidate: paint the warm cache instantly, then fire ONE silent background `force` to self-heal a missed watcher event and honor "entry shows fresh data"); (c) warm exactly the keys the entry reads (here, BOTH `root-only` and `full`). Result: kar-qemu enter 6.8s → ~440 ms (warm), most enters <15 ms.

### 2. Background prewarm MUST run in a separate priority+concurrency lane, or it blocks the very foreground request it accelerates — at EVERY layer
- **Problem**: After fixing #1, the warmed `::full` served instantly but `::root-only` thrashed (1.8-13 s per enter). The trace showed the enters were cache HITS yet measured slow — they were QUEUED in the git-ipc-worker behind the precompute's `getDiff(force:true)`, which holds the per-repo concurrency-1 slot while it recomputes. The worker-client hardcoded `priority:'high' + repoConcurrencyLimit:1 + repoKey:cwd` for BOTH foreground enter and the background precompute/warm, so they shared one slot, FIFO. (Same priority-inversion class as the file-click bug, one layer up.)
- **Lesson**: This is the THIRD place the same rule had to be applied (file-content fetch, then file-content worker-client, now diff worker-client + warm): every eager background producer needs its OWN lane — a distinct `repoKey` (`${cwd}::diff-precompute`) AND `priority:'low'` — so a foreground request always finds a free concurrency slot. Thread a `background`/`priority` flag through the request options end-to-end; never let "high priority for everyone" stand in for actual lane isolation. Also: the precompute must read with `force:false`, not `force:true` — the invalidator already cleared the cache before scheduling the burst, so a non-forced read recomputes fresh AND stores (warms); forcing re-invalidates the cache it is trying to warm.

### 3. `git status` rewrites `.git/index` — every read-only status path needs GIT_OPTIONAL_LOCKS=0 or it self-invalidates the warm cache
- **Problem**: The trace showed the warm cache being invalidated by the GitStateMirror watcher firing on `.git/index` *update* events (`index.lock` create → `index` write → `index.lock` delete). Source: the terminal git-status pollers (`getGitBranchAndStatus` / `getGitStatusSummary`) ran `git status` with normal locking, opportunistically rewriting the index, which the watcher saw as a change → invalidate diff cache → warm defeated.
- **Lesson**: EVERY strictly read-only `git status`/`git diff` on a watched repo must run with `GIT_OPTIONAL_LOCKS=0` (the mirror worker already did; the diff path and now the terminal-status pollers do too). Otherwise the read silently mutates `.git/index` and triggers the watcher that invalidates your caches — a feedback loop that's invisible until you trace `watcher-fire {path: .git/index, kind: update}`.

## 2026-06-03: Windows Git Diff caching parity with macOS — ctime, nested-submodule .git churn, and self-inflicted prewarm wipes (multi-agent workflow)

A multi-agent investigation workflow (4 parallel code-investigators + peer research + adversarial verifiers + synthesis) found why Windows Git Diff caching was worse than macOS: "Render: loaded" rare (clicks served by MAIN cache not the renderer cache), first-enter slow, background warm "ineffective." A real user-session perf trace (`perf-0022`) was the decisive evidence over pure code reading.

### 1. ctime in a change-fingerprint is a Windows-only invalidation storm; macOS hides it
- **Problem**: The GitStateMirror change-fingerprint stat token was `mtimeNs:ctimeNs:size:mode`. On NTFS, **ctime is bumped by metadata-only touches that never change mtime** — Defender/EDR open-scan-close, Windows Search, Explorer attribute reads. Each touch flipped the fingerprint → `mirror-update` → diff-cache invalidation (every layer wiped). On macOS/APFS ctime moves in lockstep with mtime, so identical background activity never flipped it — the bug was invisible on the dev's primary platform.
- **Lesson**: Never include ctime in a content-freshness fingerprint. Key on `mtime + size` (+ mode + the already-hashed `git status` text as backstop) — exactly what git and VS Code do. A real edit always bumps nanosecond mtime. This is a platform-divergence class: a token that is stable on APFS can be a thrash engine on NTFS. (`git-state-mirror-change-fingerprint.ts`, body-cache token in `git-state-mirror-worker-entry.ts`.)

### 2. A recursive worktree watcher must filter NESTED submodule `.git/` the same as the top-level `.git/`
- **Problem**: The decisive trace finding — all 10 invalidations in the user session fired on `…/kar-qemu/src/third_party/KAR/.git/index.lock` (the SUBMODULE's git dir). `classifyEventPath` only recognised the TOP-LEVEL `.git/` (it correctly dropped `kar-qemu/.git/index.lock`); a nested submodule `.git/` fell through as a "worktree change" → recompute → invalidation → cleared the renderer body cache on every click (why "Render: loaded" was rare). The churn source is platform-independent (any git activity in the submodule — the user's own, or our probes — creates `index.lock`), so read-only-hardening our own probes is necessary but NOT sufficient; the watcher filter is the robust fix.
- **Lesson**: A recursive FS watcher over a parent worktree also sees every submodule's `.git/` internals. Classify the subpath after the LAST `.git/` segment (top-level OR nested) and apply the same drop rules (lockfiles, objects, tmp, internal). Otherwise submodule git noise looks like worktree edits. (`classifyEventPath` in `git-state-mirror-worker-core.ts`.)

### 3. "macOS uses a render cache, Windows uses a main cache" was a symptom, not an architecture difference
- **Problem**: The user observed Windows clicks served by the MAIN content cache while macOS served from the RENDERER memory cache ("Render: loaded"). It looked like a deliberate platform divergence.
- **Lesson**: There is no platform branch — both use the same layers (renderer fileContents → main content cache → request cache → snapshot). The renderer layer only serves when it has NOT been invalidated; macOS hit it more purely because its invalidation rate was low (no ctime storm, FSEvents coalescing). The fix for Windows is NOT to move content into the renderer — it is to stop over-invalidating (lessons #1, #2) so the existing renderer layer survives between clicks. Authoritative content belongs in MAIN (matches VS Code/GitLens: cache in the extension host, hand the renderer only the open diff's models) — it avoids a serialize-over-IPC round-trip, survives view teardown, and can be pre-warmed before the view exists. When two platforms "use different caches," first check whether it's actually "same cache, different hit rate due to invalidation volume."

### 4. A stale-while-revalidate that force-refreshes on every open can wipe the very prewarm it depends on
- **Problem**: My own prior fix added an unconditional `loadDiff({force:true})` background revalidate on every Git Diff open. A forced `getDiff` routes through the IPC handler's `invalidateContentCacheForProject`, which drops every prewarmed per-file body — so the user's first click cold-missed right after the warm filled the cache (invisible on macOS where the re-cold is sub-second; multi-second on EDR Windows).
- **Lesson**: SWR's "revalidate" must be a cheap freshness check that does NOT invalidate sibling caches. Don't force-on-every-open when an event-driven watcher already refreshes on real mutation; if a guaranteed refresh is needed, gate it on watcher-health/staleness, and decouple "re-read the list" from "wipe the content bucket." A revalidate that nukes the cache is worse than no revalidate.

## 2026-06-17: Environment-caused test failures — pnpm 10 silently skips dependency build scripts

### 1. pnpm 10's default is to ignore ALL dependency build scripts — the Electron binary never downloads on a fresh install
- **Problem**: A clean `pnpm install` printed `Ignored build scripts: …, electron, …` and skipped every dependency postinstall. `node_modules/electron` had no `path.txt`/`dist/`, so any runner resolving `require('electron')` at runtime failed at 0 s — looking like a contract failure but actually environment drift. No `.npmrc`, no `pnpm.onlyBuiltDependencies` existed to opt back in.
- **Lesson**: On pnpm ≥ 10, build scripts must be explicitly allowlisted via `pnpm.onlyBuiltDependencies` in `package.json` (committed → applies on every platform + CI). Allowlist only the scripts that must run AND succeed via prebuilt download (electron, esbuild, @vscode/ripgrep, electron-winstaller, plus prebuilt-shipping natives node-pty / @parcel/watcher). Leave no-op donation banners (core-js, es5-ext) out.

### 2. Never allowlist a native module whose build is redundant with the project's own `electron-rebuild` postinstall
- **Problem**: Allowlisting `better-sqlite3` forced its **Node-ABI** source build. System Node v26 has no better-sqlite3 prebuilt → fell back to `node-gyp` → which died on a **broken Homebrew Python 3.14** (`pyexpat` libexpat symbol mismatch) → `pnpm install` exited 1. But nothing Node-side consumes better-sqlite3: the packaged app's copy is rebuilt against **Electron's ABI** by the project's `postinstall` (`electron-rebuild -w node-pty,better-sqlite3`), which fetches a prebuilt (no Python).
- **Lesson**: Distinguish "native module the Node process needs" from "native module the Electron app needs." The latter is owned by `electron-rebuild`/electron-builder, ABI-rebuilt at build time — do NOT also force a Node-ABI build via `onlyBuiltDependencies`. When a source compile is unavoidable, ensure node-gyp uses a working Python (Apple's `/usr/bin/python3` worked here; Homebrew's was broken) — but prefer prebuilt paths so the host compiler/Python is irrelevant.

### 3. A from-scratch `rm -rf node_modules && pnpm install` is the only faithful proof of "fresh clone / CI / Windows" health
- **Problem**: `git status` is clean even when the installed dependency tree has drifted from the committed spec (patches unapplied, binaries missing) — because `node_modules` isn't tracked, only the spec (`package.json` + `patches/`) is. The bug only surfaces in the built app.
- **Lesson**: Validate dependency-config changes with a clean reinstall, then build + full regression — not `pnpm rebuild` (which can't reproduce the fresh-install path). Back it with a fast pre-flight in the orchestrator (`onlyBuiltDependencies` is the root fix; the pre-flight is the safety net for a forgotten reinstall). Also: a UI scroll-into-view assertion that flakes under post-reinstall cold caches (e.g. PSQL-28) is a test-timing problem, not an environment failure — confirm by re-running before attributing it to the dependency change.

## 2026-06-23: Durably eliminating the Node 24 + yauzl truncated-rg.exe class — bump the dependency, don't patch the unzip

The Windows host runs Node v24.16.0 on PATH. `@vscode/ripgrep@1.17.1`'s postinstall unzipped `rg.exe` via yauzl streaming inflate, which truncates entries > ~5 MB on Node 24 (the inflate stream never emits `end`). The truncated `rg.exe` (5,384,573 B vs 5,429,760 B) is a broken PE → global search silently returns 0 matches. The first pass only re-extracted the binary by hand — a band-aid that recurs on every `pnpm install`. The durable fix bumped the dependency to `^1.18.0`.

### 1. Eliminate the fragile code path; don't patch or verify around it
- **Problem**: The candidate "permanent" fixes were a `pnpm patch` on the unzip, or a postinstall re-extract verifier. Both keep the download+unzip surface alive and merely repair its output. `pnpm patch` is also brittle on pnpm 11 (a patch that no longer applies hard-fails the install, or with the escape hatch silently un-applies).
- **Lesson**: `@vscode/ripgrep@1.18.0` deleted `lib/download.js` / `lib/postinstall.js` / the `postinstall` script / the `yauzl` dependency entirely — the binary now ships pre-extracted inside per-platform packages (`@vscode/ripgrep-<platform>-<arch>`, os/cpu-gated `optionalDependencies`), SHA256-verified at publish. No download, no unzip, no network, no postinstall → the truncation class is structurally impossible on any machine/Node version. When a whole bug class lives in a dependency's install path, prefer the upstream version that removes the path over patching it. Peer evidence: this is exactly what VS Code itself shipped (`build/prepare-binaries.js` verifies against `binaries.lock.json` at publish, then ships verbatim). pnpm records all 12 platform packages in the lockfile and installs only the matching os/cpu on each host — strictly more portable than a downloader.

### 2. An existence-only integrity check is a lie — check size, not just presence
- **Problem**: The project's own postinstall safety net (`scripts/ensure-ripgrep-binary.js`) checked only that `rg.exe` *existed*. A truncated 5.38 MB file exists, so it reported "already present" and the corruption sailed through to runtime. The guard meant to catch this was blind to it.
- **Lesson**: Any "is this artifact OK?" gate must assert a content invariant (size floor, hash, header), never mere existence — a partially-written file is the exact failure these gates exist to catch. The hardened gate now checks existence AND a 2 MB size floor; the pure decision (`classifyRipgrepBinary`) is unit-tested (`test/unittest/ensure-ripgrep-binary.test.mts`, ERG-U-01..08) so the gap cannot reopen, and the same floor is mirrored in the orchestrator env pre-flight (`_check_ripgrep_binary`) as defence-in-depth.

### 3. In an Electron + pnpm app, a dependency that flips CJS→ESM + download→platform-packages is not a one-line bump
- **Problem**: 1.18.0 is ESM-only (`"type":"module"`) and relocates the binary into a per-platform package. The main process is bundled CJS and did `require('@vscode/ripgrep')`; the binary was unpacked via an `asarUnpack` glob on `node_modules/@vscode/ripgrep/**`; the postinstall verifier resolved `@vscode/ripgrep/bin/rg.exe`. All three break silently under a naive version bump.
- **Lesson**: Bumping such a dependency ripples into (a) the consumer — resolve the platform package's binary file directly (`require.resolve('@vscode/ripgrep-<platform>-<arch>/bin/rg[.exe]')`) so the CJS bundle never depends on the Electron runtime supporting `require(ESM)`, keeping the wrapper as fallback; (b) packaging — extend `asarUnpack` to the per-platform package (`node_modules/@vscode/ripgrep-*/**`); (c) the postinstall verifier — resolve the new layout. Verify the whole chain with a clean reinstall → build → packaged-app smoke (the global-search suite spawns the real rg), not just a typecheck. Map the integration points before bumping; the dependency graph hides them. **pnpm gotcha:** the per-platform package is NOT hoisted to top-level `node_modules` — it is only resolvable from WITHIN `@vscode/ripgrep`. And 1.18.0's `exports` map blocks `require.resolve('@vscode/ripgrep/package.json')` (`ERR_PACKAGE_PATH_NOT_EXPORTED`). The working cascade: try a direct `require.resolve(platformSpecifier)` (flat/npm), else `createRequire(require.resolve('@vscode/ripgrep')).resolve(platformSpecifier)` (resolve the wrapper ENTRY — not its package.json — then scope createRequire to it), else the ESM wrapper's `rgPath`.

### 4. A from-scratch `rm -rf node_modules` install is the only way to catch a native-module build that "always worked" only because node_modules was never wiped
- **Problem**: The faithful fresh-clone install (`rm -rf node_modules && pnpm install`) — done to validate the ripgrep bump — exposed a SECOND, unrelated environment failure: the project postinstall `electron-rebuild -f -w node-pty,better-sqlite3` force-builds node-pty from SOURCE, and node-pty's bundled winpty gyp action `cmd /c "cd shared && GetCommitHash.bat"` fails on this Windows host, aborting the whole postinstall non-zero (so `ensure-ripgrep-binary.js` never even ran). This had been invisible because node_modules was never wiped — the working tree carried a previously-built state.
- **Lesson**: node-pty 1.1.0 is **N-API** (`node-addon-api ^7`) and ships per-platform prebuilds (`prebuilds/<platform>-<arch>/{pty,conpty,conpty_console_list}.node`) that are ABI-stable across Node/Electron — it does NOT need an Electron-ABI rebuild at all. The ONLY module here that genuinely needs `electron-rebuild` is **better-sqlite3** (traditional native, ABI-specific). The force-rebuild of node-pty was both redundant AND the thing failing. Fix: scope electron-rebuild to the module that needs it with `--only` (not `-w`, which does NOT exclude others): `electron-rebuild -f -o better-sqlite3`. This makes a fresh `pnpm install` succeed on any Windows host. General rule: distinguish N-API natives (prebuilds suffice, never rebuild) from ABI-specific natives (rebuild), and use `electron-rebuild -o <abi-specific-module>` to rebuild ONLY the latter. Validate dependency-config changes with `rm -rf node_modules && pnpm install`, never `pnpm rebuild`.

## 2026-06-23: EDR full-suite "timing flakiness" is mostly TEST-DESIGN races — gate on the OUTCOME (方案2), don't widen budgets

On an EDR/AV Windows host (every process spawn taxed 1.3–12.9 s) the full regression failed a different ~3–4 suites each run (shifting set), never green across 3 iterations. Peer research (Google/Fowler test pyramid, Chromium perf-dashboard, Playwright/Cypress auto-waiting, MS Dev Drive) framed the fix; per-suite analysis then showed **5 of 6 "EDR flakes" were not "slow" at all — they were test-design races/conflations**, plus **1 genuine product bug**. The durable fix is the *test-architecture* one (方案2: wait for the deterministic OUTCOME, separate perf from correctness), because the *environment* fix is blocked here (see lesson 4 below).

### 1. The "deadline is a hang-detector, not a perf budget" rule, applied
- **Problem**: autotests gated correctness on fixed per-wait timeout BUDGETS (45–200 s). A correct-but-slow operation on an EDR host trips the budget → red. Widening the budget either still flakes or turns the gate into a slow hang-detector with the wrong name.
- **Lesson**: A correctness wait must poll the OUTCOME with a *generous hang-detector* ceiling so a slow-but-correct run passes and only a true hang fails; a performance check must be SEPARATE and non-gating (measured, or N-trial pass-if-≥1-of-N with margin). Industry split: correctness gates, perf is measured/tracked (Chromium never pre-submit-gates on an absolute ms threshold). Concrete fixes this session: DSM-02/RSM-02 split `shell-visible` (gating) from `shell-latency-3trial` (≥1-of-3, non-flaky); TP-06 dropped a noisy throughput A/B from the gate, kept it as a logged `measured` field, gated only on the deterministic hidden-suppression state.

### 2. Polling a FROZEN cache / a one-shot-observed transient is the #1 race class
- **Problem**: GDS-29 polled the renderer's diff file-LIST (`getFileList`), which the product refreshes with ONE post-action re-diff; under EDR write-visibility lag that single re-diff read pre-revert git status and then the cache FROZE — the 80 ms poll watched a value that could never change and burned the whole ceiling. ### 5. (2026-06-24 closure) The shifting failure set is ONE meta-pattern with sub-classes — poll GROUND TRUTH, never a stale/early/proxy snapshot
- **Problem**: `--repeat 3` run#1 was NOT STABLE (iter1+iter3 failed *different* suites — the shift), run#2 reached **STABLE 3/3 (81 PASS / 1 SKIP / 0 FAIL each)**. The whack-a-mole feeling is an illusion: every distinct failure was the same meta-bug — an assertion reading a value BEFORE the async state it describes had settled under EDR — wearing a different costume per suite.

### 6. (2026-06-24) Two Windows environment-固化 fixes the readiness work surfaced — durable across machines, distinct from load-tuning
- **EPERM on fixture `rmSync`**: the 3 GDS group-runners (`run-git-diff-submodule{,-refresh}`, `run-git-diff-ux-tree`) share ONE `fixtures/git-diff-staleness-and-submodule/runtime/`; a prior runner's lingering EDR/git/electron handle held it open past `robustRmSync`'s 10×/5.5 s retry → EPERM aborted the next fixture build (→ the GDS cluster ran against a broken/absent fixture). **Lesson**: on Windows you usually cannot DELETE a directory with a locked child, but on NTFS you CAN **rename it aside** (a directory-entry rename; stale handles keep pointing at the renamed inode), freeing the canonical path for a fresh build. Added a rename-aside last resort to `robustRmSync` + a best-effort husk sweep + `/runtime.stale-*/` to the fixture `.gitignore`. The structurally-cleaner long-term fix is a unique per-invocation runtime dir, but rename-aside is the low-risk durable patch.
- **Shell quote-retention in fixture create**: `test-pdf-epub-preview.ts` created its scratch marker with a raw POSIX idiom `printf '%s' '…' > '${NAME}'`. Under a NON-bash Windows shell the single quotes around the redirect target are not stripped, so the file is created as **`'__autotest_pdf_epub_marker.txt'`** — quotes literally IN the name. That quoted name then evades BOTH the runner EXIT-trap sweep and the orchestrator sweep (both match the unquoted `__autotest_` prefix), leaking permanently into the working tree while every sweep reports "clean". **Lesson**: any fixture command sent to the autotest terminal MUST be built per-platform with an EXPLICIT shell invocation (the copy/delete builders already do `powershell -Command "…"`); never assume the terminal's default shell strips POSIX quotes. Fixed with a platform-aware `platformBuildWriteMarkerCommand` (`Set-Content -LiteralPath` on win32). This is the cross-platform-fixture hard rule (CLAUDE.md) in action: a POSIX idiom in a fixture command is a latent Windows leak even when the assertion passes.

## 2026-06-24 (final): reactive per-suite hardening does NOT converge — the HOLISTIC `waitFor` scale + a product crash fix did. STABLE 2/2.

The 3/3 in § "2026-06-23" was a calm-EDR fluke. Re-running `--repeat 2/3` kept failing a DIFFERENT ~4-6 suites each time (15+ distinct suites across runs) — proof the readiness/latency meta-pattern is pervasive and that fixing only the suites that happened to fail this run never catches up. What actually converged it:

### 7. The single highest-leverage fix: scale the SHARED `waitFor` ceiling in ONE place
- **Problem**: per-suite hardening is whack-a-mole; each 6-hour full run re-discovers more flaky suites.
- **Lesson**: the autotest `waitFor` is built ONCE in `ProjectEditor.tsx` (~8660, inside the `ONWARD_AUTOTEST` bootstrap, so autotest-only) and reaches ~every suite: most suites use `ctx.waitFor` directly; the common helpers (`waitForGitDiffOpen` / `waitForImagePreview` / `waitForGitHistoryOpen` / `waitForDiffLargeFile`) all `return waitFor(...)` (inherit it); and the only suite with a local `waitFor` (`test-git-diff-staleness`) delegates to `baseWaitFor` = `ctx.waitFor`. Scaling its ceiling there (`EDR_WAIT_SCALE = 2.5`, applied ONLY to ceilings ≥ 3000 ms so short "confirm-X-does-NOT-happen" / quick-close waits keep their tight window) hardens the whole in-app suite set with one edit. It is nearly free: `waitFor` short-circuits the instant the predicate is true, so a passing wait is NOT slowed — the scale only extends the give-up point for a wait that would otherwise time out mid-spawn-tax. This collapsed the shifting failure set from 6+ suites to ONE. Helpers that roll their OWN poll loop (`waitForTerminalCwd`, the GSM mirror loops, the CDP `.mjs` drivers) don't inherit it and need their own ceiling/scale — but they are few.

### 8. A teardown SEGFAULT is a PRODUCT bug, not a flake — fix the code (crash-vs-flake split)
- **Problem**: `prompt-input-latency` segfaulted ~1-in-750 suite-quits, ALWAYS after `[AutoTest] done`, during `cleanupIpcHandlers`, before the perf-trace flush (so the trace was lost). Could not be reproduced in isolation (only under full-suite EDR pressure).
- **Lesson**: the (this-session-new) `destroyAllWindowsForQuit` HARD-destroyed the window (`w.destroy()` frees the webContents native object) BEFORE `cleanupIpcHandlers` disposed the native subsystems that hold a webContents reference (GitStateMirror worker, parcel-watchers) → a callback in that gap touched freed memory = use-after-free segfault. **Correct invariant: dispose native subsystems FIRST, THEN destroy windows, THEN `app.quit()`** — so reorder every quit path to `cleanupIpcHandlers()` → `destroyAllWindowsForQuit()` → `app.quit()`. Also added crash-survivable `logQuitPhase()` **console** breadcrumbs (perfTrace is buffered and lost on a teardown crash; a console line survives in the runner log and pinpoints the last phase reached). No segfault in ~480+ quits since. When a crash can't be isolate-reproduced, root-cause it from WHERE in teardown it landed (the missing trace + the last log line) and fix the ordering invariant — don't paper it over in the test.

### 9. Scaling timeouts HELPS converging waits but HURTS never-converging ones (it can CAUSE timeouts)
- **Problem**: a blanket `edrMs(2.5x)` on the GSM own-loops fixed GSM-08 (static) but made `gsm17` TIMEOUT (272.9 s vs 270 s budget, consistently).
- **Lesson**: `gsm17`'s own comment says "the badge never converges, so every step waits out its full timeout" — those waits TIME OUT rather than short-circuit, so scaling their ceiling DIRECTLY multiplies every step's cost. Scaling is only "free" for waits that SUCCEED (short-circuit); for waits that habitually give up at the ceiling, scaling is pure added runtime. Fix: revert the over-scale (GSM-08 stays covered by the holistic `ctx.waitFor` scale on its flip-watch) and, per the CLAUDE.md oversized-TIMEOUT rule, TRIM the isolated `gsm17` split to 1 trial (its per-`(trial,phase)` assertions are independent, so one full 12-phase matrix pass still gates the behaviour). Before scaling a wait, ask: does this predicate normally SUCCEED (scale freely) or normally TIME OUT (scaling just burns budget)?

### 10. Validate individual fixes in ISOLATION; full-run ONLY for final acceptance
- **Lesson** (user directive): do not burn a 6-hour full `--repeat` run to *discover* failures or to validate a single fix. Validate each fix with `run-full-regression.py --only run-<suite> [--repeat N]` (cheap, minutes). Run the FULL regression only once, for final global acceptance, after all individual fixes are in. When an acceptance run does surface failures, collect ALL of them, fix + isolate-validate each, then do ONE re-acceptance run — never fix-one-then-full-run repeatedly.

## 2026-06-25: EDR full-regression convergence — transferable methodology lessons (structured)

> A methodology-layer distillation of the technical detail in §7–§10 above (Problem / Cause / Lesson, for quick scanning). §1–§10 are "what the bug was"; this section is "how to THINK next time you hit the same class."

### A shifting failure set is ONE meta-bug, not N independent bugs
- **Problem**: the full regression failed a DIFFERENT set of suites each run (A/C this run, B/D/E the next) — endless whack-a-mole.
- **Cause**: I reacted suite-by-suite ("fix whatever failed this run"), treating the COUNT of symptoms as the count of bugs, and burned a 6-hour full run each time just to re-discover more.
- **Lesson**: the **randomness/drift of the failure set is itself the diagnostic signal** — a stably-reproducing failure is a deterministic bug; a drifting one is a single shared, probabilistic root cause. When you see drift, STOP and find the common cause; do not fix one-by-one. (Same as ML's "don't overfit to a single sample — look at the data-generating mechanism.")

### When reactive fixing won't converge, find the LEVERAGE POINT (single point of control)
- **Problem**: per-suite hardening ran for several rounds and still drifted — no convergence.
- **Cause**: I hadn't realized that almost every suite's readiness waits come from ONE shared `waitFor` (built once in `ProjectEditor.tsx`, passed to all suites; the few local helpers delegate back to it).
- **Lesson**: **when you're making the same class of change in N places, there is almost always an upstream confluence point where one edit replaces N**. Here: one EDR scale on the shared `waitFor` collapsed the shifting set from 6+ suites to 1. On any repetitive change, first ask "is there a common upstream?"

### A crash ≠ a flake — a crash is a PRODUCT bug, and is often "teardown in the wrong order"
- **Problem**: a suite segfaulted ~1-in-750 quits, not reproducible in isolation.
- **Cause**: the quit path HARD-destroyed the window (freeing the native webContents) BEFORE disposing the native subsystems (worker/watcher) that still held a reference → a callback in that gap touched freed memory (use-after-free). The JS `isDestroyed()` guard can't stop a native dangling pointer, so it's a segfault, not a catchable exception.
- **Lesson**: (1) **handle crashes and flakes differently** — flakes harden the test, crashes fix the code. (2) **Destruction order must be the reverse-topological order of dependencies**: tear down the "users" before the "used". (3) **An un-reproducible crash is located by "which step did it die on"** — what trace/log got written vs. what didn't is bisection information; use **synchronous, crash-survivable breadcrumbs** (console) rather than a pretty trace that buffers and is lost on a teardown crash.

### Before applying any GLOBAL scale/knob, understand its direction of effect per sub-group
- **Problem**: adding a 2.5× timeout scale to the poll loops (meant to help suite A) instead CAUSED suite B (gsm17) to time out consistently.
- **Cause**: scaling is free for waits that USUALLY SUCCEED (they short-circuit on success); but for waits that are DESTINED TO TIME OUT it directly multiplies their cost. gsm17's waits "never converge — every step waits out its full timeout", so the scale pushed it past budget.
- **Lesson**: **the same knob can have OPPOSITE effects on different sub-groups** (like a global learning rate across heterogeneous layers). Before any global transform, ask "is its effect same-signed and beneficial for every sub-group?" Fix: revert the over-scale + trim the over-budget suite's trial count.

### Passing once ≠ stably passing; conclude from statistics, not a single sample, on a stochastic system
- **Problem**: I reported "STABLE 3/3 — done" mid-way and wrote it into the docs; it turned out to be a calm-EDR LUCK WINDOW and failed on re-run.
- **Cause**: I treated a SINGLE observation of a stochastic process as evidence.
- **Lesson**: **burn `(1-p)^N` into your head** — 80 suites in series, a tiny 0.5% per-suite flake rate → only 66% of single runs all-green, only 44% for two in a row. Small per-unit unreliability is amplified exponentially under large-scale series; this is why you must drive it very low AND why a holistic lever beats per-suite fixing. Never declare success prematurely.

### Match the granularity of validation to the granularity of the fix
- **Problem**: I repeatedly used 6-hour full runs to validate single-point fixes.
- **Cause**: I didn't separate "single-point validation" from "global acceptance".
- **Lesson** (user correction): **validate a single fix in ISOLATION** (`--only run-<suite>`, minutes); run the FULL regression ONLY for final global acceptance. Reserve the expensive full run for "does the whole still hold?", and answer "did this one spot get fixed?" with the cheapest, fastest experiment. (Same as ML's "validate on small data / a unit first, then run the full training.")

## 2026-06-25: Electron postinstall integrity gate failed a healthy macOS extraction (wrong file size-floored)

### On macOS the `Contents/MacOS/Electron` is a ~34 KB launcher stub, NOT the >100 MB payload
- **Problem**: `pnpm install` failed in `scripts/ensure-electron-binary.js` with "electron binary still missing/truncated after re-extracting", even though the extraction was perfectly healthy (the launcher ran and printed `v39.8.5`). This aborted the `&&`-chained postinstall, so `electron-rebuild better-sqlite3`, the node-pty spawn-helper step, and the ripgrep check never ran — `better_sqlite3.node` was absent and the tree looked "installed" but was half-prepared.
- **Cause**: the health check size-floored a FIXED path — `binaryRelPath()` — against 50 MB. That assumption ("Every platform's Electron executable is >100 MB") is true on Windows (`electron.exe`) and Linux (`electron`), but FALSE on macOS: `Electron.app/Contents/MacOS/Electron` is only a ~34–50 KB launcher stub; the ~170 MB payload lives in `Frameworks/Electron Framework.framework/Versions/A/Electron Framework`. So the floor could NEVER pass on a healthy macOS dist.
- **Lesson**: know the platform's actual binary layout before size-flooring a path. On macOS the heavy code is in the framework dylib, not the `MacOS/<app>` launcher. The robust, genuinely cross-platform integrity signal is **"does the extracted tree still contain at least one file ≥ floor?"** (largest-file probe) — it tracks the yauzl-truncation symptom (the single heavy entry is dropped) without depending on WHICH file is heavy per platform, and it survives future layout changes.

### A "unified cross-platform" check must be validated against each platform's real data, not an assumption
- **Problem**: the check was written to fix a Windows yauzl-truncation issue and deliberately reused one shared code path for Windows + macOS. It worked on Windows but silently never passed on macOS — the "unified" path was only ever validated on one platform.
- **Cause**: the shared invariant ("the path.txt target is >100 MB") was assumed to hold everywhere instead of being checked per-platform with actual file sizes. The asymmetry (macOS splits launcher vs. framework; Win/Linux do not) was invisible until run on a Mac.
- **Lesson**: a single shared check is good for maintainability, but "shared" is only correct if the invariant it relies on is true on EVERY platform. Before committing a cross-platform unified path, verify its core assumption against real artifacts on each OS — or pick an invariant (like largest-file-size) that is inherently platform-agnostic.

### Don't trust a self-heal gate's own failure LABEL — verify the artifact directly
- **Problem**: the script's message framed the failure as a "yauzl/Node24 truncation symptom", and the cached zip's binary entry was indeed only 33,968 bytes — both pointed at "corrupt download / bad extraction". The real artifact was fine; only the gate's verdict was wrong.
- **Cause**: I initially trusted the gate's framing and started down "the cached zip is corrupt" before checking the extracted tree directly. Comparing the `MacOS/Electron` entry size across cached zip versions (v33/v35 = 50 KB, v39 = 34 KB — all tiny) and confirming the 173 MB framework dylib + a runnable launcher disproved the "truncation" story.
- **Lesson**: a gate that self-diagnoses can mis-diagnose; its failure label is a hypothesis, not a finding. When a "corruption"/"truncation" gate fails, inspect the actual artifact (run the binary, compare sizes across known-good references) before acting on the gate's stated cause. Data-first beats trusting the error message's framing.

## 2026-06-25: Packaged app crashed at launch — a native module's optional PLATFORM package was not bundled

### pnpm + electron-builder silently drops a native module's NESTED optional platform package
- **Problem**: the packaged app (`pnpm dist:dev`) launched its main process but showed no window. The real error (only visible by reading the main-process console, not from the alive main PID): `No prebuild or local build of @parcel/watcher found. Tried @parcel/watcher-darwin-arm64`. `@parcel/watcher`'s JS made it into `app.asar`, but the native `@parcel/watcher-darwin-arm64/watcher.node` was bundled NOWHERE (not in asar, not in `app.asar.unpacked`).
- **Cause**: `package.json` declared only `@parcel/watcher` (a production dep); its platform binary `@parcel/watcher-darwin-arm64` is a NESTED `optionalDependency` of `@parcel/watcher`. Under pnpm that nested optional package gets NO top-level `node_modules/@parcel/` symlink, so electron-builder's dependency tracer never collects it. `@vscode/ripgrep` had hit the exact same wall earlier — which is why all six ripgrep platform packages are declared as DIRECT `optionalDependencies` in this repo AND listed in `asarUnpack`. `@parcel/watcher` was simply missing that same treatment. It only manifests in a PACKAGED build (unpackaged dev resolves the nested package straight off disk), so it can hide until the first real dist.
- **Lesson**: when a native module resolves a platform-specific sub-package by name at runtime (`require('@parcel/watcher-' + platform + '-' + arch)`), declare every target platform's package as a DIRECT `optionalDependency` (so pnpm hoists a top-level symlink and electron-builder's tracer + `asarUnpack` glob can both see it), and add `node_modules/<scope>/<pkg>-*/**` to `asarUnpack` so the `.node` lands unpacked (Node cannot `dlopen` a `.node` from inside an asar). Mirror the in-repo ripgrep precedent. Cross-platform nuance: unlike ripgrep's single libc-agnostic binary, `@parcel/watcher` picks a `-glibc` vs `-musl` variant via `detect-libc` at runtime, so BOTH Linux libc variants must be declared, not just glibc.

### "App launched" is NOT "main process is alive" — verify the RENDERER / main UI
- **Problem**: I earlier reported "startup smoke test PASS" after only confirming the main process PID was alive. The app was in fact broken — the main process survived but no window ever rendered, because a `require()` threw before the BrowserWindow's content loaded. The user hit the broken window I had called "PASS".
- **Cause**: a dead-on-arrival renderer does not kill the main process. The main Electron process can stay alive (event loop running) while the window is blank / never created. "Main PID exists" is a necessary but FAR-from-sufficient signal, yet I treated it as acceptance.
- **Lesson**: the honest launch-smoke signal is "a `--type=renderer` helper process exists (and stays alive a few seconds, not crash-looping)" — that proves web content actually loaded, which is what "enter the main UI" means. Check the full process tree (`ps -Ao pid,args | grep -F "<exact app name> Helper"` then group by `--type=`), not just `pgrep -lx "<main>"`. Bonus trap that bit me the same round: `pgrep -f "Helper (Renderer)"` treats the literal parens as a regex group and silently fails to match — use `grep -F` (fixed-string) for process names containing `()`.
